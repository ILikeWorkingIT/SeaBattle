# Нефункциональные требования

**Статус:** `Согласовано` (2026-08-24). Изменения вносятся отдельным решением заказчика.

**Контекст:** `requirements/glossary.md`, `requirements/functional-requirements.md`  
**Источник правды:** `documentation/specification-sea-battle-v1-1.md`  
**Модель качества:** ISO/IEC 25010:2023 (модель качества продукта)  
**Нумерация:** с `NFT-001`.

Термины и коды (`MISS`, `HIT`, `SUNK`, `GAME_OVER`, игровая сессия, десктопный клиент, серверный ИИ) — по глоссарию. Формулировки без стека и UI-решений, кроме каналов REST / WebSocket, уже зафиксированных в согласованных ФТ.

---

## Границы модели (7 характеристик)

В ISO/IEC 25010:2023 у модели качества продукта **9** характеристик. В эту таблицу включены **7** характеристик качества, которые задают НФТ (не поведение партии). Решение заказчика Q1 (2026-08-24): набор подтверждён.

| № | Характеристика (EN) | Русское имя |
| --- | --- | --- |
| 1 | Performance efficiency | Эффективность производительности |
| 2 | Compatibility | Совместимость |
| 3 | Interaction capability | Способность к взаимодействию |
| 4 | Reliability | Надёжность |
| 5 | Security | Защищённость |
| 6 | Maintainability | Сопровождаемость |
| 7 | Flexibility | Гибкость |

**Не включены в таблицу (намеренно):**

- **Functional suitability** — закрывается согласованными ФТ (`FT-001` … `FT-062`), а не отдельными НФТ.
- **Safety** — в ТЗ нет вреда жизни, здоровью или имуществу; для PvE-игры «Морской бой» характеристика не применяется.

## Правила измерения

| ID | Содержание | Статус |
| --- | --- | --- |
| A1 | Контрольная нагрузка MVP: до **3** одновременных активных игровых сессий (как FT-004), каждая с одним десктопным клиентом. | Следует из ТЗ / ФТ |
| A2 | Сеть измерения: один хост или локальная сеть без искусственной задержки. Интернет-SLA в MVP нет. | Решение заказчика Q6 |
| A3 | Процентиль **p95** считается не менее чем по **100** однотипным операциям в контрольном прогоне, если в условии не указано иное. | Решение заказчика (принято вместе с Q2, Q3, Q4) |
| A4 | Время хода серверного ИИ измеряется **на сервере**: от момента, когда право хода перешло ИИ, до момента готового результата выстрела (до отправки клиенту). | Решение заказчика (принято вместе с Q3) |
| A5 | Время ответа на выстрел игрока измеряется **на клиенте**: от отправки выстрела по WebSocket до получения результата `MISS` / `HIT` / `SUNK` / отказ. | Решение заказчика (принято вместе с Q2) |
| A6 | Пороги времени в таблице — согласованные значения заказчика (Q2, Q3, Q4, Q12). | Решение заказчика 2026-08-24 |

## Таблица требований

| NFT-ID | Характеристика | НФТ | Метрика | Условие |
| --- | --- | --- | --- | --- |
| NFT-001 | Эффективность производительности | Система должна вернуть игроку результат его выстрела по WebSocket так, чтобы p95 времени «отправка выстрела → получение `MISS`/`HIT`/`SUNK` или отказа» не превышала 300 мс. | p95 латентности, мс; объём выборки ≥ 100 выстрелов | Контрольный прогон при 1…3 активных игровых сессиях; измерение на десктопном клиенте; сеть по A2 (localhost/LAN); ход принадлежит игроку |
| NFT-002 | Эффективность производительности | Серверный ИИ должен рассчитать матрицу вероятностей и выбрать клетку выстрела так, чтобы p95 времени расчёта не превышала 200 мс. | p95 длительности расчёта Hunt Mode и Target Mode, мс; выборка ≥ 100 выстрелов ИИ | Поле 10×10; до 3 параллельных сессий; измерение на сервере по A4; право хода у серверного ИИ |
| NFT-015 | Эффективность производительности | Система должна создать игровую сессию и выдать игроку его расстановку так, чтобы p95 времени «запрос создания сессии → получение расстановки игрока» не превышала 2 с. | p95 длительности создания сессии, с; выборка ≥ 100 созданий | Сеть по A2; нагрузка 1…3 сессий; генерация двух расстановок (игрок и серверный ИИ) |
| NFT-003 | Совместимость | Система должна одновременно обслуживать до трёх независимых игровых сессий так, чтобы выстрел в сессии A не изменял матрицы полей, историю выстрелов и текущий ход сессии B. | Число искажённых чужих сессий = 0; число проверенных пар сессий ≥ 3 сценария «A стреляет, B ждёт» | 3 активные сессии; параллельные выстрелы; сверка состояния до и после хода |
| NFT-004 | Совместимость | Система должна провести одну партию, используя REST для создания сессии, генерации полей и выдачи статистики и WebSocket для выстрелов, без потери согласованности состояния между каналами. | Доля партий, в которых состояние после REST-инициализации совпадает с первым снимком по WebSocket и статистика после `GAME_OVER` совпадает с запросом по REST = 100% | Выборка ≥ 10 завершённых партий (`GAME_OVER`); MVP-контракт каналов (FT-017, FT-042, FT-055) |
| NFT-005 | Способность к взаимодействию | Десктопный клиент должен оставаться отзывчивым во время сетевого обмена и расчёта хода ИИ: главный цикл интерфейса не блокируется дольше 200 мс. Анимация дольше 200 мс допустима, если цикл интерфейса не заморожен. | Максимальная длительность блокировки UI-потока, мс; число зафиксированных блокировок > 200 мс = 0 | Партия с ходами игрока и ИИ; 1 клиент; прогон ≥ 10 минут или до `GAME_OVER` |
| NFT-006 | Способность к взаимодействию | Система должна показать игроку отказ по нелегальному выстрелу (FT-044…FT-048, FT-051) не позднее чем через 1 с и не менять поле. | p95 времени до сообщения об отказе ≤ 1000 мс; число изменений поля после отказа = 0 | Выборка ≥ 20 отказов каждого класса: повтор, вне поля, чужой ход, после `GAME_OVER`, по своему полю, второй выстрел в том же ходе |
| NFT-016 | Способность к взаимодействию | Десктопный клиент должен при смене языка пунктом меню сразу показать новые подписи экрана на выбранном языке (русский или английский) без пересоздания игровой сессии. | Число подписей, оставшихся на прежнем языке после смены, = 0; игровая сессия сохраняет тот же идентификатор и состояние | Активная партия до и после смены языка; оба направления RU→EN и EN→RU; выбор сохраняется для следующих запусков (FT-062) |
| NFT-007 | Надёжность | Система должна сохранять оперативное состояние игровой сессии в течение скользящего idle TTL 30 минут и возобновлять сессию по идентификатору без потери матриц, истории выстрелов и текущего хода. | Доля успешных возобновлений с побитово сравнимым снимком состояния = 100%; простой между отключением и возобновлением < 30 мин | ≥ 10 циклов «ход → разрыв канала → возобновление по id»; TTL не истёк (FT-005, FT-054) |
| NFT-008 | Надёжность | Серверная часть не должна аварийно завершать процесс и не должна терять три активные сессии в течение 30 минут непрерывной игры. | Число падений процесса сервера = 0; число сессий, исчезнувших без TTL и без `GAME_OVER`, = 0 | 3 сессии; игроки делают выстрелы не реже 1 раза в 2 минуты (idle TTL не срабатывает) |
| NFT-009 | Защищённость | Система не должна передавать десктопному клиенту клетки флота серверного ИИ и матрицу вероятностей, пока соответствующие палубы не стали результатом `HIT` или `SUNK`. | Число клиентских сообщений (REST и WebSocket), содержащих скрытые палубы ИИ или heatmap, = 0 | Перехват всего трафика клиента за ≥ 5 партий до первого `HIT` по флоту ИИ и отдельно проверка heatmap (FT-015, FT-050) |
| NFT-010 | Защищённость | Система должна применять выстрел только к игровой сессии открытого канала и отклонять выстрел с чужим или несуществующим идентификатором без изменения любой сессии и без выдачи состояния чужой сессии. | Число успешных мутаций чужой сессии = 0; доля корректных отказов = 100%; число отказов, содержащих состояние чужой или несуществующей сессии, = 0 | 2 активные сессии; попытка выстрела сессии A с идентификатором сессии B; перебор несуществующих id; ≥ 20 попыток каждого вида |
| NFT-017 | Защищённость | Система должна выдавать идентификатор игровой сессии из пространства не менее 2^128 различимых значений, чтобы идентификатор нельзя было подобрать перебором за время жизни сессии. | Мощность пространства идентификаторов ≥ 2^128; доля угаданных чужих активных сессий за контрольный перебор = 0 | Контрольный перебор не более 10^4 попыток за время прогона; до 3 активных сессий; idle TTL 30 минут |
| NFT-011 | Сопровождаемость | Для каждого Must-требования к правилам партии (FT-006…FT-034, FT-043…FT-052, FT-057, FT-058) должен существовать хотя бы один автоматизированный тест, падающий при нарушении требования. | Покрытие Must-ФТ правилами игры автотестами = 100%; число Must-ФТ без теста = 0 | Контрольный прогон регрессии перед поставкой MVP |
| NFT-012 | Сопровождаемость | Автотесты домена правил и серверного ИИ должны покрывать не менее 80% строк этого домена. | Line coverage домена ≥ 80% | Исключаются слой доставки (HTTP/WS) и клиентский UI |
| NFT-013 | Гибкость | Серверная часть и хранилище состояния должны стать готовы к приёму создания игровой сессии не позднее чем через 60 с после штатного запуска развёртывания из состава поставки. | Время от команды запуска до успешного FT-001, с | Чистая машина с заранее установленным ПО развёртывания; один экземпляр сервера; без ручной правки кода |
| NFT-014 | Гибкость | Десктопный клиент должен запускаться и проводить партию PvE на 64-битной Windows 10, если сервер доступен по A2. | Доля успешных запусков и завершённых до `GAME_OVER` партий = 100% | Windows 10 x64; ≥ 3 полных партий; одновременно не более 3 сессий |

## Вне MVP / вне scope

- Целевая доступность 24/7, процент uptime (Q11), SLA в интернете (Q6), CDN, горизонтальное масштабирование сверх 3 сессий.
- Лимит времени на ход игрока (Q9); обрыв партии — idle TTL 30 минут (FT-005, FT-053).
- Клиент на Linux и macOS (Q5).
- Идентификация игрока, аутентификация, роли, персональные данные (логин вне MVP); доступ к партии — по идентификатору сессии (Q7).
- PvP, ручная расстановка, рейтинг.
- Functional suitability и Safety как отдельные НФТ (Q1).
