## 1. Анализ критических ошибок (Архитектурные нарушения DDD)

### C1. Эфемерный расчёт объявлен Aggregate Root

`Heatmap` смоделирован как агрегат с обязательным `HeatmapId`, хотя у него нет жизненного цикла, хранилища и инварианта согласованности между транзакциями. FT-002 **явно исключает** матрицу вероятностей из оперативного состояния сессии. Расчёт — функция от снимка `Session` на один ход Бэкенда.

В каноне DDD это **доменная служба** + набор VO (`WeightGrid`, `TargetArea`, результат выбора). Искусственный корень с id «на время расчёта» размывает смысл агрегата (Evans: агрегат — граница транзакционной согласованности хранимого кластера).

### C2. Связь агрегатов без ID: Runtime → Settings

В сводке заявлено «между агрегатами только ID», но таблица связей Runtime:

`Runtime | Settings | 1 : 1 | Тот же Фронтенд читает язык из локальных настроек`

Это **прямая объектная связь** двух корней (Settings и Runtime), без `InstallId`. Нарушение правила ссылок между агрегатами.

### C3. `Cell` объявлен Entity без собственной идентичности

У клетки нет id, кроме `coords`. Координаты не меняются; клетки не создаются и не удаляются. Жизненный цикл клетки = жизнь `Board`. Это классический **Value Object** (идентичность = значение координаты), а не сущность. 200 «сущностей» внутри одного агрегата раздувают граф без выигрыша в согласованности.

Граница агрегата `Session` при этом **не перегружена по смыслу транзакции**: выстрел обязан атомарно менять клетку, палубу, право хода, TTL и историю (UC-002 / UC-003). Это правильный корень. Ошибка — классификация `Cell`, не размер транзакции.

### C4. `EndReason.EmptyHeatmap` как причина `GAME_OVER`

В `Session.endReason` значение `EmptyHeatmap` допускается только вместе со статусом `GameOver`. По FT-052 / FT-075 / глоссарию:

- пустая heatmap **и** флот Игрока уничтожен → `GAME_OVER`, причина — **уничтожение флота** (победа Бэкенда), не «пустая heatmap»;
- пустая heatmap **и** флот жив → `SESSION_ABORTED`, сессия **удаляется**, `GAME_OVER` **нет**.

Литерал `EmptyHeatmap` на завершённой партии противоречит ФТ и размывает границу агрегата (сбой heatmap — удаление, а не статус `GameOver`).

## 2. Несоответствия исходным требованиям (ФТ/UC/Глоссарий)

### 2.1. Единый язык

A0138/A0139 сознательно ввели английские идентификаторы. Глоссарий при этом **остался русским** (игровое поле, клетка, палуба, ход, матрица вероятностей, глобальная статистика). Для вайбкодинга это терпимо, для UL — **два словаря**.

Расхождения, которые мешают даже при двуязычности:

| Модель | Канон глоссария / ФТ | Суть |
| --- | --- | --- |
| `Board` | игровое поле | EN в глоссарии нет; «Board» не зафиксирован |
| `turn` | право хода / ход | «ход» в статистике = выстрел (A0015); `turn` путает очередь и сам выстрел |
| `Mark.Clear` | непроверенная клетка (FT-044) | выдуманный литерал; в глоссарии кода нет, в ФТ — «проверена / непроверена» |
| `Facing` | горизонталь / вертикаль (расстановка) | дальше от канона, чем `Orientation` |
| `WeightGrid` | матрица вероятностей / Heatmap | глоссарий уже даёт EN **Heatmap** |
| `Ledger` / `Record` / `Snapshot` | глобальная статистика, запись партии | в глоссарии нет Ledger |
| `Glyph` | отображение A0099 | нет в глоссарии (допустимо в Generic BC) |
| `ShipStatus.Wounded` | для **выстрела** HIT и «ранен» не разделяются (A0028) | на уровне **корабля** «ранен» в глоссарии есть; путаница, если Wounded попадёт в API выстрела |

Имена `Session` ↔ игровая сессия / матч (A0010), `Fleet`/`Ship`/`Deck`, `MISS`/`HIT`/`SUNK`/`GAME_OVER`, Hunt/Target — согласованы по смыслу.

**Участник** из глоссария в модели сведён к `Side` — приемлемо (нет PlayerId, A0016).

### 2.2. Потерянные или оторванные атрибуты

| Пробел | Требование |
| --- | --- |
| `CellCode` описан как VO, но **ни у одной сущности нет атрибута** с этим типом; FT-063 не привязан к клетке | FT-063, A0013 |
| Не зафиксировано, что код клетки **выводится** из индексов (А3→`02`) и не живёт отдельно от `column`/`row` | глоссарий §2 |
| Нет инварианта согласованности `Cell.occupancy` и `Ship.decks` (двойная запись одной палубы) | FT-009, FT-013 |
| Независимость сессий (выстрел A не меняет B) нет в инвариантах Session/Registry | FT-003, NFT-003, UC-003 §5.5 |
| Возобновление: вернуть матрицы, историю, текущий ход; TTL не сдвигать | FT-002, FT-054, UC-006 |
| Перечень оповещений партии не отражён даже как доменные события | FT-036, FT-066, FT-076 |
| Источник оставшегося TTL — Бэкенд (`ttlAnchor`+`idleTtl`); `RemainTtl` на Runtime — копия | FT-080, A0120 |
| Канал сдачи — мутация партии (WebSocket), не REST | A0130, UC-005 |

### 2.3. Логика статусов vs UC/ФТ

- `SessionStatus.GameOver` vs A0142: после `GAME_OVER` агрегат **не обязаны** хранить. Статус `GameOver` имеет смысл только **в момент фиксации** и доставки события; дальше источник истины исхода — `Ledger.Record`. В модели это сказано слабо (инвариант про «не хранить снимок» есть, связь со статусом — нет).
- `Shot.gameOver` дублирует FT-071 и `Session.status` / `winner`: при хранении двух фактов они разъедутся.
- `eventId` как отдельный атрибут при каноне `seq` (A0141) провоцирует второй счётчик, несмотря на текст «синоним».

## 3. Рекомендации по оптимизации

Формат «Было → Стало».

| # | Было | Стало |
| --- | --- | --- |
| R1 | Агрегат `Heatmap` + `HeatmapId` | BC Heatmap без агрегата: служба `HeatmapBot.aim(SessionSnapshot) → Aim`. VO: `WeightGrid`, `TargetArea`, `Remaining`, `Aim` (`Picked`+клетка или `Empty`) |
| R2 | `Cell` — Entity | `Cell` — VO на `Board`; идентичность = `CellCoordinate` |
| R3 | `Runtime` — Settings 1:1 «читает язык» | `Runtime.settingsId: InstallId` (только ID) |
| R4 | `EndReason.EmptyHeatmap` при `GameOver` | Убрать. `GAME_OVER` только `FleetLost` \| `Surrender`. Пустая heatmap + живой флот → не статус сессии, а удаление + `SESSION_ABORTED` |
| R5 | `Shot.gameOver` | Удалить атрибут. FT-071 — инвариант применения выстрела на корне `Session` |
| R6 | `Shot.eventId` + VO `EventId` | Не моделировать второй идентификатор. Для транспорта: идемпотентный ключ = `seq` (A0141). Имя поля API — позже |
| R7 | `CellCode` рядом, но нигде не стоит | `CellCoordinate.code` — производная двухцифровая строка (FT-063); не отдельное хранимое поле |
| R8 | `Mark.Clear` | `Unchecked` (как FT-044 «ещё не проверена») |
| R9 | `WeightGrid` | `Heatmap` как имя VO матрицы (термин глоссария); служба не называется так же, как VO: служба `HeatmapBot`, VO `Heatmap` |
| R10 | `Duration` для idle TTL | `IdleTtl` (термин глоссария/ФТ) |
| R11 | Две копии палуб: клетка и `Ship.decks` | Инвариант: множество координат палуб корабля = клетки с `occupancy.ship = этот ShipId` |
| R12 | `turn` | Оставить имя (A0139) **или** переименовать в `toMove`; в глоссарии модели явно: «право хода, не номер выстрела» |
| R13 | Старт = два агрегата (Registry + Session) | Явная доменная/прикладная служба `StartSession`: проверка слота → создание Session → запись `GameSessionId` в Registry. Не вкладывать чужие сессии в `Session` |
| R14 | `GAME_OVER` + `Ledger` (A0129) | Оставить как **единственную** допустимую совместную фиксацию двух корней; не размножать такие транзакции |
| R15 | Глоссарий без EN-идентификаторов | Отдельной командой: колонка EN в глоссарии = имена модели (не смешивать в одном предложении «игровое поле» и `Board` без таблицы) |

`Registry` как отдельный корень внутри BC Session **оставляем** (A0143): инвариант «≤ 3» нельзя честно положить внутрь одной `Session`.

`Board` и `Fleet` оставляем Entity: у каждого есть идентичность стороны (`owner`) и изменяемое содержимое; это не «адрес».

`Runtime` / `Settings` — не домен боя; для вайбкодинга UI допустимы как Generic BC. Не тащить `shotPending` на Бэкенд.

## Session

Контекст проводит партию PvE: жизненный цикл игровой сессии, поля, флоты, выстрелы, ход, TTL, лимит слотов. Core.

### Агрегат: Session

*Один матч. Единственная точка входа для изменения полей, флота, истории выстрелов и права хода. Снаружи — только `GameSessionId`.*

#### 3. Бизнес-инварианты и правила

* Сессия не существует и слот не занимает, пока старт не завершён выдачей расстановки Игроку; отказ в окне NFT-015 — без сессии и без статистики (FT-010, A0081).
* Выдать Игроку только `playerFleet` / `playerBoard` (FT-014); флот и heatmap Бэкенда не отдавать (FT-015, FT-050).
* Только PvE; ручной расстановки нет.
* Оба флота: 10 кораблей / 20 палуб, состав 1+2+3+4; прямолинейно; дистанция ≥ 1 клетка включая углы (FT-011, FT-012, FT-013).
* Координаты каждой палубы `Ship.decks` совпадают с клетками своего `Board`, у которых `occupancy.ship` равен этому `ShipId`, и наоборот.
* Первый ход — Игрок (FT-016). Выстрел до старта запрещён (FT-069).
* Выстрел игрока — только канал партии; иначе `SHOT_WRONG_CHANNEL` без изменения состояния (FT-055). Сдача — тот же канал партии (A0130).
* Запрос выстрела без координат / с неверным типом — отказ без изменения состояния (FT-070).
* Стрелять только по полю соперника, в `Unchecked` клетку [0..9, 0..9], при своём `turn`, пока `Active` (FT-044…FT-048).
* `MISS` — ход сопернику; `HIT` и `SUNK` — ход остаётся у стреляющего.
* При `SUNK`: последняя палуба `SUNK`; периметр `MISS` (FT-021, FT-072).
* Уничтожение 10 кораблей (20 палуб) → в том же исходе `SUNK` и отдельно `GAME_OVER`, победа противоположной стороны (FT-025, FT-026, FT-071).
* Сдача: `GAME_OVER` + победа Бэкенда, в том числе на ходе Бэкенда; обрыв ≠ сдача; повторной сдачи после `GAME_OVER` нет (FT-077).
* Мутации сессии упорядочены; первая принятая побеждает (A0124). Сдача до фиксации выстрела Бэкенда отменяет выстрел (A0126).
* Лишние выстрелы той же стороны после первого принятого — отказ (FT-051).
* Применение выстрела атомарно относительно состояния этой сессии; выстрел в сессии A не меняет поля, историю и ход сессии B (FT-003).
* Idle TTL сдвигают только создание и принятый выстрел. Истечение — удаление без `GAME_OVER` и без статистики; Фронтенд оповещается (FT-053, FT-066).
* Обрыв не освобождает слот, пока `Active` и TTL жив (FT-074).
* При `GAME_OVER` слот снимается сразу (A0128). Длительно хранить `Session` для просмотра не требуется (A0142); исход для статистики — `Ledger`.
* Возобновление по id, пока TTL жив: семантически эквивалентный снимок FT-002; TTL не сдвигать (FT-054). Недоступный id — единый отказ без различия причин (FT-067).
* Доменные события партии (не отдельные агрегаты): смена хода; `MISS`/`HIT`/`SUNK` любой стороны; `GAME_OVER`; выстрел Бэкенда (FT-036); TTL (FT-066); `SESSION_ABORTED` (FT-076). Создание сессии — ответ на старт, не push.

#### 4. Связи

Внутри агрегата: Session 1:2 Board, 1:2 Fleet; Board 1:100 Cell (VO); Fleet 1:10 Ship; Ship 1:1…4 Deck; Cell occupancy → ShipId.

Между агрегатами: только `GameSessionId` к Registry, Record, Runtime.
