## 2. Назначение и цели создания системы

### 2.1. Назначение

Система предназначена для проведения пошаговой тактической партии «Морской бой» в режиме игрок против Бэкенда (PvE) и для демонстрации полного цикла постановки и реализации учебной автоматизированной системы.

Вид автоматизируемой деятельности: игровая партия (создание сессии, выстрелы, ход Бэкенда, завершение, учёт глобальной статистики, смена языка интерфейса).

### 2.2. Объекты автоматизации

- Процесс партии на стороне Игрока (ввод хода, наблюдение полей и исхода).  
- Процесс ведения состояния партии и расчёта хода Бэкенда.  
- Учёт глобальных итогов завершённых партий на экземпляре Бэкенда.

### 2.3. Цели создания (измеримые)

| Цель | Критерий |
| --- | --- |
| Обеспечить партию PvE по канону поля 10×10 и флота 10 кораблей / 20 палуб | Соответствие FT-006…FT-026 |
| Обеспечить скрытие расстановки Бэкенда и матрицы вероятностей | FT-015, FT-050, NFT-009 |
| Обеспечить не более трёх активных сессий | FT-004, FT-049, MR-01 |
| Обеспечить создание сессии с p95 не более 2 с | NFT-015 |
| Обеспечить результат выстрела игрока с p95 не более 300 мс | NFT-001 |
| Обеспечить расчёт хода Бэкенда с p95 не более 200 мс | NFT-002 |
| Обеспечить покрытие Must-правил партии автотестами | NFT-011 |

Детализация ценности для стейкхолдера — в документе Vision & Scope.

## 3. Характеристика объектов автоматизации

### 3.1. Сведения об объекте

Объект — локальный игровой контур без идентификации личности. Учётной записи Игрока нет. Доступ к конкретной партии — по идентификатору игровой сессии.

Правила предметной области: классический «Морской бой» (Russian standard rules): поле 10×10; флот 1+2+3+4; прямолинейная расстановка с буферной клеткой; первый ход — у Игрока; исходы `MISS` / `HIT` / `SUNK`; победа при уничтожении флота либо при сдаче Игрока.

### 3.2. Условия эксплуатации

- Фронтенд: 64-битная ОС Windows 10 (норма приёмки NFT-014).  
- Бэкенд и хранилище: контейнерный запуск из состава поставки; сеть измерения — один хост или локальная сеть без искусственной задержки (MR-02).  
- Язык интерфейса: русский или английский; при первом запуске — язык ОС, если он русский или английский, иначе английский.

### 3.3. Границы системы

**Входит:** Фронтенд, прикладной программный интерфейс (создание сессии, статистика, канал партии), хранилище оперативного состояния и журнала статистики, расчёт хода Бэкенда.

**Не входит:** PvP; логин; ручная расстановка; персональная статистика; клиент на Linux и macOS как норма приёмки; доступность 24/7; SLA в сети Интернет.

## 4. Требования к системе

### 4.1. Требования к системе в целом

#### 4.1.1. Структура и функционирование

Система должна включать: подсистему взаимодействия с Игроком (Фронтенд); подсистему прикладной логики и канала партии (Бэкенд); подсистему хранения оперативного состояния и статистики.

Смежные автоматизированные системы **не устанавливаются**.

Режимы: проведение активной партии; запрос глобальной статистики; смена языка интерфейса без изменения состояния партии.

Диагностирование промышленного класса **не устанавливается**. Перспектива развития: post-MVP по Vision & Scope, без обязательств первой очереди.

#### 4.1.2. Численность и квалификация персонала

Штат операторов АС **не устанавливается**. Игрок совмещает роль пользователя UI и, на учебном стенде, роль лица, запускающего зависимости runtime (интерпретатор языка программирования, контейнерная среда). Режим работы — эпизодический, не круглосуточный.

#### 4.1.3. Показатели назначения

| Показатель | Значение | Источник |
| --- | --- | --- |
| Число одновременных активных сессий | ≤ 3 | FT-004 |
| Idle TTL оперативного состояния | 1800 с | FT-005 |
| p95 создания сессии | ≤ 2 с | NFT-015 |
| p95 ответа на выстрел игрока | ≤ 300 мс | NFT-001 |
| p95 расчёта хода Бэкенда | ≤ 200 мс | NFT-002 |
| Блокировка UI-потока | ≤ 200 мс | NFT-005 |
| Мощность пространства идентификатора сессии | ≥ 2^128 | NFT-017 |
| Готовность Бэкенда к приёму создания сессии после команды запуска | ≤ 60 с | NFT-013 |

#### 4.1.4. Надёжность

Система должна сохранять процесс Бэкенда без аварийного завершения в течение 30 минут непрерывной игры при трёх сессиях и выстрелах не реже одного раза в 2 минуты (NFT-008, NFT-020).

При истечении idle TTL система должна удалить состояние без `GAME_OVER` и без изменения статистики и оповестить Фронтенд (FT-053, FT-066).

При пустой матрице вероятностей и неуничтоженном флоте Игрока система должна передать событие прерывания, затем удалить состояние без выстрела и без статистики (FT-075, FT-076).

Возобновление по идентификатору должно возвращать состояние, эквивалентное сохранённому, пока TTL не истёк (FT-054, NFT-007). Ограничение Фронтенда первой очереди: автовозобновление только того же запуска приложения.

#### 4.1.5. Безопасность

Требования безопасности для жизни и здоровья **не распространяются** на систему в связи с отсутствием воздействия на человека и имущество, отличного от обычной работы ПЭВМ (характеристика Safety в НФТ не применяется).

#### 4.1.6. Эргономика и техническая эстетика

Главный цикл интерфейса не должен блокироваться дольше 200 мс при сетевом обмене и расчёте хода Бэкенда (NFT-005). Анимация длительностью более 200 мс допускается при незамороженном цикле (NFT-018). Подписи стороны соперника на экране — «Компьютер» (EN: Computer).

#### 4.1.7. Транспортабельность

Для стационарного учебного стенда на ПЭВМ требования транспортабельности **не применимы**.

#### 4.1.8. Эксплуатация, ТО, ремонт, хранение

Промышленное ТО **не устанавливается**. Эксплуатация — запуск из состава поставки (контейнеры Бэкенда и хранилища; запуск окна Фронтенда). Хранение состояния партий — в оперативном хранилище с TTL; длительное хранение снимка завершённой партии **не требуется**.

#### 4.1.9. Защита информации от НСД

Идентификация личности и разграничение ролей **не устанавливаются**. Система должна:

- применять выстрел только к сессии открытого канала; отклонять чужой или несуществующий идентификатор без выдачи чужого состояния (NFT-010);  
- отклонять второй одновременный клиент той же сессии (FT-068);  
- выдавать идентификатор из пространства не менее 2^128 различимых значений (NFT-017).

#### 4.1.10. Сохранность информации при авариях

При обрыве соединения слот лимита активных сессий не освобождается, пока состояние хранится и TTL не истёк (FT-074). Сохранность после сбоя носителя и резервное копирование **не устанавливаются**. Журнал статистики изменяется только при `GAME_OVER` совместно с фиксацией исхода; повтор записи не должен давать второго начисления (FT-056).

#### 4.1.11. Защита от внешних воздействий

Климатические и механические воздействия на технические средства **не нормируются** сверх обычных условий ПЭВМ.

#### 4.1.12. Патентная чистота

Специальные требования патентной чистоты в источниках **не установлены**.

#### 4.1.13. Стандартизация и унификация

Прикладной интерфейс должен соответствовать согласованному описанию OpenAPI поставки. Коды исходов выстрела: `MISS`, `HIT`, `SUNK`. Код конца партии: `GAME_OVER`.

#### 4.1.14. Дополнительные требования

Язык сессии на Бэкенде хранить не допускается (A0091). Матрица вероятностей Игроку не передаётся (FT-050).

### 4.2. Требования к функциям

Функциональность первой очереди вводится **полностью** (отдельных очередей внедрения внутри MVP нет).

Система должна обеспечивать:

1. Создание игровой сессии PvE, генерацию двух валидных расстановок, выдачу Игроку только его флота, передачу первого хода Игроку (FT-001, FT-010, FT-014, FT-016).  
2. Ведение не более трёх активных сессий; отказ четвёртой без занятия слота (FT-004, FT-049).  
3. Приём выстрела Игрока по полю Бэкенда только по каналу партии реального времени; фиксацию `MISS`/`HIT`/`SUNK`, буферной зоны при `SUNK`, смены права хода (FT-017…FT-024, FT-055).  
4. Выполнение хода Бэкенда с пересчётом матрицы вероятностей Hunt/Target и выбором клетки (FT-027…FT-034, FT-058, FT-064, FT-079).  
5. Фиксацию `GAME_OVER` при уничтожении флота или сдаче; учёт глобальной статистики; немедленное освобождение слота; удаление оперативного состояния после доставки оповещения (FT-025, FT-056, FT-077, A0128, A0145).  
6. Возобновление состояния по идентификатору при соблюдении TTL и ограничения одного живого соединения (FT-054, FT-067, FT-068).  
7. Выдачу глобальной статистики по запросу (FT-042).  
8. Русский и английский языки интерфейса без пересоздания сессии (FT-059…FT-073).

**Временной регламент:** партия пошаговая. После `MISS` право хода переходит. После `HIT`/`SUNK` стреляющий сохраняет ход, в том числе Бэкенд выполняет серию выстрелов, пока сохраняется его ход. Таймаут хода Игрока **не устанавливается**; ограничение жизни сессии — idle TTL. p95 операций — по NFT-001, NFT-002, NFT-015. Окно генерации расстановки — NFT-015 совместно с FT-010.

**Критерии отказа ключевых функций**

| Функция | Отказ | Поведение |
| --- | --- | --- |
| Создание сессии | три активных слота | отказ, сессия не создаётся |
| Создание сессии | нет валидной расстановки за окно | отказ старта, слот не занят |
| Выстрел | повтор клетки, вне поля, не свой ход, после конца, своё поле, не канал партии, до старта, неверная нагрузка | отклонение без изменения состояния (кроме уже применённого конкурирующего события) |
| Сдача | не канал партии | отклонение без изменения состояния |
| Handshake канала | нет сессии / `GAME_OVER` / живой второй клиент | отказ соединения |
| Ход Бэкенда | пустая heatmap, флот жив | прерывание сессии без статистики |

Полный перечень формулировок — приложение А (файл функциональных требований). Нелегальные выстрелы: сообщение об отказе с p95 ≤ 1000 мс, поле без изменений (NFT-006, NFT-019).

| Вид обеспечения | Требование |

## Приложение А. Перечень функциональных требований

Полная таблица: документ «Функциональные требования» поставки (FT-001…FT-080). Снятые идентификаторы не переиспользовать: FT-035, FT-037, FT-057, FT-078.

Вне первой очереди (не включать в приёмку MVP): PvP, логин, ручная расстановка, рейтинг, персональная статистика.

## Приложение Б. Перечень нефункциональных требований

Полная таблица: документ «Нефункциональные требования» (NFT-001…NFT-020) и правила измерения MR-01…MR-07. Вне MVP: 24/7, интернет-SLA, клиент Linux/macOS, горизонтальное масштабирование сверх трёх сессий.

## Приложение В. Термины и определения

Краткая выборка. Полный канон — глоссарий поставки.

| Термин | Определение |
| --- | --- |
| Игрок | Человек-участник партии |
| Бэкенд | Серверная сторона партии и расчёта хода |
| Фронтенд | Настольное приложение Игрока |
| Игровая сессия | Оперативное состояние одной партии |
| PvE | Режим игрок против Бэкенда |

На экране Фронтенда сторона Бэкенда обозначается «Компьютер».

## Приложение Г. Структура данных

Описание агрегатов и полей — доменная модель и словарь данных поставки. Оперативные ключи хранилища первой очереди: реестр слотов; JSON сессии с истечением; журнал статистики (хеш счётчиков, список записей, множество учтённых идентификаторов сессий).

## Приложение Д. Архитектура системы

Слои Бэкенда: представление, прикладные сценарии, предметная область, инфраструктура хранилища. Фронтенд: интерфейс и сетевой клиент без самостоятельного решения правил боя. Развёртывание: процесс Фронтенда на хосте; контейнеры Бэкенда и хранилища. Детали витрины — архитектурная записка портфолио (не норма приёмки вместо ФТ).

## Приложение Е. Схемы взаимодействия

Контекстная схема — в Vision & Scope §18. Последовательность выстрела и возобновления канала, состояния сессии, C4 — текстовые диаграммы поставки (каталог диаграмм). BPMN жизненного цикла партии — файл BPMN первой очереди обзора процесса.
