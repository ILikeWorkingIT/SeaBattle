# Контроль качества US и UC

Прочитай и выполни `.cursor/skills/skill-quality-control-us-uc.md` целиком. Команда `/qc-us-uc` запускает этот скилл.

Скиллы написания (`skill-us`, `skill-uc`) — только канон формы: не выполняй их алгоритмы и не вызывай `/us` / `/uc` «заодно».

## Ввод

`$1` и дальнейший текст — уточнение: пути к папкам US/UC, ФТ, глоссарию; чьи ответы обработать; куда сохранить отчёт; только US / только UC.

Если текста нет — проверь пакеты, которые **есть** в проекте (`requirements/user-stories/` и/или `requirements/use-cases/`). Отчёт пиши в `reports/incompatibility-us-uc.md`. Отсутствие незаказанного пакета не дефект.

## Какой режим

Смотри на ввод, отдельную подкоманду выбирать не нужно.

- **Отчёт без правок** (шаги 1–2 скилла) — нет ответов по строкам отчёта и нет фраз вроде «внеси», «обработай ответы», «согласен» по пунктам QC. Типично: пустой `/qc-us-uc`, «проверь US/UC», «аудит». Файлы пакета не меняй.
- **Перенос ответов** (шаг 3 скилла) — в чате или в колонке «ответ» отчёта уже есть ответы / «да» / «согласен» / «сделай рекомендацию», либо явно сказано обработать ответы. Внеси правки и `Axxxx`; повторный `/qc-us-uc` по тем же правкам не предлагай.
- **«Исправь» в том же запросе, что и аудит** — сначала отчёт; сразу правь только пункты типа «Исправление» (в источниках уже достаточно данных). Строки-вопросы без ответа не закрывай догадкой.

Если в одном сообщении и «проверь», и ответы — сначала перенеси ответы (шаг 3), новый полный аудит не начинай, пока пользователь его явно не попросил.

## После выполнения

Кратко: путь отчёта, число строк по приоритетам, критичные ID. Не повторяй таблицу.

- Аудит без ответов: файлы US/UC не меняй (если в запросе не сказано «исправь»).
- В запросе есть ответы, согласие на правки или «исправь»: внеси по шагу 3 скилла (или правь пункты с достаточной опорой в источниках). Не предлагай и не запускай повторный `/qc-us-uc` по тем же правкам.
