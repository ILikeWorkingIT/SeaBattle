# Контроль качества DDD-модели

Прочитай и выполни `.cursor/skills/skill-quality-control-ddd.md` целиком. Команда `/qc-ddd` запускает этот скилл.

Скилл написания (`skill-ddd`) — только канон формы: не выполняй его алгоритм написания модели и не вызывай `/ddd` «заодно».

## Ввод

`$1` и дальнейший текст — уточнение: путь к модели, глоссарию, ФТ, US, UC; чьи ответы обработать; куда сохранить отчёт.

Если текста нет — аудируй `requirements/domain-model.md`, отчёт пиши в `reports/domain-model-review.md`.

## Какой режим

Смотри на ввод, отдельную подкоманду выбирать не нужно.

- **Отчёт без правок** — нет согласия на перенос §4 и нет фраз вроде «внеси», «примени §4», «обработай ответы», «согласен» по пунктам аудита. Типично: пустой `/qc-ddd`, «проверь модель», «аудит DDD». Файл `requirements/domain-model.md` не меняй.
- **Перенос §4** — пользователь явно согласился применить скорректированный вариант из отчёта (чат, колонка согласия, «внеси» / «примени §4»). Перенеси в модель только разрешённый набор из скилла; закрытые пары — в `Axxxx` с кодом `DDD`. Повторный `/qc-ddd` по тем же правкам не предлагай.

Если в одном сообщении и «проверь», и согласие на правки — сначала перенеси §4, новый полный аудит не начинай, пока пользователь его явно не попросил.

Заключительный QC после `/ddd` вызывает сам скилл написания модели (режим «после /ddd»): отдельную команду `/qc-ddd` в той же сессии ждать не нужно.

## После выполнения

Кратко: путь отчёта, есть ли критические C-находки, требуется ли согласие на перенос §4 в модель. Не дублируй таблицы отчёта в чат.

- Аудит без согласия: `domain-model.md` не меняй.
- Есть согласие на правки: внеси разрешённый набор §4. Не предлагай и не запускай повторный `/qc-ddd` по тем же правкам.
