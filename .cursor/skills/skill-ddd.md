# Предметно-ориентированная модель (DDD)

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки к названию или домену текущего репозитория.

**Цель:** один файл доменной модели, который после обязательного прохода `skill-quality-control-ddd` в режиме «после /ddd» (в той же сессии, без ожидания команды `/qc-ddd`) можно отдать в разработку как согласованный набор ограниченных контекстов, агрегатов, сущностей, объектов-значений, атрибутов и инвариантов.

**REQUIRED SUB-SKILL:** заключительный этап этого скилла — ровно **один** полный прогон `.cursor/skills/skill-quality-control-ddd.md` в режиме «после /ddd». Без отчёта работу не завершай. После переноса правок `/qc-ddd` **не** запускай второй круг «на всякий случай».

## Когда применять

- Пользователь просит доменную модель, DDD, агрегаты, сущности, VO, карту контекстов.
- Запущена команда `/ddd`.
- Нужно обновить уже существующий `domain-model.md` по новым ФТ/US/UC/`Axxxx`.

Не применяй вместо `/ft`, `/nft`, `/us`, `/uc`, если задача только про требования или сценарии без модели. Не подменяй этот скилл «наброском классов под СУБД».

Не применяй, если пользователь просит **только** аудит уже готовой модели — тогда `/qc-ddd`.

## 1. Источники и границы

1. Читай только текущий репозиторий: ТЗ/спецификация, глоссарий, ФТ/НФТ, US, UC, роли/права, закрытые `Axxxx`, явные указания пользователя. Архивные папки — только по явному `@`.
2. Перед работой, если пользователь просит учитывать накопленное, проверь `reports/agent-memory.md`.
3. Не выдумывай бизнес-правила, роли, статусы, лимиты, интеграции, сущности «для полноты DDD». Факт отдельно от допущения.
4. Термины описаний — из глоссария. Новый устойчивый термин предложи в глоссарий, не вводи молча.
5. Модель — поведение и согласованность, не стек, не СУБД, не API JSON, не UI-фреймворк (если пользователь не просил solution design).
6. Соблюдай MVP / scope. Вне scope — списком в модели, без сущностей «на будущее», пока пользователь явно не попросил.
7. При вопросах заказчику **всегда** давай рекомендацию, с которой можно согласиться.
8. `Axxxx` важнее предварительного ТЗ при конфликте.

## 2. Идентификаторы для разработки

Описания и инварианты — на языке требований проекта (обычно язык глоссария).

Имена **типов и атрибутов** в таблицах — стабильные идентификаторы для кода:

| Что | Правило |
| --- | --- |
| Bounded Context, Aggregate, Entity, VO | PascalCase, **одно или два** слова |
| Атрибут | camelCase, **одно или два** слова |
| Протокольные коды из источников (статусы операций, коды ошибок) | не переименовывать |

Язык идентификаторов:

- **по умолчанию** бери канон глоссария (не выдумывай транслит и не переводи молча);
- английские PascalCase/camelCase на 1–2 слова — только если пользователь явно готовит модель к коду **или** это уже закрыто в `Axxxx` / правилах проекта;
- тогда описания остаются на языке глоссария, в шапке модели — таблица «термин глоссария → идентификатор»;
- не смешивай языки в одном имени типа.

Переименование **уже зафиксированных** в `Axxxx` или явно согласованных имён — таблица «было → стало» в чате и согласие. Точечные правки новых имён допустимы. Полный откат языка идентификаторов после фиксации заказчиком — нет.

При **обновлении** существующей модели: читай текущий `domain-model.md`; не стирай закрытые решения; новые объекты именуй по этому разделу.

Не путай атрибут «чья очередь / текущее состояние процесса» с номером записи в истории событий: разные атрибуты, разные имена.

## 3. Как выделять модель

### 3.1. Ограниченные контексты и ядра

1. Режь контексты по **разному языку** и разным причинам изменения, не по слоям «UI / API / БД».
2. Для каждого BC укажи subdomain: **Core** / **Supporting** / **Generic** и зачем он выделен.
3. Не плоди BC на каждую таблицу. Маленький MVP часто: один Core (основной процесс) + Supporting (учёт, специализированный расчёт) + Generic (локаль, настройки клиента).
4. Карта контекстов: кто у кого что запрашивает; между контекстами — только ID и явно описанные события.
5. Не шарь **типы сущностей** между BC (один и тот же Entity-класс в двух контекстах). На границе — ID и контракт события; при разных языках — явное сопоставление (антикоррупционный слой в прозе), не общий «класс на двоих».
6. Общий VO на два BC — только как явный общий контракт. Иначе у каждого BC свой тип и маппинг.

### 3.2. Агрегаты и корень

1. Агрегат — граница **транзакционной** согласованности. Внутри корня меняются только те сущности, которые по сценариям должны меняться **атомарно вместе**.
2. Корень — **единственная** точка входа: снаружи нельзя менять внутреннюю сущность в обход корня. Коллекция **других** корней внутри агрегата запрещена: только их ID.
3. Не объявляй агрегатом:
   - эфемерный расчёт, который источники **не включают** в хранимое оперативное состояние;
   - снимок для UI;
   - «кластер на всякий случай» с искусственным id «на время вычисления».
4. Такой расчёт — **доменная служба** + VO результата. Служба не пишет чужой журнал учёта и не подменяет корень основного процесса.
5. Инвариант, который **нельзя** честно удержать внутри одного экземпляра основного агрегата (лимит одновременных экземпляров, реестр активных идентификаторов) — отдельный корень **в том же BC**, если язык тот же. Отдельный BC — только если язык и команда реально разные (спроси с рекомендацией).
6. Совместная фиксация **двух** корней — исключение: только если это явно в источниках (например, «исход процесса + запись учёта в одной операции»). Не размножай такие транзакции.
7. Координация двух корней на старте/завершении — именованная служба (`Start…`, не вложенность агрегатов).

### 3.3. Сущность vs объект-значение

**Entity**, если есть идентичность и жизненный цикл: объект отличают не только значения полей; его можно проследить во времени.

**Value Object**, если важны только свойства; нет собственного id и независимого жизненного цикла; равенство по значению; заменяют целиком, не «чинят поле внутри» как у сущности. Типично: деньги, адрес, координата, код, состав-норма, длительность политики, снимок счётчиков.

Агрегат может состоять из корня и одних VO, без вложенных Entity — это нормально. Не плоди Entity «чтобы в таблице что-то было».

Красные флаги «это VO, не Entity»:

- единственный «id» — координата, позиция, номер строки в фиксированной матрице;
- объект не создаётся и не удаляется отдельно от владельца;
- искусственный `…Id` «чтобы был корень» у расчёта без хранения.

Не дублируй один факт в двух хранимых атрибутах (флаг на событии и статус корня). Производное — в тексте «производные», не как второй источник истины.

Код/номер, однозначно выводимый из других полей (например, строковый код из индексов) — **производный** атрибут VO, не отдельное хранимое поле.

### 3.4. Связи

- Внутри агрегата — объектные связи допустимы.
- Между агрегатами — **только идентификаторы**. Запрещена формулировка связи «читает объект другого корня» без поля id.
- Ссылка на внутреннюю сущность чужого агрегата — только её id, и только если это нужно правилу (иначе читай снимок, не держи объект).

### 3.5. Атрибуты

Для каждого атрибута: бизнес-тип (ID, строка, дата/метка, целое, десятичное, логический, enum/статус, длительность, набор ID), обязательность, правила валидации, описание.

Литералы enum — только те, что следуют из источников. Не вводи статус «конца», которого нет в жизненном цикле (сбой/удаление ≠ успешное завершение с тем же enum).

Не моделируй учётную запись пользователя, если в источниках нет идентификации личности.

Каналы, лимиты, срок жизни объекта, идемпотентность — как инварианты корня, если это правила домена, не детали транспорта. Для идемпотентности до контракта API — один канонический монотонный номер; второй id только как синоним того же факта, не второй счётчик (лучше не хранить второй).

### 3.6. Инварианты

Секция инвариантов каждого агрегата/службы должна закрывать **проверяемые** правила из ФТ и основных потоков US/UC, относящиеся к этому кластеру. Не копируй все ФТ слепо: разнеси по BC.

Обязательно проверь, что не потеряны:

- создание и отказ создания;
- легальные/нелегальные команды изменения состояния;
- смена статуса и исход;
- что **не** двигает политику жизни объекта (idle-таймер, кэш, «просмотр»);
- независимость экземпляров, если она в ФТ;
- скрытие информации (что нельзя отдавать другой стороне);
- конкурирующие команды к одному корню (порядок, «первая принятая», идемпотентность);
- создание: невалидный агрегат **не существует** (отказ без «полусозданного» состояния), если так в источниках;
- два представления одного факта (например состав и размещение) не расходятся;
- события оповещения — списком доменных событий у агрегата/службы, не отдельными агрегатами, если это только доставка.

Состояние UI (блокировка кнопки, анимация) не клади в Core. Срок жизни / секрет доступа — домен, если так в ФТ.

Инварианты создания проверяет корень или явно названная фабрика/служба.

Помечай допущения модели отдельным разделом. Открытый вопрос — с рекомендацией.

## 4. Формат `domain-model.md`

Шапка: статус, дата, назначение, источники (включая `Axxxx` по именам модели).

Краткое соглашение об именах (как в §2).

Карта BC (таблица + по желанию mermaid). Список доменных служб. Вне MVP.

Для **каждого** ограниченного контекста:

## [Имя контекста]

Краткое назначение (язык глоссария в прозе, идентификатор BC в заголовке).

### Агрегат: [Имя корня]

*Смысл и граница согласованности.*

Если в контексте нет агрегата (только служба) — заголовок `### Служба: [Имя]`, таблица сущностей: «Нет».

#### 1. Сущности (Entities)

Таблица:

| Сущность | Атрибут | Тип данных (Бизнес) | Обязательность | Правила / Валидация | Описание |
| :--- | :--- | :--- | :--- | :--- | :--- |

#### 2. Объекты-Значения (Value Objects)

Таблица:

| Объект-Значение | Атрибут | Тип данных (Бизнес) | Правила / Валидация | Описание |
| :--- | :--- | :--- | :--- | :--- |

#### 3. Бизнес-инварианты и правила

Маркированный список. Ссылки на ID требований / `Axxxx`.

#### 4. Связи

Таблица: От | К | Кратность | Как связывается (внутри агрегата / только ID).

По желанию у агрегата — короткий список **доменных событий** (имя, когда вспыхивает, кто заинтересован). Не отдельный BC «уведомления», если это только доставка.

В конце файла: сводка ID между агрегатами; допущения; открытые вопросы (или «Нет»).

## 5. Порядок работы

1. Собрать источники (§1). Зафиксировать формулировку задачи и явные вводные; недостающее — вопросы с рекомендацией, не догадки.
2. Набросать BC и ядра. Если граница BC спорна — **не жди ответа в чате, чтобы продолжить:** зафиксируй вопрос и рекомендацию в модели, строй черновик **по рекомендации**. Не закрывай спор молча как факт.
3. Для каждого BC: корни, сущности, VO, атрибуты, инварианты, связи.
4. Записать `requirements/domain-model.md` (черновик).
5. **Заключительный этап — обязателен, без паузы на согласие пользователя:**
   - немедленно прочитай и **целиком выполни** `.cursor/skills/skill-quality-control-ddd.md` в режиме «после /ddd» (**один** проход);
   - не объявляй `/ddd` завершённым, пока нет отчёта и пока в модель не внесены правки, которые скилл `/qc-ddd` разрешает переносить в этом режиме;
   - после переноса **не** запускай `/qc-ddd` повторно в той же сессии;
   - запрещённые отговорки: «модель короткая», «QC сделаем потом», «пользователь не вызывал /qc-ddd», «нарушений на глаз нет», «сначала ответьте на вопросы границ — QC откладываю».

В чат после полного прогона: путь модели, путь отчёта, какие BC/агрегаты, какие вопросы ждут ответа. Не дублируй все таблицы.

## Типичные ошибки

| Ошибка | Как правильно |
| --- | --- |
| Агрегат = таблица БД | Агрегат = транзакция по сценариям |
| Корень на каждый расчёт | Служба + VO |
| Entity без id и жизненного цикла | VO |
| Связь агрегатов «читает объект» | Поле id |
| Enum исхода, которого нет в ФТ | Только литералы из жизненного цикла |
| Инварианты «правила процесса» без отказов и границ | Закрыть ФТ/UC по чек-листу §3.6 |
| Закончить после записи модели | Обязательно выполнить `skill-quality-control-ddd` в режиме «после /ddd» (не ждать slash `/qc-ddd`) |
| Ждать ответы на границы BC, откладывая QC | Вопрос в модели + черновик по рекомендации + один проход `/qc-ddd` |
| НФТ-latency в инвариантах | В домен только бизнес-ограничения |
| Другие корни списком объектов в агрегате | Только ID |
