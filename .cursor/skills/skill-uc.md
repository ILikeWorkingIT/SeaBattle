# Написание Use Cases (Cockburn)

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки скилла к названию или домену текущего репозитория.

## Когда применять

- Пользователь просит Use Cases, сценарии использования по Cockburn, реестр UC или обработку ответов по вопросам UC.
- Запущена команда `/uc`.
- Нужна **проверка качества** уже написанного пакета UC — полный прогон по `.cursor/skills/skill-quality-control-us-uc.md` (команда `/qc-us-uc`). Чек-лист §10 — для самопроверки при написании; не подменяет `/qc-us-uc`.

Не применяй вместо `/ft`, `/nft` или `/us`, если задача только про таблицы ФТ/НФТ или User Stories без сценариев UC.

---

## Результат (формат файлов)

По умолчанию (если пользователь не указал иной путь) — папка `requirements/use-cases/`:

| Артефакт | Файл | Содержание |
| --- | --- | --- |
| Один сценарий | `uc-NNN-<kebab-name>.md` | Заголовок, метаданные, секции Cockburn (§4) |
| Реестр UC и вопросы | `list-uc.md` | Список UC, статусы, связи, вне scope, **единый** список вопросов |

Статус новых артефактов: `Черновик, требует согласования`, пока заказчик явно не согласует.

### Именование и ID

- Файл: префикс `uc-` + **трёхзначный** номер + kebab-название (пример: `uc-001-login.md`).
- ID в заголовке и реестре: **`UC-001`**, `UC-002`, … — тот же трёхзначный номер, что в имени файла.
- Нумерация с последнего существующего ID; если папки нет — с `UC-001`.
- Если в правилах репозитория задан иной формат — следуй правилам репозитория (не ломай naming conventions проекта ради промпта «UC-01», если в правилах трёхзначный ID).

### База закрытых ответов

Если в проекте есть `requirements/answers-project.md` (и правило переноса ответов) — закрытые пары вопрос→ответ пиши только туда (код `UC`; при влиянии на ФТ/НФТ/US — `FT` / `NFT` / `US` по теме). Не копируй закрытые Q&A в тела UC как хранилище ответов. Если файла базы нет — держи открытые вопросы в `list-uc.md` и спроси, куда складывать закрытые.

## 1. Источники и границы

1. Читай только источники **текущего** репозитория: ТЗ/спецификация, глоссарий, ФТ/НФТ, US, роли/права, закрытые `Axxxx`, явные указания пользователя. Не читай архивные папки без явного `@`.
2. Не выдумывай бизнес-правила, роли, лимиты, каналы, статусы и интеграции. Отделяй факт от предположения.
3. Термины — из глоссария проекта; новый устойчивый термин предложи в глоссарий, не вводи молча.
4. Формулируй поведение, не реализацию (без стека, СУБД, паттернов), если пользователь не просит solution design.
5. Соблюдай MVP / scope. Вне scope и post-MVP — **списком в реестре** (§5), без полных UC-файлов, пока пользователь явно не попросил иное.
6. В `.md` **запрещён** fence ` ```text ` и пустой ` ``` ` для длинных цитат (горизонтальная прокрутка в MarkText). Обычный markdown; fence только с осмысленным языком (`mermaid` и т.п.).

### 1.1. Таксономия атрибуции источников

В поле **Источники** каждого UC указывай происхождение сценария и ключевых правил. Метки можно комбинировать через `;`.

| Метка | Когда ставить |
| --- | --- |
| `ТЗ` / бриф / спецификация | Сценарий или правило прямо из предварительного ТЗ / брифа / спеки |
| `встреча` / протокол / транскрипт | Зафиксировано на встрече |
| `глоссарий` | Роль или термин из глоссария |
| `US-NNN` | UC выровнен с конкретной User Story |
| `Axxxx` | Закрытый ответ из `answers-project.md` |
| `память проекта` / decision log | Явно сохранённое решение в памяти / логе решений |
| `сгенерировано агентом` | Агент сам додумал поток, альтернативу, исключение или правило без прямой опоры во вводе |

Правила:

1. Альтернативы и исключения «для полноты Cockburn» без опоры во вводе помечай `сгенерировано агентом` (в источниках UC и/или у конкретного шага в вопросах реестра).
2. Не ставь `ТЗ` / `встреча`, если шаг — интерпретация агента.
3. В реестре пакета перечисли входные артефакты; в каждом UC — конкретные метки по сценарию.
4. После согласия заказчика / записи в `answers-project.md` замени или дополни метку на `Axxxx`; голое «решение заказчика» без `Axxxx` не используй.

## 2. Декомпозиция и связи

### 2.1. Как выделять UC

1. По умолчанию — **1:1 к согласованным User Stories**, если пакет US есть и заказчик не задал иную декомпозицию.
2. Иначе — по **целям пользователя** (user goal) / системным целям; не плодить UC на каждый технический шаг.
3. Общий исход «завершение / фиксация результата», вызываемый из нескольких сценариев, оформляй отдельным UC уровня extension/subfunction с **include** из вызывающих UC (не дублируй полный основной поток).
4. Системный участник может быть **primary** (ход системы, фоновый процесс), если ценность для пользователя описана; заинтересованный пользователь — interested / supporting.

### 2.2. Акторы: дисциплина одного основного актора

1. Бери роли **только** из источников (глоссарий, ТЗ, матрица прав, `Axxxx`). Типы: primary, supporting, interested. Не выдумывай персон «для полноты».
2. У каждого UC — **один основной актор (primary)**.
3. Вспомогательные (supporting) и заинтересованные (interested) допустимы, но **не подменяют** основного в предусловии, триггере и шагах **основного** потока.
4. В предусловии, триггере, основном/альтернативных потоках и постусловии называй **того же** основного актора, что в разделе «Акторы» (для системного primary — ту же системную роль из источников).
5. Не приписывай роли чужие цели: если актор A инициирует сценарий, не пиши шаги «как от лица B» без основания в источниках.
6. Роль в потоке меняется только если это **суть** сценария (например, регистрация: гость → зарегистрированная роль). Иначе держи одного primary до конца UC.
7. Другие роли, если реально участвуют, — во вспомогательных / interested или в **отдельных** UC; не перечисляй «также роль X, роль Y» у primary без нужды.

### 2.3. Запрет суррогата «Пользователь» / «User»

1. **Не** вводи и **не** пиши в UC обобщённые «Пользователь», «User», «юзер», если такой роли **нет** в глоссарии / матрице прав / ТЗ проекта.
2. Используй конкретное имя роли из источников.
3. Если в источниках роль названа иначе — следуй канону проекта; при неоднозначности спроси (с рекомендацией), не подставляй «Пользователь» как заглушку.

## 4. Структура файла одного Use Case

**Порядок секций строго** (как в §3):

1. `# UC-NNN: <Краткое название>`
2. Метаданные: **Статус артефакта**; **Уровень**; **Связанные US**; **Связанные ФТ** (и НФТ при необходимости); **Источники** (§1.1); при необходимости **связанные сценарии** (include/extension).
3. `## 1. Акторы`
4. `## 2. Предусловие`
5. `## 3. Триггер`
6. `## 4. Основной поток` — **5–8 шагов**. Если длиннее — краткое обоснование в файле.
7. `## 5. Альтернативные потоки` — **ровно шесть категорий** (§4.1).
8. `## 6. Потоки исключений` — минимум **2**; у каждого — возврат или завершение.
9. `## 7. Постусловие`
10. `## Вопросы` — только ссылка на `list-uc.md` и ID (или «закрыты: Axxxx»). Полный текст — в реестре (§5).

### 4.1. Шесть категорий альтернатив

1. Некорректные данные  
2. Timeout / недоступность  
3. Прерывание  
4. Недостаточно прав  
5. Конкурентный доступ  
6. Граничные значения  

Правила:

- Ветки размечай **`[Шаг N.x]`**.
- У каждой ветки явно: **возврат** в основной поток (с указанием шага) **или завершение**.
- Если категория **реально не применима** — **«Не применимо»** + обоснование из источников / `Axxxx`. Не выдумывай правила ради заполнения.
- Лимиты: различай **допустимое состояние** («не более N») и **условие успешного создания ещё одного** («сейчас меньше N»).

### 4.2. Исключения vs альтернативы

- Альтернативы — ожидаемые отклонения бизнес-потока.
- Исключения — сбои, аварийные ветки, нарушение инвариантов; ≥2; возврат или завершение.

## 5. Реестр `list-uc.md`

Обязательные блоки:

1. Метаданные пакета (дата, статус черновика/согласования, ссылки на источники и роли).
2. Таблица реестра: ID | название | файл | связанные US (если есть) | статус **`готово`** | **`требует уточнения`**. Допустима колонка **основной актор**.
3. Кратко: связи сценариев (таблица или mermaid); покрытие акторов.
4. **Вне MVP / вне scope** — **списком** (название / краткое обоснование / источник), **без** полных `uc-*.md`, пока пользователь не попросил оформить отдельными UC.
5. **Открытые вопросы пакета** — единый полный список (§6). В телах `uc-*.md` не дублировать.
6. **Закрытые вопросы** — сводка ID вопроса → `Axxxx`.
7. Рекомендуемый следующий шаг.

Статус UC:

- **готово** — сценарий выведен из источников; открытые вопросы не блокируют основной поток.
- **требует уточнения** — есть открытый вопрос или противоречие, без которого нельзя однозначно принять постусловие / исключения.

## 6. Вопросы и рекомендации

### 6.1. Где хранить

- Все открытые вопросы — **только** в `list-uc.md`.
- Колонки: `ID` | `UC` | `Вопрос` | `Рекомендация` | `Ответ`.
- ID: `UC-NNN-C#` (заказчик), `UC-NNN-D#` (разработка).
- В `uc-NNN-*.md` — ссылка на реестр и перечень ID.

### 6.2. Рекомендация обязательна

При каждом вопросе по проекту предложи **рекомендацию для ответа**. Не оставляй вопрос без рекомендуемого решения. Рекомендацию не выдавай за принятый факт, пока нет согласия / `Axxxx`.

### 6.3. Обработка ответов

1. Читай ответы из чата и из колонки «Ответ» в `list-uc.md`.
2. Закрытые пары → `answers-project.md` (код `UC`): дословно содержательный ответ; при «да» / «согласен» / «сделай рекомендацию» — текст рекомендации.
3. Обнови затронутые `uc-*.md` и реестр; статусы UC.
4. Ответ не на тот пункт — обработай по смыслу и явно напиши интерпретацию.
5. «Позднее / при разработке API» — закрытое решение об отложении (`Axxxx`).

## 7. Алгоритм работы

Task Progress:

- [ ] 1. Собрать вводные и зафиксировать границы (scope in/out)
- [ ] 2. Выделить акторов строго из источников (§2.2–2.3)
- [ ] 3. Составить backlog UC с ID `UC-001`…
- [ ] 4. Написать отдельные файлы UC по шаблону (§3–§4)
- [ ] 5. Реестр `list-uc.md` + статусы + вне scope + вопросы с рекомендациями
- [ ] 6. Проверить по чек-листу §10; краткий ответ пользователю (§7.1)
- [ ] 7. После создания или существенного обновления пакета **предложить** `/qc-us-uc` (не запускать без согласия)

Шаги подробно:

1. Прочитай глоссарий, ТЗ, ФТ/НФТ, US (если есть), роли, `answers-project.md`, текущие UC, при необходимости `reports/agent-memory.md`.
2. Согласуй scope: зеркало US / цели / подмножество Must — если неоднозначно и меняет объём, спроси (с рекомендацией). Зафиксируй вне scope списком для реестра.
3. Создай или обнови файлы UC и реестр.
4. Вынеси все вопросы в `list-uc.md` с рекомендациями.
5. Ответь пользователю по образцу §7.1. Не дублируй полные тексты всех UC в чат.
6. После **создания** или **существенного** обновления пакета **предложи** разработчику полный контроль качества командой `/qc-us-uc` (не запускай без согласия). См. `.cursor/rules/rule-propose-qc-us-uc.mdc`.
7. После ответов — §6.3. При необходимости предложи `/ft`, `/nft`, `/us` (не запускай без запроса).

- Дописывать недостающий контекст догадками.

- Подменять основного актора в предусловии, триггере или основном потоке другой ролью без основания в источниках.

- Выдавать сгенерированные агентом ветки за `ТЗ` / `встречу` без метки `сгенерировано агентом`.
- Дублировать полные списки вопросов в каждом `uc-*.md` и в реестре.
- Писать закрытые ответы только в чат, не перенося в `answers-project.md`, если база есть.
- Использовать fence ` ```text `.
- Подменять UC таблицами ФТ или User Stories без сценариев потоков.
- Плодить полные UC-файлы на пункты вне scope без явной просьбы.

## 10. Чек-лист качества пакета UC

Перед финальным ответом проверь:

| # | Критерий |
| --- | --- |
| 1 | У каждого UC один **основной** актор из источников; нет суррогата «Пользователь» / «User» вне глоссария |
| 2 | Нет подмены актора: в предусловии, триггере и основном потоке — тот же primary, что в разделе «Акторы» |
| 3 | Есть акторы, предусловие, триггер, основной поток 5–8 шагов (или обоснование), постусловие |
| 4 | Есть все 6 категорий альтернатив; ветки `[Шаг N.x]`; возврат или завершение; N/A с обоснованием |
| 5 | ≥2 потока исключений с возвратом или завершением |
| 6 | В «Источники» есть атрибуция (§1.1); додуманные ветки — `сгенерировано агентом` |
| 7 | Термины согласованы с глоссарием; нет выдуманных правил |
| 8 | Связи include/extension не дублируют целые сценарии без нужды |
| 9 | Лимиты/инварианты сформулированы однозначно |
| 10 | Вне scope / post-MVP — списком в реестре (если есть) |
| 11 | Все открытые вопросы только в `list-uc.md`, у каждого есть рекомендация |
| 12 | Статусы в реестре соответствуют наличию блокирующих вопросов |
| 13 | Нет fence ` ```text `; именование `UC-NNN` / `uc-NNN-*.md` (или канон репозитория) |
| 14 | Закрытые ответы отражены в `answers-project.md` и в текстах затронутых UC |

Итог проверки качества кратко занеси в `list-uc.md` (дата, ok / замечания), если выполнялась проверка пакета. Полный прогон пакета US+UC — скилл `skill-quality-control-us-uc` / команда `/qc-us-uc` (отчёт по умолчанию в `reports/incompatibility-us-uc.md`).
