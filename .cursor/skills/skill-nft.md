# Написание нефункциональных требований

Универсальный скилл системного аналитика. Не подставляй факты, термины, SLA и правила другого проекта.

Модель качества продукта — ISO/IEC 25010:2023.

## Когда не применять

- Полный аудит уже написанных НФТ/ФТ («проверь НФТ», контроль качества, `/qc-ft-nft`) — **не** этот скилл. Следуй `skill-quality-control-ft-nft`. Не пиши новые НФТ «заодно» с аудитом.
- Не исполняй этот скилл «как алгоритм написания», если его открыли только как образец формы из QC.

## Результат

Единый файл НФТ (если пользователь не указал иной путь — `requirements/non-functional-requirements.md`) со статусом `Черновик, требует согласования`, пока заказчик явно не согласует документ.

Таблица:

| Колонка | Правило |
| --- | --- |
| NFT-ID | `NFT-XXX`, трёхзначный номер. Продолжай с последнего существующего ID; если файла нет — с `NFT-001`. Префикс `NFT` (по аналогии с `FT`), не `NFR`. |
| Характеристика | Имя из модели ISO/IEC 25010:2023 (русское имя из справочника ниже). |
| НФТ | SMART: субъект, действие, объект, порог, условие измерения. Канон: «[Субъект] должен [глагол] [объект] так, чтобы [измеримый порог]». |
| Метрика | Измеримая величина: имя, единица, агрегация (p95, доля, счётчик), объём выборки. Без числа, единицы или способа сбора — это не метрика. |
| Условие | Стенд, нагрузка, границы замера (что входит / не входит), ссылка на правило измерения при необходимости. В начале условия — статус порога/методики: **`факт`** (из ТЗ / ФТ / `Axxxx`), **`уточнить`** (блокер, порога или методики нет), **`сгенерировано агентом`** (черновой порог/методика без прямого ввода). Можно комбинировать с меткой источника через `;`. |
| Источник | ТЗ / ФТ и/или ID закрытого ответа `Axxxx` из `requirements/answers-project.md`. Не писать «решение заказчика» без `Axxxx`. Предложение агента без основания во вводе — в «Условии»/`Источнике` метка **`сгенерировано агентом`**. |

После таблицы — отдельные разделы:

1. **Границы модели** — какие характеристики включены и почему остальные нет.
2. **Правила измерения** — факты из источников отдельно от допущений. ID правил в файле НФТ — формат `MR-NN` (Measurement Rule): продолжай с последнего существующего ID; если правил ещё нет — с `MR-01`. Верхней границы «только до MR-07» нет. **Не путать** с ID базы ответов `A0001+`.
3. **Вне MVP / вне scope** — что сознательно не нормировалось.
4. **Вопросы заказчику** — только **открытые** пробелы. Формат таблицы:

| ID | Вопрос | На какие NFT влияет | Рекомендация |
| --- | --- | --- | --- |
| Q1 | … | NFT-00x, NFT-00y | … |

Закрытые Q&A сюда не копировать — только в `answers-project.md`.

Не веди в файле НФТ раздел «Решения заказчика» как хранилище ответов — канон закрытых ответов: `requirements/answers-project.md`.

## Справочник характеристик ISO/IEC 25010:2023

В модели продукта **9** характеристик. В таблицу НФТ по умолчанию входят **7** (качество, а не поведение функций):

| EN | Русское имя | В НФТ по умолчанию |
| --- | --- | --- |
| Performance efficiency | Эффективность производительности | да |
| Compatibility | Совместимость | да |
| Interaction capability | Способность к взаимодействию | да |
| Reliability | Надёжность | да |
| Security | Защищённость | да |
| Maintainability | Сопровождаемость | да |
| Flexibility | Гибкость | да |
| Functional suitability | Функциональная пригодность | нет: закрывается ФТ |
| Safety | Безопасность (вред жизни, здоровью, имуществу, среде) | нет, пока в источниках нет такого вреда |

Ориентир — **2 НФТ на каждую включённую** характеристику, **если источники это позволяют**. Это не потолок: больше двух — если нормы различны и проверяемы. Иной набор — только если заказчик явно просит или Safety/Functional suitability применимы; тогда задай вопрос и дай рекомендацию. Не выдумывай вторую норму (и не копируй ФТ без метрики) только ради квоты «ровно 2»: недостающую закрой вопросом с рекомендацией и при необходимости одной строкой со статусом `уточнить` / `сгенерировано агентом`.

## Алгоритм

1. Прочитай глоссарий, ТЗ/спецификацию, ФТ, текущий файл НФТ, `requirements/answers-project.md` (закрытые решения `Axxxx`) и структуру проекта. Не читай архивные папки без явного `@`.
2. Фиксируй только явные вводные. Не выдумывай роли, интеграции, лимиты, каналы, стек, стенд и SLA.
3. Формулируй качество, не реализацию: без стека, фреймворков, СУБД и UI-решений, если пользователь не просит уровень solution design. Имена протоколов в НФТ — только если уже есть закрытое решение `Axxxx` или явный контракт MVP в источниках.
4. Держи термины глоссария. Новый устойчивый термин предложи в глоссарий, не вводи молча.
5. Одно НФТ — одна проверяемая норма. Не дублируй ФТ: поведение «что делает система» — в ФТ; «насколько / при каких ограничениях» — в НФТ.
6. Если в источниках нет числа — не выдавай его за факт. Поставь измеримый черновой порог в таблицу с пометкой **`сгенерировано агентом`** в «Условии» **и** тот же порог в вопрос как рекомендацию. Если методики нет — статус **`уточнить`**, без выдуманного числа.
7. Неизмеримые слова («быстро», «удобно», «надёжно», «масштабируемо») без метрики не оставляй: спроси критерий и предложи рекомендацию.
8. Уже закрытые пороги и решения бери из `Axxxx` — они важнее предварительного ТЗ при конфликте; в «Условии» ставь **`факт`**.
9. При противоречии источников или двух `Axxxx` — зафиксируй явно и спроси; **не** усредняй пороги молча.
10. Ответ заказчику: кратко резюме, путь файла, диапазон ID, какие вопросы ждут ответа. Не дублируй всю таблицу в чат.
11. После создания или существенной правки НФТ **предложи** проверку качества командой `/qc-ft-nft` (не запускай без согласия). См. `.cursor/rules/rule-propose-qc-ft-nft.mdc`. **Исключение:** не предлагай и не запускай повторный `/qc-ft-nft`, если текущие правки — перенос уже согласованных находок только что завершённого QC (шаг 3 `skill-quality-control-ft-nft`).

## Согласование

- Пока нет явного «согласовано» по документу — статус черновика.
- Рекомендацию помечай как рекомендацию, не как факт. Черновой порог для характеристики, которая уже должна быть в наборе по алгоритму, — в основную таблицу с меткой `сгенерировано агентом` / `уточнить`. Совершенно новые ID сверх этого, пока заказчик сказал только «предложи» — в блоке «ждут подтверждения», не в основную таблицу.
- Ответы читай из чата **и** из раздела вопросов в файле НФТ.
- «Согласен» / «да» по рекомендации — перенеси в основную таблицу и в правила измерения; в глоссарий — если это термин; в «Источник» поставь новый `Axxxx`; в «Условии» замени `сгенерировано агентом` / `уточнить` на **`факт`**.
- После ответа пользователя (чат или файл) **обязательно** перенеси закрытые пары вопрос→ответ в `requirements/answers-project.md` по `.cursor/rules/rule-answers-project.mdc` (код `NFT`; содержательный ответ или текст рекомендации при «согласен»). Открытые вопросы оставь в файле НФТ; закрытый блок вопросов из НФТ удали.
- Ответ не на тот пункт — обработай по смыслу и явно напиши, как интерпретировал.
- Запреты и решения («запрещен», «максимум N», «только <среда измерения>») — сразу в таблицу; источник — `Axxxx` после записи в базу ответов.
- Когда заказчик согласует черновик целиком — смени статус на `Согласовано` и дату. Дальнейшие уточнения — только по новому запросу.

## Запрещено

- Дописывать недостающий контекст догадками и выдавать их за требования из ТЗ.
- Закрывать отсутствие SLA/порога «типичными» значениями (99,9 %, «как у всех») без источника и без метки `сгенерировано агентом`.
- Выдавать генерацию агента за `факт` / ТЗ / `Axxxx`.
- Усреднять или молча «сглаживать» противоречивые пороги из разных источников.
- Смешивать ФТ и НФТ в одной таблице без нужды.
- Расширять scope без запроса — даже «типичное для качества» (целевой процент доступности, SLA внешней сети, дополнительные платформы).
- Копировать стек из ТЗ в формулировку НФТ.
- Считать рекомендацию действующим требованием до согласия.
- Оставлять метрику без способа измерения или без условия (и без статуса факт / уточнить / сгенерировано агентом).
- Писать закрытые ответы только в НФТ, минуя `answers-project.md`.
- Путать `Axxxx` (база ответов) с `MR-NN` (правила измерения в файле НФТ).
- Удалять или переименовывать согласованный файл без разрешения.

## Пример канона

Система должна выполнить <операцию> так, чтобы p95 времени <границы замера> не превышала <N> <единица>.

Плохо: «Интерфейс должен быть отзывчивым».  
Хорошо: «Главный цикл интерфейса не блокируется дольше <N> мс во время <операции>» + метрика (макс. длительность блокировки, мс; число блокировок выше порога = 0) + условие (`факт` / `сгенерировано агентом`; сценарий, длительность прогона).
