# Моделирование бизнес-процессов в BPMN (bpmn.io)

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки скилла к названию или домену текущего репозитория.

## Когда применять

- Пользователь просит BPMN-диаграмму, схему процесса для `bpmn.io`, файл `.bpmn`, дорожки / пулы / шлюзы / события.
- Запущена команда `/diagram-bpmn`.
- Нужно исправить уже существующую BPMN по замечаниям после импорта в `bpmn.io`.
- Нужно ревью синтаксиса BPMN, раскладки, стрелок или трассировки к источнику без смены бизнес-смысла.

Не применяй вместо `/ft`, `/nft`, `/us`, `/uc`, если задача только про требования или сценарии без диаграммы процесса.

## Результат (формат файлов)

По умолчанию (если пользователь не указал иной путь) — папка `diagrams/`:

| Артефакт | Файл | Содержание |
| --- | --- | --- |
| Диаграмма BPMN 2.0 | `bpmn-NNN.bpmn` | XML, импортируемый в [bpmn.io](https://demo.bpmn.io/) |
| Опционально | краткий разбор в чате | Участники, старт, задачи, шлюзы, финалы, линейное описание, пять блоков проверок |

Статус новых диаграмм: черновик для согласования и визуальной правки, пока пользователь явно не утвердил.

### Именование и ID

- Файл: префикс `bpmn-` + **трёхзначный** номер (пример: `bpmn-001.bpmn`).
- **Новый процесс** (сохранение в файл): взять следующий свободный номер после последнего `bpmn-NNN` в целевой папке — не перезаписывать чужие диаграммы. Если папки нет — создай и начни с `bpmn-001`.
- **Пересоздание / правка диаграммы того же процесса**: оставить прежний номер файла и обновить содержимое на месте.
- Имя процесса (`name` у `bpmn:process`) — краткое название процесса на языке проекта.
- Если в правилах репозитория задан иной путь или naming — следуй правилам репозитория.
- Если пользователь сказал «папка diagram», а в проекте канон `diagrams/` — сохрани в каноническую папку и кратко сообщи фактический путь.

### Формат вывода

Целевой формат — **BPMN 2.0 XML** для импорта в `bpmn.io` (расширение `.bpmn`).

Минимум в файле:

- `bpmn:definitions` с пространствами имён `bpmn`, `bpmndi`, `dc`, `di`;
- один или несколько `bpmn:process` / `bpmn:collaboration` по выбранной модели пулов;
- полный `bpmndi:BPMNDiagram` с координатами, иначе импорт может открыться «пустым» или неудобным для правки;
- для аналитической модели по умолчанию `isExecutable="false"` на process (если пользователь не просил исполняемую модель).

После записи файла проверь, что XML парсится (хотя бы как well-formed XML). Не заявляй «готово к импорту», если парсинг упал.

В чате **не** дублируй весь XML: путь к файлу + краткий разбор.

В `.md`-артефактах проекта **запрещён** fence ` ```text ` и пустой ` ``` ` для длинных цитат. Для BPMN-фрагментов в чате допустим fence с языком `xml`, если пользователь явно просит кусок XML.

## Прогресс задачи

Копируй и отмечай по ходу:

- [ ] 1. Прочитать источники; отделить факты от допущений
- [ ] 2. Разобрать процесс по чек-листу аналитика (§2)
- [ ] 3. Спроектировать элементы BPMN (типы задач / потоков / шлюзов / событий)
- [ ] 4. Собрать `.bpmn` (process или collaboration + lanes + DI)
- [ ] 5. Пройти пять блоков проверок (§6): дорожки, потоки, синтаксис, читаемость стрелок, соответствие процессу
- [ ] 6. Отдать файл + краткий разбор; строка «Проверено: …»

Диаграмму **не считай готовой**, пока не пройдены все пять блоков §6.  
Исключение для первой сдачи черновика под совместную правку в `bpmn.io`: блоки **дорожки / типы потоков / синтаксис / соответствие процессу** — обязательны без пробелов; **читаемость стрелок и раскладка** — must try, оставшиеся пробелы явно перечисли в ответе как долг визуальной правки (не как «сломано»).

## 1. Источники и границы

1. Читай только источники **текущего** репозитория и явные вложения пользователя (`@файл`, текст в чате). Не читай архивные папки без явного `@`.
2. Не выдумывай шаги, роли, ветки и исходы, которых нет во вводе. Отделяй факт от предположения.
3. Термины — из глоссария / требований / US / UC проекта; новый устойчивый термин предложи зафиксировать, не вводи молча.
4. Моделируй **бизнес-поведение процесса**, не стек и не UI-детали, если пользователь не просит solution design.
5. Соблюдай scope источника: одна диаграмма = один согласованный срез процесса (один US/UC/раздел ТЗ или явно названный процесс). Не смешивай несколько независимых процессов в один файл без запроса.
6. Если ввода мало для старта, веток или финалов — сначала задай уточняющие вопросы с **рекомендацией** ответа; не заполняй пробелы догадками «для красоты диаграммы».
7. При конфликте «красивая раскладка» vs «верность источнику» — **верность источнику**, затем правка раскладки.

---

## 2. Обязательный аналитический проход (до или вместе с XML)

Всегда выполни и кратко зафиксируй в ответе (или в комментарии к правке):

1. **Участники → дорожки (lanes)**  
   Кто реально действует или наблюдает результат. Не плодить дорожки «для полноты».
2. **Стартовое событие**  
   Что запускает процесс (условие состояния, запрос, сообщение, таймер — по факту источника). Имя = триггер понятным языком.
3. **Задачи с типом**  
   Список задач и BPMN-тип каждой (`User` / `Service` / `Send` / `Receive` / `Manual` / `Business Rule` / обычная `Task`, если тип неясен).
4. **Ветвления и тип шлюза**  
   Вопрос шлюза + тип (`Exclusive XOR` / `Parallel AND` / `Inclusive OR` / `Event-based` — только если обосновано источником).  
   **Не** выноси в отдельный шлюз то, что в источнике — фильтр/правило **внутри** шага без видимой развилки для актора (отрази в имени задачи или примечании).
5. **Все финишные события**  
   Каждый осмысленный исход процесса — отдельный end (или явно согласованный merge + один end). Тип End — по смыслу (§3.2).
6. **Линейное описание потока**  
   Формат: `участник → задача → шлюз → …` для основного и альтернативных путей.
7. **Пять блоков проверок (§6)**  
   Исправить нарушения в XML до передачи пользователю (с оговоркой готовности из блока «Прогресс задачи»).

Если пользователь просит «только XML» — всё равно пройди шаги 1–7 внутри, а в чат отдай сжатый итог + путь к файлу.

## 3. Правила моделирования

### 3.1. Пулы и дорожки

- **По умолчанию:** один **пул** (process) и **дорожки** по участникам. Между дорожками одного пула — только **sequence flow**.
- **Отдельные пулы** — когда нужна явная граница организаций/систем и обмен сообщениями. Тогда между пулами — только **message flow**, внутри пула — sequence flow.
- Не смешивай: не рисуй sequence flow между разными пулами и не подменяй message flow линией sequence внутри одного пула.
- Дорожка наблюдателя без задач допустима **только если** участник явно есть в источнике и нужен для чтения диаграммы. Лишние пустые дорожки не добавляй.
- Каждый узел лежит в lane своего участника (`flowNodeRef` согласован с семантикой и DI).

### 3.2. События

- Имена — краткие, по смыслу триггера или исхода (глагол/факт: «Получен запрос», «Заявка отклонена»).
- Старт: `None` / `Message` / `Timer` / `Conditional` — по природе запуска из источника; не ставь Message Start «на всякий случай». Обычно один Start.
- Финалы: каждый бизнес-исход именуй явно. Не прячь разные исходы в один безымянный End без пояснения.
- Тип End выбирай по смыслу исхода:
  - `None` — обычное завершение ветки;
  - `Message` — завершение с исходящим сообщением, если это следует из источника;
  - `Error` — только если источник описывает именно ошибку / сбой исполнения, а не бизнес-ветку «иначе»;
  - `Terminate` — принудительное прекращение всего экземпляра, только если это явно нужно по источнику.
- Бизнес-условие (ветка «если … иначе …») моделируй **шлюзом**, а не Error/Escalation Event, пока источник не описывает именно техническую ошибку исполнения.

### 3.3. Задачи

- Имя задачи — **глагол + объект** («Проверить заявку», «Отправить уведомление»).
- Деловой язык из источников. Не оставляй внутренние коды (`E1`, `5.2`) **единственной** подписью — пиши смысл; код в скобках допустим для трассировки.
- Не называй задачу вопросом; вопрос — у шлюза.
- Типы:
  - `User Task` — действие человека в системе;
  - `Service Task` — автоматическая обработка системой;
  - `Send Task` — отправка сообщения / оповещения;
  - `Receive Task` — ожидание / получение сообщения;
  - `Manual Task` — ручная работа вне системы (редко; только если явно);
  - `Business Rule Task` — применение правил/скоринга, если это отдельный шаг в источнике.
- **Согласование типа с дорожкой:** человек ≠ `Service Task` в lane системы без основания; система ≠ `User Task` в lane роли без основания.
- Не дроби один атомарный шаг источника на технический микроконвейер без запроса.
- Не оставляй у задачи **два и более исходящих sequence flow без шлюза**: ветвление — только через gateway.

### 3.4. Шлюзы и типы исходящих потоков

- `Exclusive (XOR)` — взаимоисключающие ветки (по умолчанию для «да/нет», enum-результатов).
- `Parallel (AND)` — только если источник требует **одновременного** параллельного выполнения и последующего join.
- `Inclusive (OR)` — только если могут одновременно выполняться несколько (не все) веток.
- `Event-based` — выбор по тому, какое событие придёт первым.
- После сходящихся веток используй merge-gateway **или** веди каждую ветку в свой End — не оставляй «висящие» слияния без модели.

**Подписи исходящих (XOR/OR):**

| Вариант | Правило |
| --- | --- |
| Conditional Flow | Каждая исходящая с **именованным условием** из источника |
| Default Flow | Допустима **одна** ветка default (happy path / «иначе»), остальные — с условиями |
| Запрещено | Две и более безымянные конкурирующие ветки с разным смыслом |

Подписи однозначны (`Да` / `Нет`, коды исходов, имена веток из источника).

**Шлюз «повторить?» / цикл:** ветки «Да» / «Нет» явно ведут к шагу повтора или к концу; подпись потока говорит **куда** («Да — снова …», «Нет — конец …»), а не только «Да»/«Нет» без контекста, если иначе неоднозначно.

### 3.5. Типы потоков (выбирать явно)

| Тип | Когда использовать | Не путать с |
| --- | --- | --- |
| Sequence Flow | Порядок шагов **внутри** одного процесса (в т.ч. между lanes одного pool) | Message Flow |
| Message Flow | Обмен **между** разными pool (есть в источнике) | Sequence Flow через границу pool |
| Default Flow | Исход XOR «по умолчанию» | Условный исход с подписью-условием |
| Conditional Flow | Исход шлюза с условием из источника | Безымянная ветка |

### 3.6. Сообщения и оповещения

- В **одном пуле с дорожками:** Send → Receive связаны **sequence flow** (логика процесса), не message flow.
- В **разных пулах:** Send/Receive (или message events) + **message flow** между пулами.
- Не дублируй один и тот же обмен и sequence, и message «на всякий случай».

### 3.7. Раскладка и читаемость стрелок

#### Дорожки и фигуры

- Дорожки **сопоставимой высоты**, без огромных пустых полос.
- Фигуры **крупные относительно дорожки**; soft-ориентир задач ~160–200 × 80–100 px (не жёсткий закон: важнее читаемость текста внутри).
- Подписи узлов **не вылезают** за край дорожки/пула; длинные имена — перенос в имени.
- Happy path — одна горизонталь; альтернативы — ряд ниже с зазором.

#### Стрелки

- Межlane: по возможности **общая ось X** (короткая вертикаль).
- Стрелка **не проходит сквозь** задачи, шлюзы, события.
- Рёбра **не сливаются** в общий ствол с двумя разными подписями.
- Ветки шлюза стартуют **от ромба**, с разных сторон / столбцов.
- Ретраи: коридор между объектами или край пула; **не** вдоль Start так, будто старт ведёт в чужую дорожку. Тесно — **сдвинь фигуры**, не уводи стрелку через весь холст.
- От Start — только к первому шагу своей дорожки (без ложных вторых линий).

#### Подписи потоков

- Выше горизонтали; единый визуальный зазор на диаграмме.
- Не на линии и не на фигуре; не пересекают другие подписи.
- Короткая стрелка → удлини ребро или сократи текст.
- Имя шлюза — над ромбом, с запасом; не путай с подписями «Да/Нет».
- Одна подпись = один исход; не объединяй два разных исхода в одну надпись.

### 3.8. Итерации после импорта в bpmn.io

1. Первая версия — валидный импортируемый черновик с пройденными обязательными блоками §6, не «идеальная картинка».
2. Правки пользователя (скрин, список замечаний, выгрузка XML) — вноси в **тот же** `bpmn-NNN.bpmn`, если не попросили новый номер.
3. После правки снова: well-formed XML + затронутые блоки §6.
4. Не переписывай всю диаграмму ради одной стрелки, если достаточно точечного изменения.

## 4. Порядок работы агента

1. Прочитай источник процесса (US / UC / ТЗ / описание в чате).
2. Выполни аналитический проход §2.
3. Выбери модель: один пул + lanes **или** collaboration с несколькими пулами (по умолчанию — один пул).
4. Собери BPMN XML + DI-координаты; имена на языке проекта; `isExecutable="false"` для аналитики.
5. Запиши `diagrams/bpmn-NNN.bpmn` (или путь пользователя).
6. Проверь парсинг XML и пять блоков §6.
7. В чате: путь файла, сжатый разбор §2, строка «Проверено: …», открытые вопросы / вне модели, долг раскладки если есть.

При запросе «исправить диаграмму» начинай с текущего `.bpmn` и замечаний пользователя, не с нуля.

## 6. Пять обязательных блоков проверок (перед сдачей)

Пройди **все** пункты. В ответе кратко отметь:

**Проверено:** дорожки / типы потоков / синтаксис / читаемость стрелок / соответствие процессу  
(+ 1–3 замечания или долг визуальной правки, если были).

### 6.1. Дорожки

- [ ] Каждый участник из источника, который действует на диаграмме, имеет lane (или явно вынесен во внешний pool)
- [ ] Нет лишней дорожки без шагов (кроме осознанного наблюдателя по §3.1)
- [ ] Каждый узел в lane своего актора; тип задачи согласован с актором (§3.3)
- [ ] Высоты дорожек сопоставимы; фигуры не «тонут» в пустоте
- [ ] Подписи не вылезают за границы lane/pool
- [ ] `laneSet` / `flowNodeRef` согласованы с раскладкой DI

### 6.2. Типы потоков

- [ ] Внутри процесса — Sequence Flow; Message Flow — только между pool и только по источнику
- [ ] У XOR: все исходящие с именованным условием **или** одна default + остальные с условиями
- [ ] Нет безымянных конкурирующих веток с разным смыслом
- [ ] Нет Sequence Flow, имитирующего «сообщение снаружи»
- [ ] Тип каждого ребра соответствует смыслу (порядок шагов vs сообщение)

### 6.3. Синтаксис BPMN

- [ ] Число Start = задуманному; каждый путь заканчивается End
- [ ] Нет orphan узлов и висячих sequenceFlow; `incoming` / `outgoing` согласованы
- [ ] Нет нескольких исходящих sequence flow из задачи/события без шлюза (кроме осознанных допустимых случаев BPMN с пояснением)
- [ ] Шлюзы: тип (XOR/AND/OR/Event) соответствует источнику; default указан, если выбран этот вариант
- [ ] Типы задач (User/Service/Send/Receive/…) согласованы с актором
- [ ] Типы End (None/Message/Error/Terminate) осмысленны; бизнес-ветки не подменены Error без основания
- [ ] Нет задач-вопросов; вопросы только на gateway
- [ ] Send/Receive и message flow согласованы с моделью пулов (§3.6)
- [ ] XML well-formed; в DI есть bounds/waypoints для отображаемых элементов
- [ ] Фигуры DI не перекрывают друг друга критично

### 6.4. Читаемость стрелок

- [ ] Ветки шлюза визуально различимы (не общий ствол на две подписи)
- [ ] Каждая ветка начинается от шлюза, не «рядом»
- [ ] Стрелки не режут фигуры
- [ ] Межlane-связи короткие/по оси, без ложного чтения «из Start в чужую дорожку»
- [ ] Подписи однозначно привязаны к своей стрелке; не на линии и не на объекте
- [ ] Длина ребра достаточна для текста подписи
- [ ] Ретраи/обходы не маскируют основной поток
- [ ] Ориентир размеров задач соблюдён по возможности (~160–200 × 80–100)

### 6.5. Соответствие процессу (трассировка)

- [ ] Триггер источника = Start (по смыслу)
- [ ] Основной поток источника покрыт happy path (каждый обязательный шаг — задачей или осознанно свёрнут с пометкой)
- [ ] Альтернативы / исключения из источника отражены ветками **или** явно отложены в «открытых вопросах» / «вне модели»
- [ ] Нет веток и задач, которых нет в источнике (кроме технических стыковок вроде «к другому процессу», если это следует из текста)
- [ ] Участники диаграммы = акторы/системы из источника
- [ ] Постусловия / исходы источника соответствуют End-событиям
- [ ] Имена узлов и подписей потоков узнаваемы по тексту процесса (смысл, не только код)
- [ ] Расхождения и упрощения перечислены в ответе (не скрыты)

## 9. Антипаттерны

| Не делать | Делать |
| --- | --- |
| Крошечные задачи на огромных дорожках | Сопоставимые lane, крупные читаемые задачи |
| Общий ствол двух веток шлюза | Разные стороны / столбцы, своя подпись |
| Подпись на фигуре или на линии | Свободное место, единый отступ |
| Message Flow вместо Sequence внутри process | Sequence между lanes; Message между pool |
| Ветка без следа в источнике | Только по тексту процесса или «открытый вопрос» |
| Коды `E1` без расшифровки | Понятное имя (+ код в скобках) |
| Ретрай «как будто из Start» | Коридор между объектами или сдвиг фигур |
| Шлюз из внутреннего фильтра шага | Правило в имени задачи; шлюз — только видимая развилка |
| User Task в lane системы / Service в lane человека без основания | Тип задачи согласован с актором дорожки |
| Сдача без §6 | Пять блоков проверок обязательны (с оговоркой готовности) |
