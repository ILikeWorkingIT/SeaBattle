# Vision & Scope (концепция и границы проекта)

Универсальный скилл технического писателя (роль `tech-writer`, команда `/vision`). Не подставляй факты, термины, лимиты и интеграции другого проекта.

## Когда применять

- Создать или обновить документ Vision & Scope.
- Команда `/vision`.
- Запрос вроде «концепция и границы», «Vision and Scope», «vision-scope».

## Когда не применять

- Детальные ФТ / НФТ / US / UC / DDD — соответствующие точечные скиллы (`/ft`, `/nft`, `/us`, `/uc`, `/ddd`).
- Полный QC уже написанных ФТ/НФТ или US/UC — `/qc-ft-nft`, `/qc-us-uc`.
- Не раздувай Vision & Scope до копии таблиц требований.

## Режимы по зрелости источников

Отдельной подкоманды нет. Выбери режим по наличию артефактов:

| Режим | Когда | Опора | Ограничения |
| --- | --- | --- | --- |
| **Ранний Vision** | Нет согласованных ФТ/НФТ/US/UC или пакеты пусты | Предварительное ТЗ, глоссарий (если есть), чат, `project-config` | В §10 не выдумывай ID `FT-xxx` / `US-xxx`. Ссылайся на разделы ТЗ или помечай `сгенерировано агентом`. Коллизии лимитов — вопрос + рекомендация, не «канон по ФТ» |
| **Vision после пакета** | Есть согласованные или черновые таблицы требований | `Axxxx` → пакеты → ТЗ | Ссылки на ID требований обязательны там, где факт уже в пакете. Коллизии лимитов — канон по ФТ/`Axxxx`/UC |

Смешанный случай (часть пакетов есть): для закрытых тем — как «после пакета»; для остальных — как «ранний».

## Результат

Единый файл (если пользователь не указал иной путь — `artifacts/vision-scope.md`) со статусом:

- `Черновик, требует согласования` — пока заказчик явно не согласует Vision;
- `Согласовано` — после явной фразы **«согласую Vision»** / **«принимаю Vision & Scope»** (или эквивалент без слова «утверждаю»).

**Не путать** с утверждением этапа MAS («утверждаю» / «принимаю этап» → `Stage: … APPROVED` в `pm-state.md`). Согласование Vision **не** ставит APPROVED этапа и не требует, чтобы ФТ/НФТ/US уже были согласованы.

Vision согласуется **сам по себе**. В шапке можно (не обязательно) указать ссылки на уже согласованные пакеты требований — это контекст, не предусловие статуса Vision.

Документ **не заменяет** ФТ/НФТ при приёмке функций. При конфликте с детальными требованиями приоритет у закрытых ответов `Axxxx` и согласованных пакетов в `requirements/`.

В `.md` файлах проекта **не** использовать обёртку ` ```text ` … ` ``` ` (см. `rule-structure.mdc`).

После создания или существенной правки файла при необходимости обнови упоминание `vision-scope.md` в `.cursor/rules/rule-structure.mdc` и `documentation/project-structure-v1-1.md`, если шаблон ещё не описан.

## Источники (только факты проекта)

Читай в порядке приоритета (не выдумывай):

1. `requirements/answers-project.md` (`Axxxx`) — при конфликте важнее предварительного ТЗ.
2. Пакеты требований: ФТ, НФТ, глоссарий, US, UC, доменная модель, словарь данных (если есть; согласованные важнее черновиков).
3. Предварительное ТЗ / спецификация в `documentation/`.
4. `reports/project-config.md`, чеклист срезов (если есть) — для среды и границ поставки, без подмены бизнес-правил.

В режиме **ранний Vision** пункты 1–2 могут быть пустыми: опирайся на п.3–4 и вопросы. Не читай архивные папки без явного `@`. Не переноси чужой репозиторий.

## Обязательная структура документа

Включи **все** разделы ниже. Пустой раздел не оставляй: либо факты из источников, либо явная пометка «не зафиксировано в источниках» + вопрос с рекомендацией (вопрос дублируй в §21, пока открыт).

| № | Раздел | Содержание |
| --- | --- | --- |
| 1 | Назначение документа | Зачем Vision & Scope; что не дублирует (таблицы ФТ/НФТ) |
| 2 | Связанные документы | Пути к ТЗ, requirements, config |
| 3 | Краткое резюме | 1 абзац: продукт, ценность, границы MVP |
| 4 | Предыстория | Как появилась инициатива; что уточнилось относительно предварительного ТЗ (если ТЗ нет — так и напиши) |
| 5 | Проблема и бизнес-возможность | Проблема стейкхолдера; возможность без solution-design |
| 6 | Цели проекта | **Обязательно два уровня** — см. § «Бизнес-цели vs цели продукта» |
| 7 | Критерии успеха | Проверяемые критерии MVP; без неизмеримых «удобно» |
| 8 | Потребности пользователей | **Обязательно профиль** + таблица потребностей — см. § «Профиль пользователя» |
| 9 | Видение решения | Vision Statement (для / продукт / который / в отличие от / наш продукт) |
| 10 | Ключевые возможности | Группы major features; ссылки на ID требований **если они есть**, иначе — на ТЗ / «сгенерировано агентом». Без копипасты описаний ФТ |
| 11 | Область проекта | MVP in-scope; post-MVP; явно out of scope |
| 12 | Ограничения | Таблица ограничений + **критерии исключения** — см. § «Критерии исключения» |
| 13 | Допущения | AS-NN; не смешивать с требованиями |
| 14 | Зависимости | Внешние системы, платформа, пакет требований |
| 15 | Риски | Риск → влияние → митигация в scope MVP |
| 16 | Стейкхолдеры | Роли; отсылка к профилю §8 |
| 17 | Приоритеты проекта | MoSCoW / порядок при конфликте ресурсов |
| 18 | Среда эксплуатации | ОС, runtime, интеграции; при необходимости контекстная диаграмма Mermaid |
| 19 | Связь с артефактами требований | Карта Vision → ФТ/НФТ/US/UC/… (пустые ячейки, если пакетов ещё нет) |
| 20 | История изменений | Версия, дата, кратко что изменилось |
| 21 | Вопросы по Vision, которых нет в документации | Только **открытые** вопросы с рекомендацией. Закрытые Q&A сюда не копировать: они живут в `answers-project.md` |

Метаданные в шапке: продукт, версия документа, дата, статус, аудитория; опционально — ссылки на согласованные пакеты.

## Бизнес-цели vs цели продукта (раздел 6)

**Запрещено** выдавать только продуктовые/технические цели («скрыть внутреннюю обработку», «показать процент выполнения», «выбрать стек») как единственный уровень раздела 6.

### 6.1. Бизнес-цели (Business Goals)

Верхнеуровневая выгода для стейкхолдера / организации. Минимум **одна** цель (лучше 1–3). Каждая:

- формулирует **ценность** (деньги, время, риск, конфиденциальность, compliance, доля рынка и т.п.);
- по возможности **измерима** и с горизонтом (срок / метрика);
- опирается на источники или помечена `сгенерировано агентом` + вопрос на подтверждение в §21.

Примеры **абстрактных** шаблонов (подставь факты проекта, не копируй чужие цифры):

- Снизить затраты на X до Y к сроку Z.
- Обеспечить N% соответствие правилу конфиденциальности / локальности данных.
- Сократить время цикла процесса P на M%.

### 6.2. Цели продукта (Product Goals)

Что делает система, чтобы реализовать бизнес-цели. У каждой продуктовой цели — колонка связи с BG-id.

Если в источниках только продуктовые формулировки — выведи BG как рекомендацию (в §6.1 с пометкой + вопрос в §21), не маскируй под факт.

## Профиль пользователя (раздел 8)

Не ограничивайся фразой «есть роль Пользователь».

Обязательная таблица профиля (атрибуты по фактам; отсутствующее — вопрос в §21):

| Атрибут | Что выяснить / зафиксировать |
| --- | --- |
| Роль | Канон глоссария; одна или несколько ролей |
| Контекст | Личные / корпоративные нужды; заказчик = разработчик или нет |
| Ожидания от UI продукта | No-code (кнопки/формы) vs требуется консоль / CLI для основного сценария |
| Инфраструктура вне продукта | Что пользователь **обязан** уметь сам вне UI: установка и запуск внешних runtime-зависимостей, учётные записи смежных систем, VPN, админка и т.п. (конкретный список — только из источников проекта) |
| Ожидания от сообщений об ошибках | Сообщения в UI vs «разберётся по логам» |
| Вне компетенции | Что сознательно не целевой навык |

Если из допущений следует, что пользователь сам настраивает внешние зависимости runtime — это **обязательно** в профиле, не только в списке AS.

Далее — таблица потребностей → как закрывает продукт (ссылки на US/FT, если есть; иначе — на разделы ТЗ).

## Критерии исключения для ограничений (раздел 12)

Таблица ограничений **недостаточна**, если не сказано, что происходит при нарушении.

Для каждого существенного лимита (объём данных, квоты, таймауты, платформа, форматы) добавь подраздел **12.1 Критерии исключения**:

| Ограничение | Условие нарушения | Поведение системы | Источник |
| --- | --- | --- | --- |

Правила:

1. Поведение берётся из ФТ / `Axxxx` / UC, если они есть. Не выдумывай «молча обрезать» или «упасть», если в источниках иное.
2. Различай **вместимость поля / импорт** и **лимит на действие** (например вызов внешней системы): если источники разделяют — зафиксируй явно.
3. При двух конкурирующих моделях реализации (например «полный импорт + отказ при запуске» vs «превентивная обрезка при парсинге»):
   - **есть ФТ / `Axxxx` / UC** — выбери канон по ним, назови обе модели, пометь канон и вне-scope;
   - **нет ФТ** — **не** объявляй канон: опиши обе модели, дай рекомендацию и вопрос в §21; в таблице поведения пометь `сгенерировано агентом` / «ждёт подтверждения».
4. «Приложение не падает и не зависает» указывай, только если это следует из надёжности в источниках или согласовано; иначе не обещай.
5. Не подменяй критерий исключения блокировкой кнопки, если в ФТ проверка в момент действия (и наоборот). Если ФТ ещё нет — не выбирай механизм UI молча; спроси или оставь на уровне «отказ при действии» vs «превентивный запрет» без виджетов.

## Алгоритм

1. Определи режим (ранний / после пакета / смешанный). Прочитай доступные источники. Зафиксируй формулировку задачи и явные вводные; отметь неопределённости.
2. Не выдумывай бизнес-правила, роли, интеграции, лимиты, стек. Solution design (конкретный UI-фреймворк, СУБД) — только если уже канон в источниках / `project-config` / `Axxxx`.
3. Собери раздел 6: сначала BG, затем продуктовые цели со связью.
4. Собери профиль пользователя и потребности (§8).
5. Собери scope in / post-MVP / out; не расширяй MVP «для полноты».
6. Собери ограничения + критерии исключения. Коллизии «импорт vs лимит действия»: при наличии ФТ — канон по ФТ; без ФТ — рекомендация + вопрос в §21 (см. п.3 критериев исключения).
7. Заполни остальные разделы 1–20; для среды — краткая контекстная диаграмма Mermaid при наличии внешних систем.
8. Собери §21: только открытые вопросы, у каждого — рекомендация.
9. В истории изменений — новая версия при существенных правках.
10. Пройди **самопроверку** (ниже). При провале — исправь документ до отчёта в чат.
11. В чат: краткое резюме (путь, статус, режим, что уточнено, открытые вопросы). Не дублируй весь документ.
12. После ответа заказчика: перенеси закрытые пары в `requirements/answers-project.md` с кодом **`VS`** по `rule-answers-project.mdc` (содержательный ответ или текст рекомендации при «согласен»). В Vision замени отсылки на `Axxxx`. **Закрытые** вопросы из §21 (и вкрапления в других разделах) **удали**; открытые оставь. Не жди отдельной команды «перенеси», если ответы уже даны.

## Самопроверка перед «готово»

Все пункты должны быть «да». Иначе документ не считай завершённым.

| # | Проверка |
| --- | --- |
| 1 | Есть ≥ 1 бизнес-цель (BG); продуктовые цели не выданы за единственный уровень §6 |
| 2 | Профиль пользователя заполнен (таблица §8); инфраструктура вне UI отражена, если следует из допущений |
| 3 | У каждого заявленного существенного лимита в §12 есть строка критерия исключения в §12.1 |
| 4 | Нет двусмысленного канона лимитов без ФТ/`Axxxx` (либо канон со ссылкой, либо вопрос в §21) |
| 5 | Документ не является дампом таблиц ФТ/НФТ |
| 6 | §21 содержит только открытые вопросы; у каждого есть рекомендация |
| 7 | В режиме «ранний» нет выдуманных ID FT/US; в режиме «после пакета» ссылки на существующие ID там, где факт из пакета |
| 8 | Статус черновика, пока нет явного «согласую Vision» / «принимаю Vision & Scope»; фраза «утверждаю» этапа не использована для статуса Vision |

## Согласование и правки

- Пока нет явного «согласую Vision» / «принимаю Vision & Scope» — статус черновика.
- Уточнение решения: не правь «на месте» закрытый `Axxxx`; новый ID в секции текущего дня (правило базы ответов).
- При противоречии двух `Axxxx` — остановись и спроси; не усредняй молча.
- Минорные правки структуры Vision (BG, профиль, критерии исключения) после ревью — повысь версию документа в шапке и в истории.
- Ответ не на тот пункт — обработай по смыслу и явно напиши, как интерпретировал.

## Запрещено

- Копировать детали чужого или предыдущего проекта как факты текущего.
- Подменять бизнес-цели списком фич.
- Оставлять лимиты без поведения при нарушении, если лимит заявлен.
- Игнорировать квалификацию пользователя вне UI, если она следует из допущений.
- Писать Vision как полный дамп ФТ/НФТ.
- Объявлять канон поведения при коллизии лимитов без ФТ/`Axxxx`/UC.
- Использовать согласование Vision как утверждение этапа MAS.
- Использовать ` ```text ` в `.md` артефакте.
- Писать в базу ответов код отличный от **`VS`** для вопросов именно по Vision (если вопрос по сути про ФТ — код `FT`, и правь ФТ, не только Vision).

## После выполнения

Кратко сообщи:

- путь к файлу;
- версию и статус;
- режим (ранний / после пакета / смешанный);
- сколько BG / продуктовых целей;
- были ли разрешены коллизии ограничений (канон со ссылкой или вопрос);
- сколько открытых вопросов в §21;
- результат самопроверки (пройдена / что осталось).

Не запускай QC ФТ/НФТ «заодно», если Vision не менял таблицы требований. Если попутно вскрылись пробелы в ФТ — предложи `/ft` или `/qc-ft-nft`, не запускай без согласия.
