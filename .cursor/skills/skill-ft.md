# Написание функциональных требований

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта.

## Результат

Единый файл требований (если пользователь не указал иной путь — `requirements/functional-requirements.md`) со статусом `Черновик, требует согласования`, пока заказчик явно не согласует документ.

Таблица:

| Колонка | Правило |
| --- | --- |
| ID | `FT-XXX`, трёхзначный номер. Продолжай с последнего существующего ID; если файла нет — с `FT-001`. |
| Название | Глагол + существительное. |
| Описание | Канон: «[Субъект] должен [глагол] [объект] [при условии]». |
| Источник | ТЗ / глоссарий и/или ID закрытого ответа `Axxxx` из `requirements/answers-project.md`. Не писать «решение заказчика» без `Axxxx`. |
| Приоритет | MoSCoW: Must / Should / Could / Won't. |

После таблицы — отдельные разделы:

1. **Вне MVP / вне scope** — что сознательно не включалось.
2. **Граничные случаи, не покрытые требованиями** — ситуации, которых нет в источниках, поэтому отдельных ФТ нет (после закрытия — в списке закрытых случаев со ссылкой на FT).
3. **Вопросы по ФТ, которых нет в документации** — только **открытые** вопросы с рекомендацией. Закрытые Q&A сюда не копировать: они живут только в `answers-project.md`.

Не веди в файле ФТ раздел «Решения заказчика» как хранилище ответов — канон закрытых ответов: `requirements/answers-project.md`.

## Алгоритм

1. Прочитай глоссарий, ТЗ/спецификацию, текущий файл ФТ, `requirements/answers-project.md` (закрытые решения `Axxxx`) и структуру проекта. Не читай архивные папки без явного `@`.
2. Фиксируй только явные вводные. Не выдумывай роли, правила, интеграции, статусы, сроки жизни объектов, лимиты, каналы и UI.
3. Формулируй поведение, не реализацию: без стека, фреймворков, СУБД, паттернов и UI-решений, если пользователь не просит уровень solution design.
4. Держи термины глоссария. Новый устойчивый термин предложи в глоссарий, не вводи молча.
5. Одно ФТ — одно проверяемое поведение. Название — действие.
6. Must — без этого основной сценарий невозможен. Should — заявлено в целях/контракте, но сценарий без этого возможен. Could — слабое следствие источников. Won't — вне scope, в таблицу не тащи.
7. Неизмеримые слова («быстро», «удобно», «надёжно») не оставляй в ФТ: спроси критерий.
8. Канон из источников (в т.ч. «классические правила» предметной области) можно включить как Must, но пометь источник и спроси подтверждение, если фразы в ТЗ нет. Уже закрытые уточнения бери из `Axxxx` — они важнее предварительного ТЗ при конфликте.
9. Ответ заказчику: кратко резюме, затем таблица в файле; не дублируй всю таблицу в чат.
10. После создания или существенной правки ФТ предложи разработчику проверку качества командой `/qc-ft-nft` (не запускай без согласия).

## Согласование

- Пока нет явного «согласовано» — статус черновика.
- Если заказчик пишет «предложи рекомендацию» — дай рекомендацию отдельно, **не** добавляй её в основную таблицу как ФТ.
- Рекомендацию помечай как рекомендацию, не как факт. Предлагаемые ID держи в блоке «ждут подтверждения».
- Ответы читай из чата **и** из раздела вопросов в файле ФТ.
- «Согласен» / «да» по рекомендации — перенеси в основную таблицу и в глоссарий, если это термин; в «Источник» поставь новый `Axxxx`.
- После ответа пользователя (чат или файл) **обязательно** перенеси закрытые пары вопрос→ответ в `requirements/answers-project.md` по `.cursor/rules/rule-answers-project.mdc` (код `FT`; содержательный ответ или текст рекомендации при «согласен»). Открытые вопросы оставь в файле ФТ; закрытый блок вопросов из ФТ удали.
- Ответ не на тот пункт — обработай по смыслу и явно напиши, как интерпретировал.
- Запреты и решения («запрещен», «максимум N») — сразу в таблицу; источник — `Axxxx` после записи в базу ответов.
- Когда заказчик согласует черновик целиком — смени статус на `Согласовано` и дату. Дальнейшие правки — только по новому запросу.

## Запрещено

- Дописывать недостающий контекст догадками.
- Смешивать ФТ и НФТ в одной таблице без нужды; тип уточняй, если неясно. Префикс ID нефункциональных требований — `NFT` (не `NFR`).
- Расширять scope без запроса — даже «типичное для домена».
- Копировать стек из ТЗ в формулировку ФТ.
- Считать рекомендацию действующим требованием до согласия.
- Писать закрытые ответы только в ФТ, минуя `answers-project.md`.
- Путать `Axxxx` (база ответов) с ID правил измерения НФТ (`MR-01`…`MR-07`).
- Удалять или переименовывать согласованный файл без разрешения.

## Пример канона

```text
Система должна создать объект <X>, когда <актор> выполняет <действие>.
```

Плохо: «Использовать <СУБД> и <протокол из ТЗ> для хранения <объекта>».  
Хорошо: «Система должна хранить оперативное состояние <X>, пока <условие>».
