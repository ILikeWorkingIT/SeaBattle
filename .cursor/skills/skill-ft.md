# Написание функциональных требований

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта.

## Результат

Единый файл требований (если пользователь не указал иной путь — `requirements/functional-requirements.md`) со статусом `Черновик, требует согласования`, пока заказчик явно не согласует документ.

Таблица:

| Колонка | Правило |
| --- | --- |
| ID | `FT-XXX`, трёхзначный номер. Продолжай с последнего существующего ID; если файла нет — с `FT-001`. |
| Название | Глагол + существительное. |
| Описание | Канон: «[Субъект] должен [глагол] [объект] [при условии]». |
| Источник | Ссылка на документ проекта (ТЗ, глоссарий, решение заказчика). |
| Приоритет | MoSCoW: Must / Should / Could / Won't. |

После таблицы — отдельные разделы:

1. **Вне MVP / вне scope** — что сознательно не включалось.
2. **Граничные случаи, не покрытые требованиями** — ситуации, которых нет в источниках, поэтому отдельных ФТ нет.
3. **Вопросы по ФТ, которых нет в документации** — только то, без чего нельзя закрыть пробел. Не превращай вопрос в требование.

## Алгоритм

1. Прочитай глоссарий, ТЗ/спецификацию, текущий файл ФТ и структуру проекта (путь и имя файла). Не читай архивные папки без явного `@`.
2. Фиксируй только явные вводные. Не выдумывай роли, правила, интеграции, статусы, TTL, лимиты, каналы и UI.
3. Формулируй поведение, не реализацию: без стека, фреймворков, СУБД, паттернов и UI-решений, если пользователь не просит уровень solution design.
4. Держи термины глоссария. Новый устойчивый термин предложи в глоссарий, не вводи молча.
5. Одно ФТ — одно проверяемое поведение. Название — действие.
6. Must — без этого основной сценарий невозможен. Should — заявлено в целях/контракте, но сценарий без этого возможен. Could — слабое следствие источников. Won't — вне scope, в таблицу не тащи.
7. Неизмеримые слова («быстро», «удобно», «надёжно») не оставляй в ФТ: спроси критерий.
8. Канон из источников (в т.ч. «классические правила» предметной области) можно включить как Must, но пометь источник и спроси подтверждение, если фразы в ТЗ нет.
9. Ответ заказчику: кратко резюме, затем таблица в файле; не дублируй всю таблицу в чат.

## Согласование

- Пока нет явного «согласовано» — статус черновика.
- Если заказчик пишет «предложи рекомендацию» — дай рекомендацию отдельно, **не** добавляй её в основную таблицу как ФТ.
- Рекомендацию помечай как рекомендацию, не как факт. Предлагаемые ID держи в блоке «ждут подтверждения».
- «Согласен» / «да» по рекомендации — перенеси в основную таблицу и в глоссарий, если это термин.
- Ответ не на тот пункт (текст про другое) — обработай по смыслу и явно напиши, как интерпретировал.
- Запреты и решения заказчика («запрещен», «максимум N») — сразу в таблицу, источник: решение заказчика.
- Когда заказчик согласует черновик целиком — смени статус на `Согласовано` и дату. Дальнейшие правки — только по новому запросу.

## Запрещено

- Дописывать недостающий контекст догадками.
- Смешивать ФТ и НФТ в одной таблице без нужды; тип уточняй, если неясно.
- Расширять scope (PvP, логин, рейтинги и т.п.) без запроса — даже «типичное для домена».
- Копировать стек из ТЗ в формулировку ФТ.
- Считать рекомендацию действующим требованием до согласия.
- Удалять или переименовывать согласованный файл без разрешения.

## Пример канона

```text
Система должна создать объект <X>, когда <актор> выполняет <действие>.
```

Плохо: «Использовать Redis и REST для хранения сессии».  
Хорошо: «Система должна хранить оперативное состояние <X>, пока <условие>».
