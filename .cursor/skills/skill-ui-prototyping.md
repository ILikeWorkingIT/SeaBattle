# Визуальный макет окна фронтенда (навигация без доменной логики)

Универсальный скилл. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки скилла к названию или домену текущего репозитория. Экраны, подписи, данные и стек бери **только** из артефактов текущего репозитория и явных указаний пользователя.

Роль при выполнении: Senior Frontend Developer и UX/UI-инженер.

## Цель макета

Макет показывает **внешний вид** приложения и дополнительных окон/экранов. Это **визуальный прототип с навигацией** (clickable shell), а не играющий / работающий по правилам домена клиент.

**Разрешено (должно работать):**

- пункты меню и кнопки, которые открывают другие экраны, панели или модальные окна;
- переключение вкладок;
- смена языка и настроек UI, если они в scope;
- переход между экранами одного главного окна (например лобби → рабочий экран).

**Запрещено (не реализовывать):**

- доменная / игровая логика: ходы, ответы второй стороны, проверка правил, таймеры партии, генерация состояния по правилам, «можно сыграть партию»;
- реакция рабочих поверхностей (ячейки поля, строки таблиц как действие домена и т.п.) на клик — клик **не меняет** снимок данных;
- живой mock-сервер с правилами из US/UC; анимации «ожидание ответа системы», пульс последнего хода и т.п.

Кнопки доменных действий (старт, выстрел, сдача и т.п.) **оставляй видимыми**, если они есть в US/UC. Клик по ним либо только открывает окно/меняет экран навигации, либо **ничего не меняет** на рабочих данных экрана — без симуляции правил.

---

## Когда применять

- Пользователь просит макет / прототип окна, ключевой экран, визуальный UI по требованиям.
- Запущена команда `/ui-prototyping`.
- Нужно поправить уже собранный макет (контраст, навигация, окна) или напомнить, как открыть окно.
- Пользователь просит **упростить / пересобрать** существующий клиент под этот скилл (убрать доменную логику) — режим **создание** или явная пересборка: привести `src/` к визуальному макету.

Не применяй вместо `/ft`, `/nft`, `/us`, `/uc`, `/ddd`, если задачи про код UI нет. Не подменяй макетом проектирование API или бэкенда.

## Когда не применять

- Только требования, истории или доменная модель без просьбы сделать UI.
- Пользователь утвердил макет и просит следующий этап (API, сервер) — не пересобирай макет «заодно».
- Запрос только «как открыть / увидеть окно» при уже собранном клиенте — режим **только запуск**: UI не пиши, выполни §0 и §7.

---

## 0. Режим и порядок шагов

Сначала выбери **один** режим по запросу:

| Режим | Когда | Что делать |
| --- | --- | --- |
| **создание** | Клиента нет; просят новый макет; или явно просят пересобрать / упростить до визуального макета | Шаги 1 → 7 ниже, затем §8 при необходимости. Существующую доменную логику в клиенте **убрать**, не сохранять «игру ради демо» |
| **правка** | Клиент есть; меняют внешний вид, навигацию, баг UI **без** просьбы упростить | Источники по делу → правки §4–§6 → напомнить запуск §7. Не пересоздавай launcher/README. Не возвращай доменную логику |
| **только запуск** | «Не вижу окно», «как открыть» | Только §7. Код, README и launcher не трогай, если способ запуска уже описан |

Порядок при **создании** (не переставляй):

1. Источники (§1).
2. Ключевой экран (§3) и стек (§2).
3. Код, статичный mock, навигация (§4, §6).
4. Контраст (§5).
5. Способ увидеть UI (§7): launcher/README — только если ещё нет.
6. В чате — как открыть **самим**; не выдавай запуск из терминала агента за видимый экран.

Не запускай GUI из чата «чтобы показать» до шага 6.

## 1. Источники (не выдумывать)

Читай артефакты **этого** репозитория, **если они есть** и нужны режиму. Не требуй полный пакет US/UC для правки или только запуска.

Два разных приоритета — не смешивай.

**Какой экран и какую правку делать** (сначала чат):

1. Явный запрос пользователя в этом ходе (экран, цвет, «только открыть окно», «упростить до макета»).
2. Уточнения в `$1` / `@`-файлах этого сообщения.
3. Уже существующий клиент в `src/` (режим правка / только запуск / пересборка).

**Откуда факты домена** (если пишешь или меняешь **внешний вид** UI):

1. Закрытые ответы заказчика, согласованные ФТ/НФТ — уточняют ТЗ.
2. User Stories / Use Cases — какие экраны, подписи, запреты показа.
3. Доменная модель, глоссарий — имена, коды, что показывать / скрывать.
4. ТЗ / спецификация стека — UI-фреймворк, десктоп vs веб, языки.

Стоп «спроси и не пиши код в этом ходе» — **только режим создание**, и только если нет ни US/UC, ни `@`-файла, ни достаточного описания экрана в чате. Спроси с **рекомендацией**, какой экран делать. Не выдумывай предметную область.

Не показывай в UI то, что требования прячут от пользователя (внутренние алгоритмы, скрытое состояние, секреты). Не добавляй возможности вне scope документов, пока пользователь явно не расширил scope.

---

## 2. Стек и место в репозитории

1. Стек UI — из спецификации текущего проекта, не «модный дефолт».
2. Если в промте упомянуты Tailwind / Framer Motion / иное «если используется» — применяй **только** когда это стек проекта. Иначе — средствами выбранного стека. Анимации — **минимум** (см. §4).
3. Код — в `src/` (или путь из правил репозитория / указания пользователя). Модульные подкомпоненты, без заглушек `TODO` / «реализовать здесь».
4. Зависимости UI — `requirements.txt` / манифест рядом с клиентом. Не тяни лишние пакеты «на всякий случай».
5. Не оставляй и не пиши модули «движка» домена (проверка ходов, ИИ, генерация флота и т.п.) ради макета. Статичные константы / снимок — достаточно.

---

## 3. Что считать «ключевым экраном» и объём окон

Один главный экран (или связка лобби + рабочий экран) плюс **все** окна/экраны/модалки, до которых можно дойти **меню и кнопками с него**. Не добавляй скрытые «глубокие» сценарии вне этой навигации.

Структура окон:

- **Одно главное окно** приложения.
- Справка, настройки, итог, статистика и т.п. — **модалки или панели** внутри него.
- Отдельные top-level окна ОС — **только** если так уже заложено в стеке / ТЗ проекта.

Не рисуй весь продукт, если пользователь просил только один экран без навигации к остальным. Макет = **UX визуального прототипа**. Утверждение макета не есть контракт API и не есть готовый бэкенд.

---

## 4. Статичные данные и навигация (вместо «живой» логики)

1. **Mock = константы / статичный снимок.** Таблицы, списки, поля, графики, «середина/конец» сценария — заполнены один раз из терминов глоссария и доменной модели. Не «Lorem ipsum», не чужой домен. Снимок **не пересчитывается** от действий пользователя.
2. **Навигация по роли элемента:**
   - меню / кнопки → другой экран стека, модалка или панель;
   - вкладки переключают панели;
   - язык / настройки UI — меняют подписи и сохранённые настройки клиента, **без** смены доменного снимка по правилам;
   - подтверждение, справка, итог, форма с несколькими полями — модальное окно (внешний вид);
   - клик по рабочей поверхности домена (ячейка, ход и т.п.) — **игнорировать** с точки зрения данных: снимок не менять.
3. Кнопки доменных действий оставляй в UI. Не симулируй правила: не меняй поле, счёт, флот, очередь хода. Допустимо только переключение экрана или открытие/закрытие окна для показа внешнего вида.
4. **Анимации — минимум:** открытие/закрытие окна или лёгкий переход панели. Без декоративного шума, без анимаций «ход / прицел / пульс выстрела».
5. **Локализация** — только если в scope; без лишних дублей строк и без полного набора языков «на будущее».
6. Не блокируй главный цикл UI. Таймеры партии, отложенные «ответы сервера», очереди ходов — не нужны макету.

---

## 5. Контраст и читаемость (обязательно)

Свой stylesheet/стиль часто сбрасывает цвет текста на системный (часто чёрный). На тёмном фоне такой текст не виден; на светлом дефолтный чёрный может быть нормален.

Правила:

- У каждого виджета/блока со **своим** стилем явно задай цвет текста. Не полагайся на наследование от окна.
- Проверь не только заголовки: списки, строки таблиц, легенды, боковые панели, подписи сущностей, вторичный текст.
- Контраст должен позволять прочитать содержимое без угадывания.
- Если пользователь указал цвет вместо нечитаемого (например жёлтый вместо чёрного) — примени его к этим элементам, не меняй всю палитру без просьбы.
- Перед «готово» в режимах создание/правка пройди панели с кастомными стилями: если текст мог остаться дефолтным — исправь.

---

## 6. Качество кода макета

- Разбей на логические подкомпоненты (экран, список/таблица/холст, диалог, локализация при необходимости).
- Полностью валидный код, без сокращений «и так далее».
- Подписи и форматы — по требованиям (язык UI, коды в состоянии vs отображение).
- Нет модулей доменного «движка» и нет `TODO` «подключить логику позже» как обязательной части макета.
- После правки внешнего вида напомни перезапустить клиент способом из §7 (п. «что сказать в чате»): живой процесс старые стили не подхватит.

---

## 7. Как пользователь увидит UI

Терминал агента в чате часто **не показывает** ни десктопное окно, ни браузер пользователя (процесс может жить без видимой рамки).

Запрещено:

- Считать запуск из чата (`python -m …`, `npm start` и аналоги) достаточным «UI открыт».
- Убивать чужие процессы, чтобы «вывести» окно.
- Писать, что пользователь уже видит экран, если запуск был только из сессии агента.

Развилка стека:

- **Десктопное окно** — launcher в проводнике; в чате назвать заголовок окна.
- **Веб** — URL (обычно localhost) открыть **самим** в браузере; в чате дать точный адрес. Launcher может поднимать dev-сервер, но не заменяет «открой URL».

Launcher и README:

- Режим **создание:** если файла запуска ещё нет — создай рядом с клиентом (`.bat` / `.cmd` на Windows, `.sh` на Unix — по ОС разработки). Если в README ещё нет секции запуска — добавь короткую: как открыть самим (проводник и/или URL) + запасная команда в **обычном** терминале пользователя, не в чате.
- Режим **правка** и **только запуск:** не создавай и не переписывай launcher/README, если способ уже есть. Только укажи его в чате.

Что сказать в чате (это и есть инструкция запуска; **не** «вернись к началу §7»):

1. Открыть UI самому: проводник / свой терминал / свой браузер.
2. Что искать: заголовок окна **или** URL.
3. Если пользователь пишет, что не видит UI после запуска из чата — не спорить; повтори пункты 1–2 этого списка. Код не переписывай, если клиент уже собран.

## 8. Утверждение и что дальше

- Пока нет явного утверждения макета — статус черновика, требует согласования. Не требуй дословную фразу «макет утверждаю»: достаточно однозначного согласия на этот UI. Голое «ок» на другой вопрос (например куда сохранить инструкцию) утверждением макета не считай.
- Утверждение относится к **внешнему виду и навигации** этого прототипа. Не расширяй scope на сервер и контракт каналов без запроса.
- Коммит — только если пользователь попросил.
- В память агента — только по явной команде («запомни» / `/pin-memory`). Имеет смысл помнить: способ запуска UI не из чата; утверждён макет (если просили записать).

После утверждения в ответе кратко: что утверждено; что это не API; какой следующий шаг **рекомендуешь** (обычно контракт клиента с бэкендом под те же экраны). Не начинай его без согласия.

## Чек-лист перед ответом «готово»

Зависит от режима. Пункты «если есть / если ещё нет» не блокируют «готово».

**Только запуск**

- [ ] В чате сказано, как открыть UI самим (окно или URL); запуск из терминала агента не выдан за видимый экран
- [ ] Код не менялся без нужды

**Создание или правка** (плюс запуск выше)

- [ ] Прочитаны те источники, которые есть и нужны этой задаче (US/UC, домен/глоссарий, стек — не обязательно все)
- [ ] Ключевой экран + окна, достижимые меню/кнопками; без выдуманного scope
- [ ] Скрытое по требованиям в UI не попало
- [ ] Mock — статичный снимок; доменная логика и «игра» отсутствуют
- [ ] Работают только навигация, вкладки, язык/настройки UI; клики по полю/домену не меняют снимок
- [ ] Анимации минимальны; локализация без лишних дублей
- [ ] Явный цвет текста на блоках со своим стилем, контраст достаточный
- [ ] Launcher и секция README есть **или** уже были — не обязательны заново при правке
- [ ] Нет `TODO` в коде макета; нет «движка» домена ради демо
