# Словарь данных (Data Dictionary)

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки скилла к названию или домену текущего репозитория.

**Цель:** один файл словаря данных: сущности и объекты-значения, поля, обязательность, типы, ограничения, умолчания, граница MVP, связи и открытые вопросы — с трассировкой к требованиям и к диаграмме классов (или к доменной модели, если схемы классов нет).

**Жёсткий гейт:** после любой записи в файл словаря **обязательна** проверка по §7 **до** сообщения разработчику, что словарь создан или обновлён. Пропуск гейта = работа не завершена. Исправление находок → повтор §7; не больше **двух** проходов гейта за один запуск (см. §7).

---

## Когда применять

- Пользователь просит словарь данных, каталог атрибутов, поля сущностей (типы, ограничения, умолчания, MVP).
- Запущена команда `/data-dictionary`.
- Нужно обработать ответы заказчика по вопросам словаря и внести их в файл.
- Нужно **проверить уже написанный** словарь чек-листом §7.

Не применяй вместо `/ft`, `/nft`, `/us`, `/uc`, `/ddd`, `/diagram-mermaid`, `/diagram-bpmn`, если задачи про словарь полей нет.

## Результат

По умолчанию (если пользователь не указал иной путь):

| Артефакт | Файл |
| --- | --- |
| Словарь данных | `requirements/data-dictionary.md` |

Статус новых и изменённых артефактов: `Черновик, требует согласования`, пока заказчик **явно** не утвердит документ. Статус `Согласовано` агент сам не ставит.

В `.md` **запрещён** fence ` ```text ` и пустой ` ``` ` для длинных цитат. Обычный markdown; fence только с осмысленным языком (`mermaid` и т.п.).

Если в проекте есть `requirements/answers-project.md` — закрытые пары вопрос→ответ только туда. Код по теме вопроса: **`DD`**; если вопрос меняет формулировку ФТ или модели — `FT` / `DDD`, не два кода на одну строку. Формат — правило проекта для базы ответов, если оно есть. Если файла базы нет — оставь открытые вопросы в словаре и спроси, куда складывать закрытые. Не считай таблицу DD-Q в словаре заменой базы ответов.

## 1. Источники и границы

Читай **текущий** репозиторий. Архивные папки — только по явному `@`. Если пользователь просит учитывать накопленное — `reports/agent-memory.md` (если файл есть).

**Список классов** (без него словарь в этом ходе не пиши):

1. Диаграмма классов (Mermaid `classDiagram`, PlantUML и т.п.) — основной источник классов, атрибутов, связей, мощностей.
2. Если диаграммы нет, а есть доменная модель с сущностями/VO — используй её как список классов и явно отметь в шапке, что покрытия class diagram нет.
3. Если нет ни диаграммы, ни модели — зафиксируй пробел, спроси с рекомендацией (например: сначала `/ddd` или диаграмма классов), **не выдумывай** сущности в этом ходе.

Остальные источники (читай, если файлы есть; отсутствие — пробел в шапке, не догадка):

| Источник | Зачем |
| --- | --- |
| Глоссарий | Канон терминов и кодов |
| Функциональные требования | Поведение, которое порождает или ограничивает поле |
| Use Cases (и US — для MVP и экранных/эфемерных полей) | Кто читает/пишет объект |
| Закрытые ответы `Axxxx` | Важнее предварительного ТЗ при конфликте |
| НФТ | **Только** ограничения данных (мощность id, срок жизни, лимит экземпляров). Latency, покрытие тестами, ОС — не поля словаря |

Правила:

1. Не выдумывай бизнес-поля, типы, enum, форматы, умолчания и сущности «для полноты».
2. Факт отдельно от предположения. Спорное — в открытые вопросы, не в таблицу как факт.
3. Термины — из глоссария. Новый устойчивый термин предложи в глоссарий, не вводи молча.
4. Соблюдай MVP / scope. Вне scope — списком, без полноценных сущностей «на будущее», пока пользователь явно не попросил.
5. Словарь — контракт данных предметной области, не схема СУБД и не JSON API, если пользователь не просил solution design.
6. При вопросах заказчику **всегда** давай рекомендацию, с которой можно согласиться или осознанно отойти.
7. Имена типов и атрибутов — как в доменной модели / class diagram (если там заданы идентификаторы). Описания — на языке глоссария.

## 2. Что описывать

**Сущности (Entity)** из списка классов — в реестре обязательно.

**Объекты-значения с боксом** на схеме (или явные VO в модели) — в реестре, если без них нельзя описать поля сущности, факт операции, снимок или отображение.

**Типы без бокса** (id, enum, однополевая константа) — в справочниках (§3.2 п. 7), не как отдельная «сущность» на каждый id. Допустимо вынести VO в реестр, если у него несколько атрибутов или отдельная таблица нужна для ограничений; тогда в покрытии классов укажи «тип атрибута на схеме, не бокс».

**Не сущности словаря:** акторы и роли без учётной записи в источниках; экраны, кнопки, каналы транспорта, JSON-схемы; службы без состояния; методы классов.

**Наследование:** если на схеме/в модели его нет — не выдумывай иерархию. Если есть — отрази как в источнике, не расширяй.

## 3. Алгоритм

Режимы по запросу (отдельной подкоманды нет). Любая запись в файл словаря заканчивается **§7**, затем §8.

| Запрос | Действие |
| --- | --- |
| Создать / обновить словарь | §1 (есть ли список классов?) → 3.1 → 3.2 → **§7** → §8 |
| Только проверить существующий файл | §7 по указанному (или умолчательному) файлу. Дефекты гейта правь в **том же** файле, если пользователь не сказал «только отчёт без правок». Второй проход §7 — только если файл менялся. Лимит проходов — §7. Затем §8 |
| Обработать ответы («согласен», тексты по DD-Q / пунктам) | Внеси в словарь и в базу ответов (если она есть) → **§7** → §8. Новые DD-Q — только если ответ породил их |

Совмещение «проверь» и ответы в одном сообщении: сначала перенос ответов, затем один гейт §7 (не два полных аудита «на всякий случай»).

### 3.1. Сбор

1. Список классов: боксы Entity + VO на диаграмме и/или сущности и VO модели; атрибуты из таблицы атрибутов источника.
2. Сопоставь схему и модель, если есть обе: то, что на схеме только *связью*, в модели часто уже атрибут.
3. Пройди ФТ, UC и при необходимости US: что хранится, что вычисляется, что только на экране, что вне MVP.
4. Кандидат в поле, которого нет в таблице атрибутов класса — сначала §4, потом строка таблицы.

Нет списка классов (§1) — на шаге 3.1 остановись, не переходи к 3.2.

### 3.2. Запись файла

Структура `data-dictionary.md` (этот порядок):

1. Шапка: статус, дата, назначение, источники, какой список классов использован (диаграмма / только модель), приоритет `Axxxx` / согласованных ФТ.
2. Соглашения колонок (§5).
3. **Реестр** — таблица объектов: имя, вид (Entity/VO), контекст/агрегат, хранится ли в оперативном состоянии (**только если** источники это различают; иначе колонку не выдумывай), MVP, краткий список обязательных полей.
4. **Покрытие классов** — таблица: класс источника → раздел словаря → как отражены атрибуты (поле / связь / производное). Если диаграммы нет — покрытие по модели, с пометкой.
5. **Связи** — из диаграммы классов (от, к, тип, мощность, какое поле словаря). Нет диаграммы — из модели. **Новых рёбер не добавляй.** Связь есть, хранимого поля нет (расчёт, функция UI) — так и напиши в строке связи.
6. **Таблицы атрибутов** — отдельная таблица на каждый объект реестра (§5).
7. Справочники: идентификаторы, константные VO, перечисления, протокольные коды из источников.
8. Анализ относительно схемы/модели: что добавлено и почему; что рассмотрено и **не** добавлено.
9. Вне MVP (списком; без полноценных таблиц «на будущее», пока пользователь не попросил).
10. Трассировка к UC (кто читает/пишет), если UC есть.
11. Открытые вопросы с рекомендациями **или** явно «открытых нет».
12. Отложенные решения, уже закрытые как «при API/коде», со ссылкой на `Axxxx` — не переспрашивать.

Затем **§7**. Не пиши в чат, что словарь готов, пока гейт не пройден или не остановлен по лимиту проходов.

## 4. Расширение относительно диаграммы (модели)

Связь на схеме ≠ отсутствие поля в словаре. Композицию и обязательную ассоциацию включай **атрибутом**, если без этой части экземпляр неполон (цель операции, адрес, вложенная коллекция).

**Перед добавлением поля, которого нет в таблице атрибутов класса, проверь по порядку. Первое сработавшее правило решает:**

1. Нет прямой опоры в глоссарии, ФТ, UC, US, модели, схеме или `Axxxx` → **не добавляй**. Если поле кажется нужным — DD-Q с рекомендацией, не строка «как будто решено».
2. Поле полностью выводится из уже описанных (производное) → **не хранить отдельно**; можно фразой в описании источника.
3. Это деталь UI или транспорта, а не данные предметной области → **не хранимое поле**; правило показа допустимо в описании, без второго атрибута «символ/глиф», если источника на хранение нет.
4. Источники относят это вне MVP → не в таблицы MVP; в список «вне MVP» или не включать, пока пользователь не расширил scope.
5. Иначе (опора есть, не дубль, данные домена, в MVP) → **добавь** и укажи источник; если на схеме это была только связь — пометь это в описании.

Не добавляй: второй штамп времени рядом с уже заданным якорем жизненного цикла; второй идентификатор факта при уже каноническом номере/ключе в источниках; учётную запись, если в источниках её нет; поля другого уровня агрегации, чем задано источниками; поля «на будущее» вне MVP.

Умолчание, которого нет в источниках, не выдумывай: ставь «—» и при необходимости DD-Q.

## 5. Колонки таблицы атрибутов

Каждая таблица объекта:

| Атрибут | Тип | Обязательность | Ограничения | По умолчанию | MVP | Описание | Источник |

Над таблицей — явный список **обязательных** полей (и отдельно необязательные / условные).

| Колонка | Смысл |
| --- | --- |
| Обязательность | **Да** / **Нет** / **Условно** (условие в той же строке) |
| Тип | Бизнес-тип (целое, строка, логический, enum, ID, VO, набор). Не тип СУБД |
| Ограничения | min/max, длина, enum, format/pattern, кратность, уникальность. Не зафиксировано источником — напиши «не зафиксировано» и вынеси в DD-Q **или** оставь в отложенных, только если это уже закрыто `Axxxx` как «при API» |
| По умолчанию | Значение в момент создания. «—» если неприменимо или не задано источником |
| MVP | **MVP** или **не MVP** (или смешанное: поле есть, часть значений enum вне MVP — тогда перечисли) |
| Источник | ID ФТ/UC/`Axxxx`/глоссарий/диаграмма/модель — без пустых ссылок |

Перечисления — отдельная таблица: имя, значения, ограничения, типичное умолчание, MVP, где используется.

## 6. Вопросы заказчику

- ID в файле: `DD-Q1`, `DD-Q2`, … (не путать с `Axxxx`). Нумерация с последнего свободного в этом файле.
- Один вопрос — одна тема (не смешивай формат идентификатора и правило округления агрегата).
- У каждого вопроса — **рекомендация**.
- Уже закрытое «решим в API» не переспрашивай.
- После ответа: перенос в `answers-project.md` при наличии файла (код по § «Результат»), правка таблиц, снятие вопроса из открытых. Если только «согласен» / «да» — в базу пиши **текст рекомендации**, не голое «Согласен».

## 7. Обязательная проверка (гейт)

Выполни после создания, обновления или переноса ответов и **до** §8. При «только проверь» — тот же чек-лист.

**Лимит:** не больше двух проходов «гейт → правка файла → гейт» за один запуск. Если после второго прохода пункт нельзя закрыть без решения заказчика — оформи DD-Q или пробел источника в шапке, **остановись**, переходи к §8. Не крути гейт третий раз.

Копируй и отмечай:

- [ ] У **каждого** поля в таблицах атрибутов заполнены: обязательность, тип, ограничения, значение по умолчанию, MVP / не MVP.
- [ ] Спорные места вынесены в **открытые вопросы**, а не записаны как факты (нет выдуманных форматов, умолчаний, enum, хранимых полей «для удобства»).
- [ ] Есть реестр объектов, таблица связей, ограничения в колонках, и секция открытых вопросов **либо** явная фраза, что открытых нет.
- [ ] Нет полей/объектов без опоры в источниках: добавления относительно схемы/модели обоснованы §4 или перечислены как отвергнутые.
- [ ] Покрытие классов: все Entity и VO-**боксы** источника (диаграмма, иначе модель) есть в реестре или явно отнесены к справочнику типов без бокса; атрибуты источника не потеряны. Объекты сверх боксов допустимы только как типы атрибутов схемы или как расширение по §4 — и перечислены в анализе. Лишних классов «с нуля» нет.
- [ ] Композиции и обязательные ассоциации отражены полями или в таблице связей помечены как не хранимые (расчёт / функция UI).
- [ ] Вне MVP не выдано за MVP; роль без учётной записи в источниках не стала сущностью.
- [ ] У открытых DD-Q есть рекомендации; fence `text` в файле нет.
- [ ] Список классов был (диаграмма или модель); если словаря нет на диске при режиме «только проверка» — не создавай второй файл молча, сообщи о пробеле.

Открытые вопросы — **допустимый исход гейта**, если они оформлены как DD-Q, а не спрятаны в таблицах как решённые факты.

**Запрещённые отговорки:** «проверка очевидна», «сделаю QC потом», «в чате опишу огрехи без правки файла», «связи и так понятны из композиций», «ещё один проход гейта на всякий случай».

## 8. Сообщение разработчику (только после §7)

Кратко, без копирования всех таблиц:

- путь к файлу и статус (для нового/изменённого без явного утверждения — `Черновик, требует согласования`);
- сколько объектов в реестре; чем покрыт список классов (диаграмма / модель);
- какие поля добавлены относительно схемы (одной строкой);
- какие `DD-Qn` ждут ответа (рекомендации — в файле; в чате не дублируй простыню);
- что гейт §7 пройден или остановлен по лимиту проходов (и почему).

Не утверждай пакет словаря сам. Предложи согласовать файл. Другие QC-скиллы (`/qc-ft-nft`, `/qc-us-uc`, `/qc-ddd`) без согласия не запускай.

## 9. Типичные ошибки

| Ошибка | Как правильно |
| --- | --- |
| Сообщить «готово» до §7 | Сначала гейт, потом §8 |
| Выдумать default / формат id / символы UI | «—» + DD-Q с рекомендацией |
| Потерять адрес, цель операции или вложенную коллекцию, потому что на схеме это связь | Включить как поле, указать «на диаграмме — связь» |
| Добавить хранимое поле только для отображения | Правило показа в описании; не второй атрибут без источника |
| Словарь = копия class diagram без ФТ/UC | Типы и связи из схемы, смысл и MVP из требований |
| Новые рёбра «для полноты» | Только связи из диаграммы или модели |
| Обработать ответы и не вызвать §7 | Любая запись в файл → §7 |
| Бесконечно крутить гейт при отсутствии диаграммы | Лимит двух проходов; пробел источника или DD-Q |

## Red flags — остановись

- Сущности, которых нет ни на class diagram, ни в доменной модели, ни в ФТ
- Умолчание «как обычно в REST» без `Axxxx`
- Гейт §7 не выполнялся в этой сессии после записи файла
- Сообщение разработчику до повторной проверки после правок гейта
- Третий проход гейта в том же запуске
- Написание словаря без списка классов
