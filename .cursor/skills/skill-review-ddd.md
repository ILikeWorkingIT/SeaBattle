# Критический аудит DDD-модели

Универсальный скилл архитектора/ревьюера модели. Не подставляй факты и термины другого проекта. Работай только с файлами текущего репозитория и вводными пользователя.

**Цель:** найти нарушения канона DDD и расхождения с требованиями; выдать отчёт; в режиме после `/ddd` сразу получить **проверенный** набор сущностей, VO, атрибутов и инвариантов в файле модели.

Строгость: не сглаживай находки. Согласованные имена (`Axxxx`) не отменяют структурные ошибки (ложный агрегат, связь без ID, неверный жизненный цикл статуса).

---

## Когда применять

- Пользователь просит аудит / ревью доменной модели, границ агрегатов, Entity vs VO.
- Запущена команда `/review-ddd`.
- **Обязательный** заключительный этап `.cursor/skills/skill-ddd.md` (режим «после /ddd»).

Не применяй вместо написания модели с нуля, если файла модели ещё нет — сначала `/ddd`. Не подменяй `/qc-ft-nft` или `/qc-us-uc`.

---

## Режимы

| Режим | Как попали | Модель после отчёта |
| --- | --- | --- |
| **После /ddd** | Финальный шаг `skill-ddd` | Запиши отчёт. В `domain-model.md` перенеси **только разрешённый набор** (ниже). Один проход на один `/ddd`; после переноса повторный полный аудит не запускай. |
| **Самостоятельный** | `/review-ddd` или явная просьба аудита | Только отчёт. **Не меняй** `domain-model.md`, пока пользователь не согласится применить §4. |

**После /ddd в модель переносить:**

1. Все находки уровня C (ложный агрегат, связь без ID, Entity без идентичности, литерал статуса против ФТ, второй счётчик идемпотентности).
2. Пробелы инвариантов с прямой опорой на ФТ / UC / `Axxxx`.
3. Реклассификация Entity ↔ VO и снятие эфемерного «агрегата-расчёта».

**После /ddd в модель не переносить без вопроса в открытом списке:**

- косметическое переименование идентификаторов, уже зафиксированных в `Axxxx` или явно согласованных;
- спорный сплит/слияние BC, если в источниках нет однозначного языка;
- новые бизнес-правила и литералы enum «для красоты учебника DDD».

Не выдумывай атрибуты, чтобы «§4 был полнее». Вопросы без факта — в отчёте и в открытых вопросах модели.

В чат: краткий вердикт, число C-находок, путь отчёта. Не дублируй все таблицы §4.

## Результат

По умолчанию: `reports/domain-model-review.md`. Статус при самостоятельном режиме: `Черновик анализа, требует согласования`. В режиме после `/ddd` после переноса правок: в шапке отчёта укажи, что критичные правки перенесены в модель; отчёт — протокол, не второй источник правды.

Объект аудита: `requirements/domain-model.md` (или путь пользователя).

В `.md` запрещён fence ` ```text `.

Если есть `requirements/answers-project.md` и пользователь **согласился** с выводами самостоятельного ревью — перенеси закрытые пары туда, код `DDD` (формат — правило проекта для базы ответов). В режиме после `/ddd` не выдумывай новые `Axxxx` на ещё не заданные вопросы.

## Входные данные

Прочитай (если есть):

- доменную модель;
- глоссарий;
- ФТ (и НФТ — только если влияют на инварианты домена);
- US, UC, реестры;
- `answers-project.md`;

- `reports/agent-memory.md`, если пользователь просит учитывать накопленное.

## Чек-лист аудита

Выполняй все пять блоков. Фиксируй только подтверждённые находки.

### 1. Единый язык (Ubiquitous Language)

- Совпадают ли имена BC / сущностей / VO / атрибутов и литералы enum с глоссарием и кодами требований?
- Если идентификаторы на другом языке, чем глоссарий — есть ли таблица соответствия в шапке модели? Нет ли смеси языков в одном идентификаторе?
- Не подменён ли термин глоссария близким, но другим смыслом (очередь процесса vs номер записи в истории; код операции vs статус составного объекта)?
- Протокольные коды из источников не переименованы?

Расхождение языка идентификаторов при явном решении проекта — **не** критическая ошибка DDD, если смысл сохранён и есть соответствие. Расхождение **смысла** — находка §2.

### 2. Границы агрегатов

- Внутри корня только то, что по UC/ФТ меняется атомарно вместе?
- Корень — единственная точка входа?
- Нет ли агрегата у эфемерного расчёта, которого нет в хранимом состоянии?
- Нет ли искусственного id у объекта без жизненного цикла?
- Нет ли **коллекции других корней** внутри агрегата (допустимы только ID)?
- Не шарятся ли типы Entity между BC?
- Инвариант на **набор** экземпляров не засунут внутрь одного экземпляра (нужен отдельный корень или служба координации)?
- Совместная транзакция двух корней — только если это явно в источниках, и это исключение?
- Не попали ли пороги НФТ (latency, покрытие тестами) в инварианты домена?

Перегруженность графа (сотни Entity там, где хватает VO) — нарушение классификации, не обязательно неверная граница транзакции. Различай в отчёте.

### 3. Ссылки между агрегатами

- Только ID?
- Нет строк вида «читает / держит объект другого корня» без атрибута id?
- Ссылка на внутренность чужого агрегата — только id, и обоснована правилом?

### 4. Entity vs VO

- Нет идентичности и независимого жизненного цикла → VO.
- Деньги, адрес, координата, длительность политики, норма состава, снимок счётчиков, код/номер, выводимый из полей → VO.
- Составной объект с id и изменяемым содержимым, который прослеживают во времени → Entity.
- Один факт не хранится дважды (флаг на записи истории и статус корня).
- Производный код не смоделирован как независимое хранимое поле, оторванное от источника.

### 5. Полнота инвариантов относительно ФТ / UC / глоссария

Пройди Must (и критичные Should) ФТ и основные постусловия UC. Для каждого: есть инвариант в нужном агрегате/службе, или правило не доменное (доставка, UI-блок, слой приложения) — тогда явная пометка «вне модели / событие / UI».

Ищи типичные пробелы: отказ создания и запрет «полусозданного» агрегата; нелегальная команда; конкурирующие команды к одному корню; независимость экземпляров; что не двигает политику жизни объекта; скрытие данных; возобновление/повторный доступ по id; единый отказ без утечки существования; перечень доменных событий; согласованность двух представлений одного факта (например, состав и размещение); UI-состояние в Core.

Литерал статуса «успешного конца», которым в ФТ помечен **сбой или удаление** — критическое несоответствие требованиям.

## Формат отчёта

# Аудит DDD-модели

Шапка: статус, дата, объект, источники.

## 1. Анализ критических ошибок (Архитектурные нарушения DDD)

Нумерованные C1, C2, … с сутью нарушения. Если критичных нет — фраза: `Нарушений не обнаружено`.

Критично (C): ложный агрегат; связь корней без ID; Entity без идентичности; статус/исход, противоречащий жизненному циклу в ФТ; два независимых счётчика идемпотентности вопреки решению проекта.

## 2. Несоответствия исходным требованиям (ФТ/UC/Глоссарий)

Потерянные атрибуты; UL; статусы vs UC; таблица «пробел → ID требования». Инварианты, которых нет в модели.

Не критикуй отсутствие стека/JSON, если это сознательно вынесено в API.

## 3. Рекомендации по оптимизации

Таблица: # | Было | Стало. Конкретные правки, не общие советы «подумать о границах».

## 4. Итоговый скорректированный вариант (Refactored Model)

Полные таблицы сущностей, VO и инвариантов **в том же формате**, что `skill-ddd` (§4 того скилла). Учти все принятые замечания §1–3.

Если замечаний нет (нет C, нет пробелов ФТ, нет правок Entity/VO/связей): в §4 напиши, что корректировка не требуется, канон — текущий файл модели.

Не копируй в §4 выдуманные поля «для красоты».

Вердикт в конце: готова ли модель к разработке; что сделать заказчику (согласиться / ответить на вопросы).

## Порядок работы

1. Прочитать модель и источники.
2. Пройти чек-лист, собрать C и прочие находки.
3. Записать отчёт.
4. По режиму: перенести **разрешённый набор** в модель **или** ждать согласия на весь §4.
5. В режиме после `/ddd`: обновить шапку модели (источник — этот аудит); открытые вопросы модели не закрывать молча; **не** начинать второй полный аудит в той же сессии.

Запрещённые отговорки: «для MVP сойдёт»; «имена уже согласованы — структуру не трогаем»; «ячейка с координатой без своего id — тоже Entity»; «ревью без правок, пользователь сам сольёт».

## Типичные ошибки ревьюера

| Ошибка | Как правильно |
| --- | --- |
| Переписать модель под любимый учебник DDD | Только разрывы с источниками и каноном границ |
| Назвать BC «лишним», если язык разный | Разный язык — повод для BC |
| Требовать один корень на весь сервер | Лимит на набор экземпляров — отдельный корень или служба |
| Пропустить связь 1:1 «читает настройки» | Это объектная связь, нужен id |
| Считать аудит законченным без §4 | §4 обязателен всегда |
| Запустить ревью повторно после переноса §4 | Один проход на один `/ddd` |
| Переименовать согласованные `Axxxx`-имена «заодно с C» | Только C, инварианты из источников, Entity↔VO |
