# Написание User Stories, ролей и прав

Универсальный скилл системного аналитика. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки скилла к названию или домену текущего репозитория.

## Когда применять

- Пользователь просит User Stories, роли/права, критерии приёмки (в т.ч. Gherkin), INVEST-ревью или реестр историй.
- Запущена команда `/us`.
- Нужно обработать ответы заказчика по открытым вопросам US и обновить артефакты.
- Нужна **проверка качества** уже написанного пакета US (роли, истории, AC, реестр) — по чек-листу §8.

Не применяй вместо `/ft` или `/nft`, если задача только про таблицы ФТ/НФТ без историй.

---

## Результат (формат файлов)

По умолчанию (если пользователь не указал иной путь) — папка `requirements/user-stories/`:

| Артефакт | Файл | Содержание |
| --- | --- | --- |
| Одна история | `us-NNN-<kebab-name>.md` | Заголовок, User Story, метаданные, AC (Gherkin) |
| Реестр историй | `us-registry.md` | Список US, статусы, INVEST, вопросы, итог проверки качества |
| Роли и права | `list-us.md` | Акторы, матрица прав, связь с US |

Статус новых артефактов: `Черновик, требует согласования`, пока заказчик явно не согласует.

### Именование и ID

- Файл: префикс `us-` + **трёхзначный** номер + kebab-название (пример: `us-001-login.md`).
- ID в заголовке и реестре: **`US-001`**, `US-002`, … — **тот же** трёхзначный номер, что в имени файла.
- Нумерация с последнего существующего ID; если папки нет — с `US-001`.
- Если в правилах репозитория задан иной формат — следуй правилам репозитория.

### База закрытых ответов

Если в проекте есть `requirements/answers-project.md` (и правило переноса ответов) — закрытые пары вопрос→ответ пиши только туда (код `US`; при влиянии на ФТ/НФТ — `FT` / `NFT` по теме). Не копируй закрытые Q&A в тела US как хранилище ответов. Если файла базы нет — держи открытые вопросы в реестре и спроси, куда складывать закрытые.

## 1. Роли (акторы) и права

### 1.1. Как выделять роли

1. Бери роли **только** из источников текущего репозитория (ТЗ, глоссарий, ФТ, закрытые ответы, явные указания заказчика). Не выдумывай персоны «для полноты».
2. Различай:
   - **Пользовательская роль** — человек (или внешняя организация), от лица которого пишется User Story.
   - **Системный участник** — сервер, клиент, бот, фоновый процесс, смежная система: есть в матрице прав, но **отдельная US от лица системы не заводится**, пока заказчик явно не подтвердит иное. Ценность для пользователя описывай в AC его историй.
3. Имена ролей — термины заказчика / глоссария. При переименовании обнови `list-us.md`, реестр и права; старые ярлыки не оставляй.
4. Компоненты «клиент / сервер / канал» указывай в правах, если без них неясны границы доступа. Не смешивай их с пользовательскими ролями без пояснения типа.

### 1.2. Матрица прав (`list-us.md`)

1. Для каждой возможности: **✓** / **✗** / **—** (не применимо) по ролям.
2. **Не ставь «—»**, где сторона реально владеет или использует сущность, без которой сценарий невозможен. Если имеется в виду «не получает через UI» — отдельные строки: «выдать/показать пользователю» vs «хранить и использовать».
3. Права опираются на ФТ / закрытые ответы / глоссарий; источники — в примечании.
4. Роли вне scope — блок «вне MVP / вне scope», не в матрицу без запроса.
5. Открытые уточнения по правам — в конце `list-us.md` со ссылкой на вопросы в `us-registry.md`.

## 2. Правила User Story

### 2.1. Когда дробить / не дробить

- Одна US = одна **пользовательская ценность**, не один технический шаг.
- Отказы, валидация, edge cases — по умолчанию **AC той же истории**, если нет отдельной ценности.
- Поведение системного участника — в AC истории пользователя, которому это нужно.
- Крупную историю можно оставить с оговоркой INVEST «Small частично» и дробить задачами разработки, не плодя Must-фрагменты без ценности.

### 2.2. Формат User Story

Канон (EN-метки допустимы; язык текста — язык проекта, по умолчанию русский):

```text
As a <роль>,
I want <действие или возможность>,
So that <ценность или результат>.
```

Эквивалент:

```text
Как <роль>,
я хочу <действие или возможность>,
чтобы <ценность или результат>.
```

Обязательно: роль, действие, ценность.

### 2.3. Структура файла одной истории

**Порядок секций строго:**

1. `# US-NNN: <Краткое название>`
2. Сразу `## User Story` и формулировка
3. Метаданные **после** User Story:
   - **Статус**
   - **Приоритет (MoSCoW):** Must / Should / Could / Won't
   - **Источник:** ТЗ / глоссарий / `Axxxx` / артефакты (не голое «решение заказчика»)
   - **Связанные ФТ** (и при необходимости НФТ), если уже есть
4. `## Acceptance Criteria (Gherkin)`

Метаданные **выше** User Story не ставить. **Источник** после приоритета обязателен.

### 2.4. Приоритет MoSCoW

- **Must** — без этого нельзя пройти основной пользовательский сценарий MVP по источникам.
- **Should** — заявлено в целях/контракте, сценарий возможен без этого.
- **Could** — слабое следствие, удобство, уточнение представления.
- **Won't** — вне scope; в файлы историй не тащи (только «Вне scope» реестра).

При расхождении с приоритетом связанных ФТ — вопрос заказчику.

### 2.5. Acceptance Criteria (Gherkin)

1. Минимум **3** AC + отдельно **edge case** (AC4 или явная пометка Edge case).
2. `Given` / `When` / `Then` / `And`; при необходимости несколько блоков в одном AC.
3. Проверяемость: наблюдаемый результат, отказ, состояние, оповещение. Без «удобно» / «быстро» без измеримого критерия (критерий — в НФТ или закрытом ответе).
4. Термины — из глоссария текущего проекта.
5. UX/отображение в AC — только после явного описания заказчиком или закрытого ответа; иначе вопрос + рекомендация.
6. Ссылки на `Axxxx` / ID ФТ в Then/And, когда правило оттуда.

### 2.6. INVEST-ревью

Проверь каждую историю по буквам:

| Буква | Вопрос |
| --- | --- |
| Independent | Можно ли понять и оценить ценность без обязательного слияния с другой US? (зависимость от «создать объект/сессию» — допустимая оговорка, не фиктивная независимость) |
| Negotiable | Детали UI/протокола можно уточнять без смены ценности? |
| Valuable | Есть явная ценность для роли? |
| Estimable | Границы ясны по источникам / ФТ / ответам, чтобы оценить объём? |
| Small | Одна ценность; при раздувании — оговорка или дробление |
| Testable | AC позволяют написать проверки? |

Оценки по букве: `OK` / `Частично` / `Нет`.  
Итог по истории: принято / принято с оговоркой / на доработку.

**Куда писать:** только в `us-registry.md` — сводная таблица (ID × буквы INVEST × итог) и краткий разбор оговорок.  
**Не создавать** отдельный файл вроде `us-invest-review.md`.

## 3. Реестр и вопросы (`us-registry.md`)

### 3.1. Обязательные блоки реестра

1. Метаданные, ссылка на `list-us.md`, источники правды **текущего** репозитория.
2. Таблица: ID | Название | Роль | MoSCoW | Файл | Статус (`готово` / `требует уточнения`).
3. Покрытие акторов.
4. Вне scope US.
5. INVEST-ревью (§2.6).
6. Вопросы к заказчику (открытые / закрытые с `Axxxx`).
7. Вопросы к команде разработки (открытые / закрытые).
8. Краткий итог проверки качества (§8), если прогон делался.
9. Рекомендуемый следующий шаг.

Статус `требует уточнения` — пока открытый вопрос влияет на AC или границы.

### 3.2. Как формулировать вопросы

- Один вопрос — одна дыра (не смешивай роли, UX и API в одном пункте).
- В той же строке/пункте: **вопрос** + **рекомендация** + зачем нужен ответ («без ответа невозможно …»).
- Вопросы к заказчику — про поведение, scope, UX, приоритет.
- Вопросы к команде — про контракты ошибок, хранение, приёмку, наблюдаемость; не подменяй ими решение заказчика о бизнес-правиле.
- Закрытые ответы не дублируй длинным текстом в реестре — ID `Axxxx` и статус «закрыто».

## 4. Алгоритм работы

1. Прочитай источники текущего репозитория: глоссарий, ТЗ, ФТ (если есть), базу ответов (если есть), структуру папок. Архивные папки — только по явному `@` / запросу.
2. Фиксируй только явные вводные. Не выдумывай роли, права, UX, интеграции.
3. Акторы → `list-us.md`.
4. Пользовательские ценности → US; системное поведение → AC.
5. Для каждой US: формулировка, MoSCoW, источник, связанные FT, ≥3 AC + edge case, INVEST.
6. Собери `us-registry.md`.
7. Пройди чек-лист качества §8; замечания — в реестр или исправь сразу, если это явная ошибка формата.
8. В чат: кратко — число ролей, диапазон US, пути, открытые вопросы. Не дублируй все AC.
9. Противоречие источников / двух закрытых ответов — спроси; не усредняй молча.
10. Неясный ответ — сначала уточни интерпретацию, затем пиши в базу и правь файлы.
11. После ответов: база ответов (если есть) → обновить US, реестр, `list-us.md`.
12. Уточнение старого решения в базе ответов: удалить старую строку, добавить новый ID (по правилу проекта для базы ответов).
13. Если ответ меняет согласованные ФТ/НФТ — правь через процесс ФТ/НФТ проекта (команды вроде `/ft`, `/nft`) и предложи контроль качества ФТ/НФТ, если он в проекте есть; не запускай без согласия.

---

## 5. Согласование

- Пакет US без явного «согласовано» — статус черновика.
- «Согласен» / «да» по рекомендации → в базу ответов текст **рекомендации**, не голое «Согласен».
- UX/API-рекомендацию не вноси в AC до согласия.
- После согласования пакета — статус `Согласовано` и дата. Дальнейшие правки — по новому запросу.

---

## 6. Запрещено

- Выдумывать роли, права, AC и UX без источника.
- US от лица системного участника без явного согласия заказчика.
- «Не применимо» в матрице там, где сторона обязана иметь/использовать сущность.
- Отдельный файл только для INVEST.
- Метаданные выше блока User Story; пропуск **Источника** после MoSCoW.
- Меньше 3 AC или без edge case.
- «Быстро» / «удобно» в AC без измеримого критерия или отсылки к НФТ / закрытому ответу.
- Расширять scope без запроса (новые роли, каналы, режимы «на будущее»).
- Закрытые ответы только в US/реестре при наличии базы ответов проекта.
- Молча править противоречивые закрытые ответы.
- Стек и детали реализации в формулировке ценности US (если не просили solution design).
- Вшивать в скилл или в шаблоны название/домен конкретного продукта.

## 7. Шаблон файла истории

1. `# US-001: <Краткое название>`
2. `## User Story` + блок:

```text
As a <роль>,
I want <действие>,
So that <ценность>.
```

3. Метаданные:

- **Статус:** `Черновик, требует согласования`
- **Приоритет (MoSCoW):** Must | Should | Could | Won't
- **Источник:** ТЗ / глоссарий / Axxxx
- **Связанные ФТ:** FT-… (если есть)

4. `## Acceptance Criteria (Gherkin)` — не меньше трёх AC и один Edge case; каждый в блоке gherkin (`Given` / `When` / `Then` / `And`).

## 8. Проверка качества пакета US

Выполни перед финальной отдачей черновика (и при запросе «проверь US»). Фиксируй только подтверждённые дефекты.

| № | Проверка | Что искать |
| --- | --- | --- |
| 1 | Полнота артефактов | Есть `list-us.md`, `us-registry.md`, файл на каждую US из реестра |
| 2 | Роли | Пользовательские vs системные; имена из источников; матрица без ложных «—» |
| 3 | Формат файла | User Story сразу после заголовка; затем MoSCoW → Источник → связанные FT; ID = имени файла |
| 4 | Ценность | У каждой US роль, действие, ценность |
| 5 | AC | ≥3 + edge case; Gherkin; проверяемость; термины глоссария |
| 6 | INVEST | Есть в реестре; оговорки объяснены |
| 7 | Трассировка | Источник и/или связанные FT/`Axxxx` не пустые там, где источники уже есть |
| 8 | Вопросы | Открытые — с рекомендацией; закрытые не торчат в реестре без `Axxxx` |
| 9 | Scope | Нет незапрошенного расширения; «вне scope» явно |
| 10 | Противоречия | Конфликт US↔ФТ↔глоссарий↔закрытые ответы — вопрос, не молчаливое сглаживание |

В чат после проверки: число замечаний по серьёзности (блокер / важный / желательный) и что исправлено сразу. Детальный список — в `us-registry.md` или отдельном отчёте только если пользователь указал путь.
