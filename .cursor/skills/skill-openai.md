# OpenAPI-спецификация

Универсальный скилл системного аналитика. Это контракт **OpenAPI** (Swagger/ReDoc), не сервис OpenAI. Не подставляй факты, термины и правила другого проекта. Не привязывай формулировки скилла к названию или домену текущего репозитория.

**Цель:** один YAML-файл HTTP-контракта (плюс канал реального времени, если он есть в источниках): только FR/UC, где нужен endpoint; схемы, `$ref`, примеры, осмысленные ответы; локальный просмотр в Swagger UI и ReDoc.

**Жёсткий гейт:** после любой записи в YAML **обязательна** проверка по §8 **до** сообщения, что контракт готов. Пропуск гейта = работа не завершена. Чек-лист §8 — **не больше двух раз** за запуск (лимит и цикл правки — §8).

---

## Когда применять

- Пользователь просит OpenAPI / Swagger / ReDoc / контракт REST или WebSocket.
- Запущена команда `/openai`.
- Нужно обновить или проверить уже существующий `openapi.yaml`.

Не применяй вместо `/ft`, `/nft`, `/us`, `/uc`, `/ddd`, `/data-dictionary`, если задачи про API-контракт нет. Не подменяй спецификацией реализацию бэкенда.

## 0. Режим

Сначала выбери **один** режим по запросу (отдельной подкоманды нет):

| Режим | Когда | Что делать |
| --- | --- | --- |
| **создание** | Файла спецификации нет | Порядок §7 (внутри — гейт §8 и сообщение §9). Один файл по пути по умолчанию (или пути пользователя) |
| **обновление** | YAML уже есть; просят поменять контракт **или** «создай», но файл уже лежит | Порядок §7. **Прави существующий файл.** Второй `openapi.yaml` в другой папке не создавай без явного спроса |
| **только проверка** | «проверь спецификацию», аудит | Не создавай второй файл. §8 по существующему YAML; §5 — если просмотрщики не отвечают 200. Дефекты гейта правь **в том же файле**, если пользователь не сказал «только отчёт без правок». Нет файла — сообщи о пробеле, не создавай молча |
| **только запуск** | «открой Swagger / ReDoc», «не вижу документацию» | Только §5. YAML, README и launcher не переписывай, если способ уже описан. Нет YAML — сообщи о пробеле |

Нет ни ФТ, ни UC, ни иного описания операций — в режиме **создание** остановись: зафиксируй пробел, спроси с рекомендацией, **не** выдумывай API. Режимы **обновление**, **только проверка** и **только запуск** из-за отсутствия ФТ/UC не останавливай: им нужен уже лежащий YAML. Нет YAML в этих трёх режимах — пробел, не создание с нуля (исключение: просили «создай/обнови», файла нет, а источники операций есть — режим **создание**).

«Только отчёт без правок» — один проход §8, YAML не меняй, второго прохода гейта нет.

## Результат

По умолчанию (если пользователь не указал иной путь и имя):

| Артефакт | Файл |
| --- | --- |
| Спецификация | `requirements/openapi.yaml` |
| Запуск просмотрщиков | рядом со спецификацией, **если ещё нет**: скрипт запуска, принятый в проекте |
| Как открыть docs | `README.md` (или API-инструкция проекта, если README нет): порты и URL |

- Формат: **YAML**, расширение `.yaml`.
- Стандарт по умолчанию: **OpenAPI 3.0.3**. Иное (3.1.x, JSON) — только если пользователь или согласованное ТЗ явно задали.
- Имена JSON-полей: **camelCase**, если пользователь не задал иной канон и он не противоречит глоссарию / словарю данных.
- `summary` и `operationId` — **английский** (идентификатор — латиница). Прочие человекочитаемые тексты (`info.description`, `description` операций и схем): при **обновлении** — язык уже лежащего YAML; при **создании** — язык ФТ/глоссария, если пользователь не задал иной (например, полностью английский контракт).
- Новые и изменённые YAML: статус в чате `Черновик, требует согласования`, пока заказчик явно не утвердил контракт. Статус `Согласовано` агент сам не ставит.

В `.md` инструкциях **запрещён** fence с языком `text` и пустой fence для длинных цитат.

База ответов (`requirements/answers-project.md`, если есть): закрывающие `Axxxx` с кодом **`API`** — только после **явного** подтверждения контракта заказчиком. Пока YAML черновик, рекомендации живут в YAML и в вопросах чата; ID `Axxxx` не выдумывай и не записывай «заодно» в том же запуске, где контракт ещё не принят.

## 1. Источники

Читай **текущий** репозиторий. Архивные папки — только по явному `@`. Накопленное — `reports/agent-memory.md`, если файл есть и пользователь просил его учесть.

| Источник | Зачем |
| --- | --- |
| ФТ / UC / US | Какие вызовы есть; успех и отказ; method/URL, если уже заданы |
| Словарь данных / доменная модель / глоссарий | Поля, типы, enum, что скрывать |
| НФТ | Каналы доставки, мощность идентификаторов; SLA — не поля JSON |
| Закрытые `Axxxx` | Важнее предварительного ТЗ |
| ТЗ / спецификация стека | Host и протоколы; стек сверх источников не выдумывай |
| Существующий `openapi.yaml` | Режим обновления: база правок, не шаблон для копии |

Правила:

1. Не выдумывай endpoint’ы, поля, коды ошибок и каналы «для полноты».
2. Не кодируй неутверждённые числа как `minimum` / `maximum` / длительности / лимиты экземпляров / размер выборки. Нет числа в источнике — вопрос с рекомендацией или пропуск ограничения, не «типичный REST-лимит».
3. Факт отдельно от рекомендации. Спорное — в YAML как **допущение аналитика** (пометка в `info.description` или в описании поля: рекомендация, не утверждено) **и** вопрос заказчику с тем же текстом. Не выдавай допущение за продуктовое решение. Не блокируй запись YAML ожиданием ответа, **кроме** случая §0 (нельзя выбрать даже набор операций).
4. Не отдавай клиенту то, что требования скрывают.
5. Соблюдай MVP / scope. Post-MVP и «на усмотрение» в `paths` не тащи, пока пользователь явно не включил их в scope.
6. `servers.url` — адрес **API-сервера** (существующего или будущего), не адрес просмотрщика документации. Если бэкенда нет — одна фраза в `info` и в README: Try it out к этому URL сейчас не подключается.

Если логина в источниках нет — в корне спецификации `security: []`. Иначе линтеры часто падают с «security not defined». Если в источниках есть схема аутентификации — опиши `components.securitySchemes` и ссылки на операциях, не оставляй пустой `security` «на всякий случай».

## 2. Что считать API-операцией

**Не** превращай каждое FR и каждый UC в элемент `paths`.

HTTP-endpoint в `paths` нужен, когда актор **вызывает систему по HTTP**, и без этого вызова сценарий не выполняется. **Method и URL** бери из источников (в т.ч. пометки вида `GET /path`). Если поведение есть, а method/URL нет — **открытый вопрос с рекомендацией**, path не выдумывай.

Сообщение канала реального времени — это **не** отдельный REST-метод. Его описывают схемы кадров и handshake (§4). Кадры, заданные через §4, **входят в контракт**: их нельзя одновременно числить omitted.

**Не** делай отдельный HTTP-метод, если это:

- только UI / локальные настройки клиента, бэкенд не участвует;
- внутренний расчёт без выдачи клиенту;
- следствие уже описанной операции (сервер сам шлёт событие после мутации);
- данные, которые клиенту запрещены;
- фоновые воркеры, очереди, out-of-band (email и аналоги) без явного HTTP-контракта.

В `info.description` как **omitted** перечисли только то, чего **нет в этом контракте вообще**: UI-only, скрытые данные, post-MVP вне scope, non-HTTP без handshake/кадров. Не маскируй такие сценарии молчаливым отсутствием path. Не пиши в omitted кадры, которые уже описаны через §4.

Если источники разделяют каналы (REST = создание и чтение; realtime = мутации активного объекта), **не** описывай успешный REST для мутации, разрешённой только на другом канале. Если FR явно требует **отказать** при доставке не тем каналом — это отдельная HTTP-операция, чей ожидаемый исход — **4xx**, а не 2xx.

## 3. HTTP-операция в `paths`

Для каждой **HTTP**-операции:

1. Метод и URL из источника (§2). Префикс версии — только если он есть в источниках.
2. Вход: path / query / `requestBody` + JSON Schema: поля, типы; `required` — только у свойств, обязательных по источникам (пустой `required` «для галочки» не добавляй). На телах запросов — `additionalProperties: false`, если источники не разрешают расширение и это не меняет смысл контракта. Тело у GET/HEAD **не** добавляй. У POST/PUT/PATCH `requestBody` пиши **только если** источники задают тело; пустой POST без полей — тело не выдумывай. `multipart` — только если так в источнике.
3. `responses`: **5xx** всегда (хотя бы общий внутренний сбой). **2xx** — только если есть успешный **HTTP**-исход (не путать с `101` handshake, см. §4). **4xx** — только **осмысленные** по источникам: валидация входа, бизнес-правило, права (`401`/`403`), отсутствие ресурса (`404`). Не добавляй декоративный `400`, если клиентской ошибки в FR/UC нет. Операция «всегда отказ» (не тот канал) — канон 4xx; не добавляй фиктивный 2xx, пока выбранный линтер это не требует. Если линтер без 2xx падает — 2xx с явным текстом, что канонический исход — 4xx, и канон остаётся 4xx. Upgrade WebSocket — §4.
4. Переиспользуемые модели — `$ref`. Помимо `schemas` / `examples` используй `components.parameters`, `components.responses`, `components.securitySchemes` — **только если это есть во входе**. Колбэки исходящего HTTP: в **3.0.x** — `callbacks` у операции; корневые `webhooks` — **только OpenAPI 3.1.x** и только если во входе есть входящий HTTP на сервер. В документ 3.0.3 поле `webhooks` не пиши. После удаления или замены `$ref` убери неиспользуемые компоненты.
5. `summary` (EN), `operationId` (стабильный, латиница), `tags` по смысловым группам из источников.
6. Типы как в словаре данных. Производное поле в **ответе** допустимо, если FR его требует. В **запросе** не дублируй производное, если канон — исходные атрибуты.
7. В `description` операции — трассировка к ID источников (`FT-…`, `UC-…`, `US-…` или `x-traceability`), **без выдуманных ID**. Нет ID — не выдумывай, сошлись на имя сценария из файла.

Ошибки: одна схема (как минимум машиночитаемый `code` и человекочитаемый `message`; `details` — только если есть в источниках). Бизнес-конфликт — **конкретный** 4xx со своим кодом, не пустой общий `Conflict` / одна «универсальная» ошибка на все случаи. Состав полей и имена кодов — из FR, если заданы; иначе рекомендация в YAML (пометка «не утверждено») и вопрос §6.

Examples: согласованы со схемой; **без** паролей, секретов, ключей, токенов, PAN/CVV и персональных данных. Нейтральные placeholders (вымышленное имя, адрес в зоне `.test`). Скрытое по FR в примеры тоже не клади.

## 4. Канал реального времени (OpenAPI 3.0.3)

3.0.3 **не описывает** кадры WebSocket. Если канал есть в источниках:

- в `paths` — один `GET` handshake (upgrade);
- канон успеха канала: **`101`**; **5xx** на handshake — всегда; **4xx** — только если источники задают отказ handshake (иначе не выдумывай 400);
- если линтер требует 2xx на операции — допустим 2xx с явным текстом, что канон успеха — `101`; не подменяй handshake успешным REST-телом «как будто кадр уже пришёл»;
- кадры клиента и сервера — `components.schemas` + расширение `x-websocket` на этой операции (`$ref` на схемы) + примеры без PII/секретов (`x-websocket` — vendor extension, не часть стандарта 3.0.3; предупреждение линтера об неизвестном `x-*` не блокер);
- прикладные ошибки после upgrade — кадр/схема ошибки, **не** подмена HTTP 4xx для каждого кадра;
- в `info.description` — какие `type` шлёт клиент и сервер (это описание контракта, не omitted); идемпотентность — только если есть в FR/`Axxxx`.

Не пиши второй артефакт AsyncAPI, пока пользователь явно не попросил.

## 5. Swagger UI и ReDoc

В режимах **создание**, **обновление** и **только проверка** спецификация без проверяемого просмотра **не сдана** (гейт §8, пункт 12). Режим **только запуск** — поднять или напомнить URL; полный гейт §8 не гоняй.

1. Подними Swagger UI и ReDoc локально (для проверки HTTP 200 это допустимо из терминала агента). Заказчик открывает **свой** браузер, не Simple Browser / предпросмотр IDE (localhost там часто «открывается» и не показывается). Не выдавай процесс из терминала агента в чате за видимое окно документации.
2. Порты по умолчанию: Swagger **8080**, ReDoc **8081**. Если заняты — следующие свободные. Фактические URL: в режимах создание/обновление — в README/инструкции, если раздела не было или порты сменились относительно уже записанных; в **только запуск** — в чате, README не переписывай ради портов.
3. `servers.url` на порт просмотрщика **не** меняй: это другой процесс.
4. Launcher: если в проекте уже есть способ открыть docs — не создавай второй с нуля; в создании/обновлении обнови порты в инструкции, только если они сменились и режим не «только запуск». Если способа нет (режим создание) — минимальный скрипт + раздел в README. Формат скрипта — как принято в репозитории, не обязательно `.bat`.
5. Проверка: HTTP 200 на обе страницы; в HTML есть бандл Swagger и ReDoc; YAML с того же origin начинается с `openapi:`. После правки YAML перечитай served-файл: если это старая копия — перезапусти просмотрщики. Не умеешь поднять просмотрщики (нет рантайма) — пункт 12 красный, не подменяй его «откроют сами».

## 6. Вопросы заказчику

Этот прогон **фиксирует** JSON-контракт. Не оставляй «решится потом при API».

Спрашивай только то, чего нет в источниках и что меняет схему (в т.ч. method/URL, required, enum, лимиты, набор 4xx). Каждый вопрос — с **рекомендацией**. Ту же рекомендацию запиши в YAML как черновик-допущение. Не жди ответа, чтобы закончить файл, если набор операций уже ясен.

Не переспрашивай закрытые `Axxxx`. Типичные пробелы: имена кодов отказа, округление десятичных, сериализация даты и длительностей, нужен ли второй HTTP-снимок, если тот же снимок уже уходит по realtime.

Перенос в `answers-project.md` — только после явного «контракт принят» / согласия с рекомендациями, не автоматически в конце написания YAML.

## 7. Порядок (создание / обновление)

Не переставляй шаги 1–6. Шаг 7 — **единственный** допустимый возврат: не больше чем к шагам 4–5 и только в пределах лимита §8.

1. Источники §1 (стоп — см. §0). Режим **обновление** — читай текущий YAML и правь его.
2. Таблица отбора: UC/FR → HTTP-операция / не операция / кадр realtime (кадр — не omitted, если идёт в §4). Кратко в чате; в `info.description` — omitted по §2 и список realtime-`type` по §4.
3. Запись YAML (§3–§4).
4. Линтер спецификации: если в проекте уже есть команда проверки OpenAPI — её; иначе валидатор OpenAPI 3.0.x (схема и `$ref`). «Просмотрел глазами» пункт 10 не закрывает. Ошибки валидности исправь **до** просмотрщиков. Неиспользуемые `components` после смены `$ref` удали. Предупреждения «`servers` = localhost» и «нет license» не блокер, если host в источниках локальный. Неизвестный `x-*` (в т.ч. `x-websocket`) не блокер.
5. Просмотрщики §5; порты в README, если сменились или раздела ещё не было (не в режиме только запуск).
6. Двойная сверка: (а) lint + preview; (б) YAML ↔ ФТ/UC/US/словарь/глоссарий. Расхождение — **одна** правка YAML или открытый вопрос, не молчаливый компромисс и не цикл «сверяй, пока не идеально». Правка здесь, **до первого** §8, в лимит проходов гейта не входит.
7. Гейт §8 (первый раз). Устранимые находки в YAML → правка → шаги 4–5 → §8 **второй (последний) раз**. Третьего §8 нет — см. лимит в §8.
8. Сообщение §9 — только после прохождения гейта или остановки по лимиту.

Режим **только проверка** шаги 1–3 не повторяет с нуля: существующий YAML → шаг 4 (линтер) → шаг 5 при необходимости → §8; правки — в том же файле, если это не «только отчёт».

Не коммить и не пиши в память агента без явной просьбы. Не реализуй бэкенд в этом запуске.

---

## 8. Гейт

Пока пункты не выполнены, не пиши «готово» — кроме остановки по лимиту ниже. Открытые вопросы заказчику — **допустимый** исход, если они не спрятаны в YAML как утверждённые факты.

**Лимит:** чек-лист §8 выполняется **не больше двух раз** за запуск.

1. Первый раз — после записи YAML (создание/обновление) или сразу по существующему файлу (только проверка).
2. Если есть находки, которые закрываются правкой YAML — исправь, повтори шаги §7.4–§7.5, затем второй (последний) раз §8.
3. Третий раз §8 **запрещён**. После второго прохода красные пункты — в §9 как блокеры / открытые вопросы, не «готово». Не запускай второй проход, если первый чистый.

«Только отчёт без правок»: один проход, без правки YAML.

| # | Критерий |
| --- | --- |
| 1 | Не каждое FR/UC стало `paths`; отбор по §2; omitted — только то, чего нет в контракте; realtime-кадры из §4 в omitted не дублируй |
| 2 | Method/URL у каждой HTTP-операции из источника; выдуманного path нет |

| 4 | POST/PUT/PATCH с телом в источниках имеют `requestBody`; у GET/HEAD тела нет; тела без источника нет |
| 5 | У каждой **HTTP**-операции есть 5xx; 2xx — если есть успешный HTTP-исход (handshake — пункт 6, не фиктивный REST-2xx вместо `101`); 4xx — только осмысленные (§3 п.3), без декоративного 400 |
| 6 | Handshake realtime (если канал в источниках): есть `101` и 5xx; 4xx — только по источникам; кадры — схемы + `x-websocket`, не выдуманный успешный REST вместо кадров |

| 8 | Нет выдуманных enum / min/max / лимитов; допущения помечены; бизнес-4xx с конкретным кодом, не пустой Conflict |
| 9 | Трассировка к FR/UC/US в `description` операций без выдуманных ID |
| 10 | Линтер: ошибок валидности нет; неиспользуемых components после `$ref` нет |
| 11 | YAML сверен с ФТ/UC/словарём/глоссарием; mismatch исправлен или вынесен в вопрос |
| 12 | Swagger и ReDoc отдают 200; YAML с них читается и соответствует файлу на диске (режим **только запуск** этот пункт не гоняет как гейт YAML — только проверка §5) |
| 13 | В создании/обновлении порты в README/инструкции совпадают с фактическими. В **только запуск** при расхождении сообщи фактические URL в чате, README не переписывай |
| 14 | В YAML нет полей из другого репозитория; нет второго файла спецификации без спроса; нет выдуманных полей вне источников |

Режим **только запуск:** пункты 1–11 и 14 не перепроверяй как предлог переписать YAML. Не используй пункт 13 как предлог править README.

**Запрещённые отговорки:** «проверка очевидна», «Swagger откроют сами без URL», «2xx/400 нарисую фиктивно по умолчанию», «ещё один проход на всякий случай», «webhooks добавлю в 3.0.3 для полноты».

## 9. Сообщение разработчику

После §8 (создание / обновление / только проверка) или после §5 (только запуск). Кратко, без дубля YAML:

- путь к файлу (create или update существующего); для нового/изменённого без утверждения — `Черновик, требует согласования`; в режиме только запуск — только URL и способ открыть, без статуса контракта;
- список HTTP-операций и что намеренно **не** стало endpoint’ом (omitted); realtime-кадры — отдельно, не как omitted;
- URL Swagger и ReDoc; напомнить обычный браузер, не предпросмотр IDE;
- гейт §8 пройден или остановлен по лимиту (почему); для только запуска — что гейт YAML не гонялся;
- какие вопросы ждут ответа (рекомендации уже в YAML как допущения).

Не утверждай контракт сам. Не запускай другие QC-скиллы без согласия.

## 10. Типичные ошибки

| Ошибка | Как правильно |
| --- | --- |
| Сообщить «готово» до §8 | Сначала гейт, потом §9 |
| `webhooks` в OpenAPI 3.0.3 | 3.0.x — `callbacks`; `webhooks` только в 3.1.x |
| Кадры WS в `paths` как REST и в omitted | Handshake + `x-websocket`; omitted — только вне контракта |
| Фиктивный 2xx/400 «чтобы было» | 2xx/4xx по исходу в источниках; 2xx из-за линтера — с явной оговоркой |
| Второй `openapi.yaml` «чтобы не трогать старый» | Один файл; нет файла при проверке — пробел |
| Третий проход §8 | Два выполнения чек-листа; дальше блокеры в §9 |
| `required` / `$ref` «для галочки» | `required` по источникам; `$ref` на переиспользуемых моделях |
| `servers.url` = порт Swagger | URL API-сервера, не просмотрщика |
| Simple Browser как проверка docs | HTTP 200 + URL для обычного браузера |
| `Axxxx` в том же запуске, где YAML ещё черновик | Сначала явное принятие контракта |

## Red flags — остановись

- Endpoint или path, которого нет в источниках
- Поле `webhooks` при `openapi: 3.0.x`
- Гейт §8 не выполнялся в этой сессии после записи YAML
- Сообщение разработчику до повторной проверки после правок гейта
- Третий проход гейта в том же запуске
- Режим «только запуск», но YAML или README переписаны
