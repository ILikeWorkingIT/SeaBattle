# Техническое задание по ГОСТ 34.602-89

Универсальный скилл технического писателя (роль `tech-writer`, команда `/gost-3460289`). Опирайся только на факты **репозитория, в котором выполняется скилл**; не подставляй факты из чужих репозиториев, примеров обучения или прошлых чатов.

## Когда применять

- Создать или обновить ТЗ на создание автоматизированной системы по ГОСТ 34.602-89.
- Команда `/gost-3460289`.
- Запросы: «ТЗ по ГОСТ», «ГОСТ 34.602», «техническое задание на АС», «приведи к ГОСТ-стилю».

## Когда не применять

- Детальные ФТ / НФТ / US / UC — точечные скиллы (`/ft`, `/nft`, `/us`, `/uc`). ТЗ **ссылается** на них, не дублирует таблицы целиком.
- Vision & Scope — `/vision`.

## Режимы

Отдельной подкоманды нет. Выбери режим по запросу:

| Режим | Когда | Действие |
| --- | --- | --- |
| **Создание** | Нет файла ТЗ или «напиши ТЗ с нуля» | Собрать из источников репозитория; выдать документ v1.0 |
| **Реструктуризация** | Есть черновик, «приведи к ГОСТ» | Выровнять разделы 1–9; вынести лишнее в приложения |
| **Стилизация** | «Официальный стиль», «формально» | Переформулировать в императив ГОСТ без смены смысла требований |
| **Аудит** | «Проверь по ГОСТ», аудит без правок | Чеклист § «Гейт перед сдачей»; отчёт в чат; файл ТЗ не менять без согласия. Полный цикл создания / реструктуризации / стилизации **не** запускать |
| **Перенос ответов** | Закрытые Q&A в чате по ТЗ | Правки файла; закрытые пары — в `requirements/answers-project.md` с кодом `TZ` (если в репозитории ведётся база ответов по `rule-answers-project.mdc`) |

## Результат

Единый файл Markdown (если пользователь не указал путь — `artifacts/tz-gost-<код>.md`, где `<код>` — условное обозначение системы латиницей, например `001`).

Статус в шапке:

- `Черновик, требует согласования` — до явного согласования заказчиком;
- `Согласовано` — после явной фразы **«согласую ТЗ»** / **«принимаю техническое задание»** (или эквивалент без слова «утверждаю»).

**Не путать** с утверждением этапа MAS («утверждаю» / «принимаю этап» → `Stage: … APPROVED` в `pm-state.md`, если в репозитории есть MAS). Согласование ТЗ **не** ставит APPROVED этапа.

В `.md` **не** использовать обёртку ` ```text ` … ` ``` ` (см. `rule-structure.mdc` в проекте, если правило есть).

После создания файла при необходимости обнови упоминание шаблона ТЗ в `rule-structure.mdc` и `documentation/project-structure-v1-1.md` проекта, если такой шаблон ещё не описан.

## Источники (только факты репозитория)

Читай в порядке приоритета (не выдумывай):

1. Закрытые ответы заказчика (`requirements/answers-project.md`, коды `Axxxx` или аналог) — при конфликте важнее предварительного ТЗ.
2. Согласованные пакеты: ФТ, НФТ, US, UC, доменная модель, словарь данных, глоссарий.
3. Vision & Scope или аналог границ продукта.
4. Предварительное ТЗ / спецификация в `documentation/`.
5. Конфигурация проекта, README, архитектурные материалы — для стека и интеграций.

Не читай архивные папки без явного `@`. Не переноси чужой репозиторий.

Если источников мало — помечай допущения и выноси открытые вопросы в раздел **«Открытые вопросы»** (см. § «Приложения») или в чат с рекомендацией.

## Обязательная структура по ГОСТ 34.602-89 (п. 2.1)

Разделы **в указанном порядке**. Нумерация документа должна соответствовать этому порядку (п. 3.1 стандарта).

| № | Раздел ГОСТ | Содержание (минимум) |
| --- | --- | --- |
| — | Титульный блок | Заказчик, разработчик, вид АС, объект автоматизации, обозначение документа, «Действует с …» |
| 1 | Общие сведения | Наименование; шифр темы/договор; заказчик и разработчик; документы-основания с датами; плановые сроки; финансирование; порядок предъявления результатов |
| 2 | Назначение и цели создания системы | Назначение; вид деятельности; объекты автоматизации; цели с измеримыми критериями |
| 3 | Характеристика объектов автоматизации | Сведения об объекте; условия эксплуатации и среды; границы системы |
| 4 | Требования к системе | 4.1 — в целом; 4.2 — к функциям; 4.3 — к видам обеспечения |
| 5 | Состав и содержание работ по созданию системы | Стадии, результаты, исполнители |
| 6 | Порядок контроля и приёмки системы | Виды испытаний; критерии приёмки; порядок утверждения |
| 7 | Подготовка объекта автоматизации к вводу в действие | Перечень мероприятий и исполнителей |
| 8 | Требования к документированию | Перечень документов; требования к оформлению |
| 9 | Источники разработки | Перечень использованных материалов |
| — | Приложения | По необходимости (см. § «Приложения»); история изменений — только приложение Ж |
| — | Лист согласования | «Составили» / «Согласовано», подписи, дата |

Разделы «Структура данных», «Архитектура», диаграммы — **не** подменяют разделы 1–9; оформляй их **приложениями** (п. 2.2 ГОСТ допускает дополнительные приложения).

**Глоссарий:** отдельное приложение «Термины и определения» — **рекомендуется**, но **не обязательно** по ГОСТ 34.602-89. Достаточно краткой таблицы в приложении и ссылки на полный глоссарий проекта, если он есть.

## Раздел 4.1 — подразделы (п. 2.6.1 ГОСТ)

Включай применимые пункты; для неприменимых — явная формулировка «не устанавливаются» с обоснованием:

1. Требования к структуре и функционированию (подсистемы, связи, режимы, смежные системы, диагностирование, перспективы развития).
2. Численность и квалификация персонала; режим работы.
3. Показатели назначения (количественные нормы из НФТ или ТЗ).
4. Надёжность (в т.ч. аварийные ситуации и требуемое поведение).
5. Безопасность (для ПО на ПК часто «не распространяются» — указать явно).
6. Эргономика и техническая эстетика.
7. Транспортабельность (для стационарных АС часто «не применимо»).
8. Эксплуатация, ТО, ремонт, хранение.
9. Защита информации от НСД.
10. Сохранность информации при авариях.
11. Защита от внешних воздействий.
12. Патентная чистота.
13. Стандартизация и унификация.
14. Дополнительные требования.

## Раздел 4.2 — функции (п. 2.6.2 ГОСТ)

Для каждой подсистемы или группы функций:

1. Развёрнутые формулировки **«Система должна…»** / **«не допускается…»** (см. § «Стиль ГОСТ»).
2. Ссылки на ID требований проекта (FT-xxx и аналог), если пакет ФТ есть.
3. **Временной регламент** (последовательность, параллельность, таймауты).
4. **Критерии отказа** по ключевым функциям (таблица или перечень).
5. Очередь внедрения: для MVP — «вся функциональность вводится в первой очереди», если иное не задано.

Не копируй в ТЗ полные таблицы ФТ — дай сводку и отсылку к приложению А.

## Раздел 4.3 — виды обеспечения (п. 2.6.3 ГОСТ)

Минимум рассмотреть:

- математическое;
- информационное;
- лингвистическое;
- программное;
- техническое;
- метрологическое;
- организационное;
- методическое.

Для каждого — требования или «не выделяется / не применимо».

## Стиль ГОСТ (обязательно)

Переформулируй разговорные и пользовательские описания в официально-технический стиль.

### Правила

| Было (недопустимо в теле ТЗ) | Должно быть |
| --- | --- |
| «Пользователь может…» | «Система должна обеспечивать возможность…» |
| «Нужно сделать…» | «Система должна…» |
| «Без внешнего сервиса не работает» | «При недоступности … система должна блокировать … и отображать сообщение…» |
| Жаргон, путь к файлам репозитория в каждом абзаце | Нейтральные названия документов; пути — в §9 и приложениях |
| Смешение «защита информации» и конфиденциальности | Разделять: НСД (п. 2.6.1.9) и сохранность/локальность данных (п. 2.6.1.10) |

### Пример преобразования (универсальный)

**Вход (неформально):** «Пользователь может просматривать записи в каталоге, выбирать нужные и оформлять заказ, если есть свободные ресурсы. Администратор может управлять каталогом и формировать отчёты.»

**Выход (ГОСТ-стиль):**

- Система должна обеспечивать отображение перечня записей каталога с атрибутами, установленными требованиями к данным.
- Система должна обеспечивать выбор пользователем записей из перечня.
- Система должна обеспечивать оформление заказа при наличии свободных ресурсов; при их отсутствии оформление заказа не допускается.
- Система должна обеспечивать администратору функции управления каталогом, учётными записями (если предусмотрены) и формирования отчётов о деятельности.

Подставляй **факты из источников репозитория**, не копируй пример дословно.

### Императивные конструкции

- «Система должна…»
- «Система не должна…»
- «… не допускается»
- «… устанавливается равным …»
- «Требования … не распространяются на … в связи с …»

## Приложения (рекомендуемый состав)

| Приложение | Содержание |
| --- | --- |
| А | Перечень функциональных требований (ссылка на полный файл ФТ) |
| Б | Перечень нефункциональных требований |
| В | Термины и определения (кратко; ссылка на глоссарий) |
| Г | Структура данных (если есть доменная модель / словарь данных) |
| Д | Архитектура системы |
| Е | Схемы взаимодействия (Mermaid и т.п.) |
| Ж | История изменений документа (версия, дата, описание) — **единственное** место истории; отдельного раздела вне приложений не создавать |

**Открытые вопросы** — не приложение: отдельный раздел **после §9 и перед приложениями** (или в конце черновика), только пока вопросы не закрыты; при согласовании ТЗ удалить или оставить пустым с пометкой «открытых вопросов нет».

## Гейт перед сдачей (самопроверка)

Перед сообщением пользователю о завершении проверь:

**Структура ГОСТ**

- [ ] Есть все 9 разделов в порядке п. 2.1.
- [ ] §4.1 содержит применимые подпункты п. 2.6.1.
- [ ] §4.2 содержит регламент, критерии отказа, формулировки «Система должна».
- [ ] §4.3 покрывает виды обеспечения п. 2.6.3.
- [ ] Разделы 5–8 не свёрнуты в один подпункт без необходимости.
- [ ] Титул и приложение Ж (история изменений) присутствуют.

**Стиль**

- [ ] Нет доминирующих «пользователь может» в требованиях.
- [ ] Нет неоговорённых «достаточно», «быстро» без метрик.
- [ ] Статус черновика, пока нет явного «согласую ТЗ» / «принимаю техническое задание»; фраза «утверждаю» этапа не использована для статуса ТЗ.

**Содержание**

- [ ] Все функции и нормы из источников отражены или явно вынесены в «вне scope».
- [ ] Нет выдуманных фактов.
- [ ] Если в НФТ есть требования к оборудованию: стенд измерения и минимальная конфигурация не смешаны.
- [ ] Глоссарий не выдаётся за обязательное приложение по ГОСТ без пометки.

**Проект**

- [ ] Нет имён, путей и артефактов **чужого** проекта.
- [ ] ID требований проекта согласованы с файлами ФТ/НФТ.

При режиме **Аудит** выдай в чат таблицу: недостающие подпункты; ошибки структуры и стиля; противоречия с ФТ/НФТ; рекомендации по исправлению.
