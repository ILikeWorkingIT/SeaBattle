# Контроль качества User Stories и Use Cases

Универсальный скилл системного аналитика. Не подставляй факты, термины, роли и правила конкретного проекта. Работай только с файлами **текущего** репозитория и явными вводными пользователя.

Не путай с контролем ФТ/НФТ (`skill-quality-control-ft-nft` / `/qc-ft-nft`): этот скилл проверяет пакет US/UC. При находке «US/UC ↔ ФТ» фиксируй её здесь; правку таблиц ФТ/НФТ не делай молча — предложи `/ft` / `/nft` / `/qc-ft-nft` после ответов.

## Результат

1. Отчёт в `reports/incompatibility-us-uc.md` (если пользователь не указал иной путь) со статусом `Черновик анализа, требует согласования`.
2. В отчёте — **один** список находок. Вопрос или исправление — **в той же строке**, не дублируй отдельным блоком Q-/F-.
3. Краткий итог проверки также занеси в реестры пакета (если они есть): `us-registry.md` и/или реестр UC (часто `list-uc.md`) — дата, счётчики по серьёзности, ссылка на отчёт.
4. В чат — краткое резюме: число проблем по приоритетам, критичные ID, путь отчёта. Не дублируй всю таблицу.

Пока заказчик не ответил — **не меняй** файлы US/UC (и связанные роли/реестры), кроме явной просьбы «исправь сразу» или согласия на конкретные правки. Исключение: если пользователь в том же запросе явно просит исправить найденное — правь только согласованные пункты.

## Входные данные

Прочитай (если есть в проекте):

- папка User Stories (по умолчанию `requirements/user-stories/`): файлы `us-*.md`, реестр (`us-registry.md` или аналог), роли/права (`list-us.md` или аналог);
- папка Use Cases (по умолчанию `requirements/use-cases/`): файлы `uc-*.md`, реестр (`list-uc.md` или аналог);
- `requirements/functional-requirements.md` (или актуальный файл ФТ);
- `requirements/glossary.md`;
- `requirements/answers-project.md` — закрытые `Axxxx` (важнее предварительного ТЗ при конфликте);
- скиллы написания пакета: `skill-us`, `skill-uc` (канон формы);
- `.cursor/rules/rule-answers-project.mdc` — формат переноса закрытых ответов;
- `reports/agent-memory.md`, если пользователь просит учитывать накопленные правила.

Не читай архивные папки без явного `@`.

## Шаг 1. Проверка по чек-листу

Выполняй по пунктам. Фиксируй только **подтверждённые** находки. Не выдумывай роли, UX, лимиты и бизнес-правила.

### A. Полнота артефактов пакета

| № | Проверка | Что искать |
| --- | --- | --- |
| A1 | Комплект US | Есть реестр историй, список ролей/прав (если предусмотрен скиллом), файл на каждую US из реестра; ID в имени файла = ID в заголовке |
| A2 | Комплект UC | Есть реестр UC, файл на каждый UC из реестра; ID в имени = ID в заголовке |
| A3 | Именование | Канон репозитория (обычно `us-NNN-*.md` / `uc-NNN-*.md`, ID `US-NNN` / `UC-NNN`) |

### B. User Stories

| № | Проверка | Что искать |
| --- | --- | --- |
| B1 | Формулировка | Есть роль, действие, ценность: `As a` / `I want` / `So that` **или** `Как` / `я хочу` / `чтобы` |
| B2 | Метаданные | После User Story: статус; приоритет MoSCoW (Must / Should / Could / Won't); **Источник**; связанные ФТ/НФТ при наличии. Метаданные не выше блока User Story |
| B3 | AC | Минимум **3** критерия приёмки + отдельно **edge case** (AC4 или явная пометка). Gherkin-ключевые слова обычным текстом, **без** fenced `gherkin` / `text` |
| B4 | Проверяемость AC | Наблюдаемый результат / отказ / состояние; нет «быстро» / «удобно» / «надёжно» без измеримого критерия или отсылки к НФТ / `Axxxx` |
| B5 | Роли | Пользовательские vs системные разделены; имена из глоссария / матрицы прав / ТЗ; нет хаотичных синонимов одной роли в разных файлах; отдельная US от лица системы — только если это явно согласовано |
| B6 | INVEST | В реестре есть сводка INVEST; оговорки объяснены |
| B7 | Источник (атрибуция) | Метки по таксономии `skill-us` (ТЗ / встреча / глоссарий / `Axxxx` / `FT-…` / `сгенерировано агентом` и т.п.). Нет ложных меток `ТЗ`/`Axxxx` на додуманных AC/edge |
| B8 | Scope | Нет незапрошенного расширения; «вне scope» явно в реестре |

### C. Use Cases

| № | Проверка | Что искать |
| --- | --- | --- |
| C1 | Секции Cockburn | Акторы; предусловие; триггер; основной поток; альтернативы; исключения; постусловие; вопросы (ссылка на реестр) |
| C2 | Основной поток | **5–8** шагов; если больше — краткое обоснование в файле |
| C3 | Альтернативы | Ровно **шесть** категорий: (1) некорректные данные; (2) timeout / недоступность; (3) прерывание; (4) недостаточно прав; (5) конкурентный доступ; (6) граничные значения. Ветки `[Шаг N.x]`; у каждой — возврат или завершение. «Не применимо» — только с обоснованием из источников / `Axxxx` |
| C4 | Исключения | Минимум **2** потока исключений; у каждого — возврат или завершение |
| C5 | Один primary | Ровно один основной актор из источников; в предусловии, триггере и основном потоке — тот же primary. Нет суррогата «Пользователь» / «User», если роли нет в источниках |
| C6 | Источники | Поле источников с атрибуцией; додуманные ветки помечены `сгенерировано агентом` |
| C7 | Вопросы | Полный текст открытых вопросов **только** в реестре UC; у каждого — рекомендация; в теле UC — ссылка и ID. Коды вида `UC-NNN-C#` / `UC-NNN-D#` (или канон проекта) |
| C8 | Статусы реестра | В реестре статусы **`готово`** / **`требует уточнения`** (или эквивалент проекта) согласованы с наличием блокирующих вопросов |

### D. Согласованность и качество формулировок

| № | Проверка | Что искать |
| --- | --- | --- |
| D1 | US ↔ UC | Зеркало 1:1 (если так принято) или явное обоснование иной декомпозиции; нет «осиротевших» Must-историй без сценария и наоборот без договорённости |
| D2 | US/UC ↔ ФТ | Поведение в AC/потоках не противоречит согласованным ФТ; пробел «есть в UC/`Axxxx`, нет в ФТ» — находка (предложить `/ft`, не чинить ФТ молча) |
| D3 | Термины | Согласованы с глоссарием; нет бытовых синонимов канонических терминов без записи в глоссарий |
| D4 | Закрытые ответы | `Axxxx` важнее предварительного ТЗ; нет устаревших «решение заказчика» / `Qn` при наличии `Axxxx`; конфликт двух `Axxxx` — вопрос, не усреднение |
| D5 | Кодировка / читаемость | Кракозябры, сломанные спецсимволы (`?` вместо `×` / `≠` и т.п.), запрещённый fence ` ```text ` в `.md` пакета |
| D6 | Неопределённые слова | В ценности US и в AC/потоках: «удобно», «быстро», «надёжно», «качественно», «по возможности» и аналоги без критерия |

Приоритет находки:

- **Критичный** — блокирует реализацию, приёмку или однозначное понимание основного потока / AC;
- **Важный** — двойная трактовка, конфликт ролей/акторов, пробел трассировки US/UC↔ФТ, ложная атрибуция источника;
- **Желательный** — стиль, именование файлов, мягкие формулировки без смены согласованного поведения.

Строки «не дефект» в таблицу не тащи.

## Шаг 2. Один список (без дубля)

Собери находки, затем **отсортируй**: Критичный → Важный → Желательный. Внутри приоритета — порядок чек-листа (A → B → C → D).

**Запрещено:** сначала таблица проблем, потом повтор тех же пунктов отдельным блоком вопросов. Заказчик отвечает **один раз**, в таблице.

Таблица отчёта (колонка «ответ» пустая, пока заказчик не заполнил):

| № | приоритет | тип | ID | описание | действие | ответ |
| --- | --- | --- | --- | --- | --- | --- |

**тип** — краткая метка из чек-листа (например `B3 AC`, `C5 primary`, `D2 US↔ФТ`).

**действие** — ровно одно из двух, в этой же ячейке:

1. **Исправление** (данных в источниках достаточно, в т.ч. в `Axxxx`): что менять в каких ID/файлах. Помечай как предложение, не как факт. В US/UC не вноси до согласия (если нет явной просьбы исправить).
2. **Вопрос** (дыры нет в источниках): формулировка + **рекомендация** + зачем нужен ответ («без ответа невозможно …»). Один вопрос на одну дыру.

В конце отчёта кратко напомни: после ответов закрытые пары уйдут в `answers-project.md` (код `US` или `UC` по теме строки; при влиянии на ФТ/НФТ — `FT` / `NFT`).

## Шаг 3. После ответов заказчика

1. Читай ответы из чата **и** из отчёта, если заказчик дописал их в файл.
2. «Согласен» / «да» по рекомендации — внеси правку в соответствующие US/UC/реестры/роли; в источниках поставь `Axxxx`.
3. **Обязательно** запиши закрытые пары вопрос→ответ в `requirements/answers-project.md` по `.cursor/rules/rule-answers-project.mdc` (код `US` / `UC` / при необходимости `FT` / `NFT`; при «согласен» — текст рекомендации). Не оставляй канон ответа только в отчёте.
4. Ответ не на тот пункт — обработай по смыслу и явно напиши, как интерпретировал.
5. Если ответ меняет согласованные ФТ/НФТ — правь через `/ft` / `/nft` и предложи `/qc-ft-nft`; не запускай без согласия.
6. При противоречии двух `Axxxx` — не правь молча: обсуди и жди решения.
7. Обнови отчёт: статус `Обработано`, таблица «как ответы внесены» (включая новые `Axxxx`). Обнови краткий итог в реестрах US/UC.

## Запрещено

- Подставлять детали другого проекта или «типичные» сценарии без источника.
- Выдавать рекомендацию за согласованное требование.
- Менять согласованный пакет US/UC без нового решения заказчика (кроме явной просьбы исправить).
- Оставлять в отчёте только общие фразы без ID.
- Смешивать полный QC с написанием нового пакета «заодно», кроме явного запроса «исправь».
- Дублировать одну находку: таблица + отдельный блок с тем же смыслом.
- Закрывать ответы только в отчёте/US/UC, минуя `answers-project.md`, если база ответов в проекте есть.
- Чинить ФТ/НФТ «по пути» без запроса — только зафиксировать находку и предложить `/ft` / `/nft` / `/qc-ft-nft`.
- Использовать fence ` ```text ` в отчёте и правках `.md`.
