# Контроль качества ФТ и НФТ

Универсальный скилл системного аналитика. Не подставляй факты, термины, пороги и правила конкретного проекта. Работай только с файлами текущего репозитория и явными вводными пользователя.

## Результат

1. Отчёт в `reports/incompatibility-ft-nft.md` (если пользователь не указал иной путь) со статусом `Черновик анализа, требует согласования`.
2. В отчёте — **один** список находок. Вопрос или исправление пишется **в той же строке**, не повторяется ниже отдельным блоком F-/Q-.
3. В чат — краткое резюме: число проблем по приоритетам, критичные ID, путь отчёта. Не дублируй таблицу.

Пока заказчик не ответил — **не меняй** файлы ФТ и НФТ. Правки требований — только после явного согласия / ответов.

**Выбор режима** (отдельной подкоманды нет): нет ответов по строкам отчёта → шаги 1–2, файлы не менять. Есть ответы в чате / в колонке «ответ» / явная просьба их обработать → шаг 3. «Проверь и исправь» в одном запросе: сначала отчёт, сразу правь только пункты типа «Исправление» (в источниках уже достаточно данных); вопросы без ответа не закрывай догадкой. Если в том же сообщении «проверь» и ответы — сначала шаг 3, новый полный аудит не начинай без явной просьбы.

Если пользователь ограничил прогон («только ФТ» / «только НФТ») — проверяй указанный файл; отсутствие второго не считай дефектом неполноты, пока пользователь не просил совместный аудит.

## Входные данные

Прочитай (если есть в проекте):

- файл ФТ (по умолчанию `requirements/functional-requirements.md`);
- файл НФТ (по умолчанию `requirements/non-functional-requirements.md`);
- `requirements/answers-project.md` — закрытые решения `Axxxx` (важнее предварительного ТЗ при конфликте);
- глоссарий, ТЗ/спецификацию, скиллы `/ft` и `/nft` проекта;
- `.cursor/rules/rule-answers-project.mdc` — формат переноса закрытых ответов;
- `reports/agent-memory.md`, если пользователь просит учитывать накопленные правила.

Не читай архивные папки без явного `@`.

**Канон формы, не исполнение:** скиллы `/ft` и `/nft` (`skill-ft`, `skill-nft`) читай **только как образец формы**. Не выполняй их алгоритмы написания, не вызывай `/ft` / `/nft` «заодно» и не начинай этот QC повторно только потому, что в скилле написания сказано «предложи `/qc-ft-nft`».

## Шаг 1. Проверка по чек-листу

Выполняй по пунктам. Фиксируй только подтверждённые находки; не выдумывай пороги и бизнес-правила.

| № | Тип проблемы | Что искать |
| --- | --- | --- |
| 1 | Противоречие | ФТ, которые нельзя выполнить одновременно; НФТ с взаимоисключающими порогами; конфликт двух `Axxxx` без решения пользователя; усреднение / «сглаживание» противоречий источников без явного решения |
| 2 | Дублирование | Разные ID с одним смыслом; ФТ + НФТ, где НФТ лишь повторяет поведение без метрики приёмки; дубликаты смысла в `answers-project.md` при разных `Axxxx` |
| 3 | Конфликт ФТ↔НФТ | Поведение ФТ несовместимо с нормой качества НФТ (например, разные пороги на один сценарий) |
| 4 | Смешение уровней | В ФТ — стек, протоколы, СУБД, UI-решения без `Axxxx` / явного решения в источниках; в НФТ — чистое поведение без метрики |
| 5 | Неполнота | Сценарии, ветки, граничные случаи, на которые нет ФТ/НФТ и нет явного «вне scope» |
| 6 | Неопределённые слова | «быстро», «надёжно», «удобно», «качественно», «как правило», «при необходимости», «максимально» (оценочное), «обычно», «иногда», «и/или», «и другие», «по возможности», «современный», «гибкий», «интуитивно понятный», «отзывчивый» без измеримого критерия |
| 7 | Форма требования | Атомарность; верифицируемость; есть источник; есть приоритет. В источнике — `Axxxx` и/или ТЗ, а не голое «решение заказчика». Генерация агента без метки `сгенерировано агентом`. В НФТ в «Условии» нет статуса `факт` / `уточнить` / `сгенерировано агентом`. Не путать `Axxxx` с правилами измерения НФТ `MR-NN` |

### Нормы формы (кратко)

**ФТ:** ID `FT-XXX`; название = глагол + существительное; канон «[Субъект] должен [глагол] [объект] [при условии]»; источник (`Axxxx` / ТЗ); MoSCoW.

**НФТ:** ID `NFT-XXX`; характеристика качества (например ISO/IEC 25010:2023); SMART-формулировка с порогом; метрика (имя, единица, агрегация, выборка); условие замера; источник (`Axxxx` / ТЗ / ФТ). Без числа / единицы / способа сбора — это не метрика. Если в источниках нет порога — вопрос с рекомендацией, не «факт из ТЗ». Правила измерения — `MR-NN` в файле НФТ, не путать с `Axxxx`.

Дублирование ФТ и НФТ допустимо, если НФТ — **измеримая приёмка** поведения ФТ; иначе пометь как дубль.

## Шаг 2. Один список (без дубля)

Собери находки, затем **отсортируй**: Критичный → Важный → Желательный. Внутри приоритета — порядок чек-листа (противоречие, дубль, конфликт ФТ↔НФТ, смешение уровней, неполнота, неопределённые слова, форма).

**Запрещено:** сначала таблица проблем, потом повтор тех же пунктов как F-001 / Q-001 с «Контекстом». Заказчик должен отвечать **один раз**, в таблице.

Таблица отчёта (колонка «ответ» пустая, пока заказчик не заполнил):

| № | приоритет | тип | ID | описание | действие | ответ |
| --- | --- | --- | --- | --- | --- | --- |

**действие** — ровно одно из двух, в этой же ячейке:

1. **Исправление** (данных в источниках достаточно, в т.ч. в `Axxxx`): что менять в каких ID. Помечай как предложение, не как факт. В ФТ/НФТ не вноси до согласия, **если нет** явной просьбы «исправь».
2. **Вопрос** (дыры нет в источниках): формулировка вопроса + рекомендация аналитика + зачем это нужно («без ответа невозможно …»). Один вопрос на одну дыру.

Не делай отдельный раздел «Исправления» и отдельный «Вопросы заказчику». Не нумеруй те же пункты второй раз как F-xxx / Q-xxx.

Приоритет:

- **Критичный** — блокирует реализацию или приёмку;
- **Важный** — двойная трактовка или лишняя работа;
- **Желательный** — формулировка без смены согласованного поведения.

Строки «не дефект» (например оценочное слово на самом деле термин) в таблицу не тащи.

В конце отчёта кратко напомни: после ответов закрытые пары уйдут в `answers-project.md` (код `FT` или `NFT` по теме строки).

## Шаг 3. После ответов заказчика

1. Читай ответы из чата **и** из отчёта, если заказчик дописал их в файл.
2. «Согласен» / «да» по рекомендации — перенеси в ФТ/НФТ (и глоссарий, если термин); в колонке «Источник» поставь `Axxxx`.
3. **Обязательно** запиши закрытые пары вопрос→ответ в `requirements/answers-project.md` по `.cursor/rules/rule-answers-project.mdc` (код `FT` или `NFT` по теме; при «согласен» — текст рекомендации). Не оставляй канон ответа только в отчёте.
4. Ответ не на тот пункт — обработай по смыслу и явно напиши, как интерпретировал.
5. Недостающий перечень / порог не выдумывай: оставь вопрос открытым или зафиксируй консервативную интерпретацию и пометь её.
6. При противоречии двух `Axxxx` — не правь молча: обсуди и жди решения (пропуски номеров допустимы).
7. Обнови отчёт: статус `Обработано`, таблица «как ответы внесены» (включая новые `Axxxx`).
8. **Не** предлагай и **не** запускай повторный `/qc-ft-nft` «на всякий случай» после этого переноса. Новый QC — только по явной просьбе пользователя или если сверх согласованных пунктов этого отчёта появились **новые** требования.

## Запрещено

- Подставлять детали другого проекта или «типичные» SLA без источника.
- Выдавать рекомендацию за согласованное требование.
- Менять согласованные ФТ/НФТ без нового решения заказчика.
- Оставлять в отчёте только общие фразы без ID.
- Смешивать проверку качества с написанием новых ФТ/НФТ «заодно», кроме явного запроса «исправь».
- Дублировать одну находку: таблица + отдельный блок F-/Q- с тем же смыслом.
- Закрывать ответы только в отчёте/ФТ/НФТ, минуя `answers-project.md`.
- Путать `Axxxx` с правилами измерения НФТ `MR-NN`.
- После шага 3 предлагать или запускать второй круг `/qc-ft-nft` по тем же правкам.
