# Описание мультиагентной системы (MAS) в Cursor v5

## Введение и Философия системы

Мультиагентная Система (MAS) является универсальной модульной надстройкой над средой разработки Cursor. Система полностью независима от конкретного технологического стека проекта: язык программирования, фреймворки и окружение определяются динамически ПМ-агентом при первом запуске путем полного сканирования папки `documentation/`. Вся структура папок, файлов, названий скиллов и команд унифицирована для всех проектов автора.

**Ключевые принципы:**

- **GitHub как единственный трекер задач:** Вся работа с бэклогом, задачами и репозиторием ведется исключительно через коммиты, GitHub Issues, Milestones и Projects. Любые внешние трекеры (Jira и др.) отсутствуют.
- **Вайбкодинг "Маленьких рабочих кусков" (Slice-Driven Development):** Система ориентирована на пошаговую генерацию рабочего кода микро-срезами по чеклисту. Написание требований выступает лишь как готовый фундамент. Основной упор сделан на итеративный производственный цикл внутри MAS под управлением ПМ.
- **Разделение именования:** Для точечного функционала используется формат `skill-<имя>.md`, для базовых агентов — `skill-agent-<имя>.md`. Аналогично для правил: `rule-*.mdc` (глобальные) и `role-*.mdc` (ролевые).

## 1. Архитектура и Механизмы взаимодействия

Управление системой в Cursor реализуется через синергию четырех слоев:

1. **Cursor Custom Agents (Modes):** Изолированные системные промпты, задающие поведение, стиль мышления и персональный манифест роли.
2. **Охранные правила (`.cursor/rules/role-*.mdc`):** Автоматически включаемые контекстные фильтры, изолирующие видимость файлов для конкретной роли.
3. **Slash-команды (`.cursor/commands/*.md`):** Параметризованные точки входа в этапы и сценарии, запускаемые пользователем в диалоге с ПМ.
4. **Исполнительный слой (`.cursor/skills/`):** Инструкции выполнения задач; PM указывает, какой скилл какую роль исполняет.

**Правила передачи контекста:**

- **PM — единая точка входа:** Пользователь общается **исключительно с ПМ-агентом**. ПМ является главным оркестратором: он анализирует текущий этап, фиксирует входной манифест данных, самостоятельно ставит задачи и управляет контекстом целевых ролей, не заставляя пользователя переходить в другие чаты или вручную вызывать команды.
- **Изоляция через манифесты:** Агенты работают под управлением ПМ и имеют доступ на чтение *только* к файлам из своего `Input Manifest`. Они не читают файлы проекта, которые им не требуются для выполнения поставленной ПМ-ом задачи.
- **Блокирующий Quality Gate:** После выполнения задачи исполнителем, PM автоматически направляет артефакты агенту `anatomist`. Наличие замечаний категорий `critical` или `major` блокирует продвижение дальше. Окончательное утверждение этапа — фраза пользователя «утверждаю» / «принимаю этап» в чате ПМ; ПМ записывает `Stage: <id>: APPROVED` в `reports/pm-state.md` и не ставит эту строку сам.
- **Состояние — Markdown:** Вся координация ведется через прозрачные файлы отчетов (`reports/project-config.md`, `reports/pm-state.md`, `reports/traceability.md`).

## 2. Расширенная структура папок и отчетов

Для обеспечения сквозной прослеживаемости (Traceability) в структуру проекта добавляются следующие файлы управления:

- `reports/navigator.md` — глобальная карта навигации по проекту для ИИ ("с чего начать").
- `reports/project-config.md` — декларация стека, языка, доступных интеграций и окружения (заполняется ПМ-агентом).
- `reports/pm-state.md` — текущий этап, статус ревью, блокирующие ошибки и queue действий.
- `reports/traceability.md` — матрица связей требований (US/UC/FR/NFR/ADR) с конкретными файлами кода и хэшами коммитов (Commit Refs).
- `reports/backlog-state.md` — моментальный снимок бэклога GitHub Issues, дата последней синхронизации и drift.
- `reports/daily/YYYY-MM-DD.md` — дейли-контекст («вчера сделано / открытые задачи / блокеры»).
- `reports/commit-audit/YYYY-MM-DD.md` — аудит кода (изменения в `src/` vs декомпозиция требований).
- `reports/templates/` — копии чистых шаблонов отчетов для быстрого копирования в новый проект:
  - `project-config.template.md`
  - `pm-state.template.md`
  - `traceability.template.md`
  - `backlog-state.template.md`
  - `review-gate-report.template.md` (объединенный шаблон манифеста стадии и отчета критика)
  - `daily-brief.template.md`
  - `commit-audit.template.md`
- `reports/weekly/` — еженедельные дайджесты для демонстрации заказчику.
- `reports/release/` — примечания к релизам (release notes).

## 3. Матрица Ролей и Функционал Агентов

### 3.1. Управленческий и Контролирующий блок

1. **Project Manager (`agent-pm`)**
   
   - *Функционал:* Оркестрация этапов, delivery-менеджмент, управление бэклогом GitHub (`/backlog-sync`), выявление orphan-коммитов (`skill-agent-pm-commit-vs-requirements`), ведение дейли-контекста. Координирует работу всех остальных агентов. Принимает решения через ADR на основе выбора пользователя. Общается с пользователем в ролях разработчика или заказчика.
   - *Манифест:* `reports/`, `documentation/`, `src/` (в режиме чтения для аудита коммитов).

2. **System Analyst (`agent-analyst`)**
   
   - *Функционал:* Разработка глоссария, ФТ, User Stories, Use Cases, генерация диаграмм процессов (BPMN, Mermaid), ведение аналитических протоколов встреч (`/meeting-outcomes`). Vision & Scope не пишет (это tech-writer).
   - *Манифест:* `requirements/`, `documentation/Specification.md`, `diagrams/`.

3. **Software Architect (`agent-architect`)**
   
   - *Функционал:* Проектирование системных компонентов, доменной модели (DDD), ER/NoSQL диаграмм, разработка Sequence-диаграмм, ведение Словаря данных (совместно с Аналитиком) и проектирование контрактов API.
   - *Манифест:* `requirements/domain-model.md`, `requirements/data-dictionary.md`, `requirements/openapi.yaml`.

4. **Technical Writer (`agent-tech-writer`)**
   
   - *Функционал:* Vision & Scope (`/vision`, скилл `skill-vision` → `artifacts/vision-scope.md`); ТЗ по ГОСТ 34.602-89 (`/gost-3460289`, скилл `skill-gost-3460289` → `artifacts/tz-gost-*.md`); internal wiki, пользовательские руководства, API Reference на основе схемы OpenAPI, оформление отчетов заказчику (`weekly-digest-customer-report`).
   - *Манифест:* `requirements/`, `documentation/`, `artifacts/vision-scope.md`, `artifacts/tz-gost-*.md`, публичные интерфейсы `src/`.

5. **Anatomist / Universal Critic (`agent-anatomist`)**
   
   - *Функционал:* Универсальный критик, контроль качества требований и кода. Работает по запросу ПМ-агента через команду `/qc-stage`. Читает `stage-id` из `reports/pm-state.md`, сопоставляет его со списком в `.cursor/list-commands.md` и возвращает ПМ-агенту структурированный отчет качества с чек-листом верификации.
   - *Манифест:* Все папки проекта (строго в режиме `read-only`).

### 3.2. Блок Дизайна, Вайбкодинга и Тестирования

6. **UI/UX Designer (`agent-designer`)**
   
   - *Функционал:* Проектирование интерактивных макетов интерфейса приложения (не сайтов) на технологическом стеке проекта (в этом репозитории — **PySide6**) по команде `/ui-prototyping`. Создает красивый вид, темы, кликабельные контроли без бизнес-логики и генерирует `.bat` лаунчеры для запуска в Проводнике.
   - *Манифест:* `requirements/use-cases/`, `src/frontend/` (тема и макет), конфигурации стилей и тем проекта.

7. **Frontend Developer (`agent-front-developer`)**
   
   - *Функционал:* Написание рабочего клиентского кода GUI по команде `/frontend`. Реализует логику отображения, стейт-менеджмент окон/экранов, обработку клиентских валидаций и интеграцию интерфейсных сообщений. Базируется на прототипе, созданном Дизайнером, переиспользуя его структуру окон и логику лаунчера.
   - *Манифест:* `src/frontend/`, дизайн-система, функциональные требования, готовые наработки из `/ui-prototyping`, `requirements/openapi.yaml`, а также общепроектные конфигурационные файлы среды. Прямой доступ к реализации бэкенда (`src/backend/`) закрыт.

8. **Backend Developer (`agent-back-developer`)**
   
   - *Функционал:* Реализация прикладного слоя и HTTP/WS API по команде `/app-layer`. Пишет бизнес-логику, FastAPI, Redis-сессии, WebSocket, серверный ИИ (heatmap) — только из канона репозитория.
   - *Манифест:* `src/backend/` (`domain/`, `application/`, `infrastructure/`, `presentation/`), `requirements/openapi.yaml`, общепроектные конфигурационные файлы среды. Доступ к прямой верстке GUI закрыт.

9. **QA / Tester (`agent-tester`)**
   
   - *Функционал:* Покрытие кода автотестами по команде `/new-tests`. Прогон наборов тестов по команде `/use-tests` с автоматическим формированием отчета упадков и генерацией очереди багов (`BUG-00X`) в файле `reports/test-run.md`.
   - *Манифест:* `tests/`, `reports/test-run.md`, весь код в `src/` (строго в режиме `read-only` для предотвращения подгонки тестов под баги).

## 4. Жесткие Инварианты Вайбкодинга по Срезам

Чтобы исключить галлюцинации моделей, затирание логики и переполнение контекстного окна Cursor при итерационной кодогенерации, вводятся следующие правила:

- **Правило Атомарного Среза:** Разработка функционала в коде ведется строго по пошаговым кускам, описанным в чеклисте срезов (`reports/checklist.md`). Агенты-разработчики не имеют права писать код для фич из последующих, еще не открытых срезов. Архитектурные пересечения изолируются строгими заглушками (`TODO` / `Mock`).
- **Разделение Слоев в рамках Одного Запроса:** Категорически запрещено изменять UI-компоненты фронтенда и прикладные сервисы бэкенда внутри одного диалогового окна ИИ. Если срез затрагивает оба слоя, работа разбивается на две независимые сессии под контролем ПМ: сначала `agent-back-developer` реализует логику и контракты (`src/backend/`), затем `agent-front-developer` подключает клиент к REST/WebSocket в `src/frontend/`.
- **Тестовый Конвейер под управлением ПМ:** Продуктовый код и код автотестов никогда не генерируются одновременно. Как только разработчик прикладного слоя завершает написание фичи среза, ПМ-агент за кулисами направляет задачу агенту `agent-tester` для покрытия кода тестами и их прогона. Разработчик приступает к багфиксингу только по результатам отчета тестера. Пользователь избавлен от необходимости ручного вызова промежуточных команд тестирования.

## 5. Этапы управления проектом и slash-команды

Каждая **развёрнутая** команда — файл в `.cursor/commands/` с разделами: Цель этапа, Роль-исполнитель, Input manifest, Skill(s), Output artifact(s), Review manifest, Gate checklist, Update traceability.

Канон команд этого репозитория — `.cursor/list-commands.md`. Пункты §5.2–5.3 без файла команды (`/full-cycle`, `/glossary`, `/backlog-sync`, `/commit-audit`, `/daily-brief`, `/meeting-actions`, `/feature-from-code`, `/feature-add`, `/report-weekly`, `/report-presentation`, `/release-notes`) **не имитировать**. Развёрнуты: `/pm`, `/vision`, `/gost-3460289`, `/ft`, `/nft`, `/us`, `/uc`, `/qc-ft-nft`, `/qc-us-uc`, `/ddd`, `/qc-ddd`, `/data-dictionary`, `/diagram-bpmn`, `/diagram-mermaid`, `/openai`, `/ui-prototyping`, `/frontend`, `/app-layer`, `/new-tests`, `/use-tests`, `/qc-stage`, `/pin-memory`.

**5.1. Этапы документации и проектирования (при необходимости PM может менять этапы):**

- `/pm` (PM) -> Инициализация `reports/project-config.md` и `reports/pm-state.md`.
- `/vision` (Tech-Writer) -> Vision & Scope (`artifacts/vision-scope.md`).
- `/glossary` (Analyst) -> Наполнение глоссария (`requirements/glossary.md`).
- `/ft` (Analyst) -> Функциональные требования (`requirements/functional-requirements.md`).
- `/nft` (Architect / Analyst по выбору в config) -> Нефункциональные требования (`requirements/non-functional-requirements.md`).
- `/qc-ft-nft` (Anatomist) -> Проверка функциональных и нефункциональных требований (`reports/incompatibility-ft-nft.md`).
- `/us` (Analyst) -> Реестр User Stories (`requirements/user-stories/US-*.md`).
- `/uc` (Analyst) -> Реестр Use Cases (`requirements/use-cases/UC-*.md`).
- `/qc-us-uc` (Anatomist) -> Проверка US и UC  (`reports/incompatibility-us-uc.md`).
- `/ddd` (Architect) -> Доменная модель (`requirements/domain-model.md`).
- `/qc-ddd` (Anatomist) -> Проверка доменной модели  (`reports/domain-model-review.md`).
- `/data-dictionary` (Analyst / Architect) -> Словарь данных (`requirements/data-dictionary.md`).
- `/gost-3460289` (Tech-Writer) -> Техническое задание по ГОСТ 34.602-89 (`artifacts/tz-gost-<код>.md`; в этом репозитории — `artifacts/tz-gost-34-602.md`).
- `/diagram-bpmn` (Analyst) -> Диаграммы процессов BPMN. Выполняется при необходимости
- `/diagram-mermaid` (Analyst) -> Диаграммы Mermaid. Выполняется при необходимости
- `/release-notes` (Tech-Writer) -> Подготовка релиз-ноутс (`reports/release/`).

**5.2. Операционные команды PM (Delivery Loop):**

- `/backlog-sync` (PM) -> Снимок бэклога GitHub Issues, Projects и Milestones в `reports/backlog-state.md` (last sync, drift).
- `/commit-audit [from..to]` (PM) -> Автоматический обход репозитория, `git log` за окно, маппинг коммитов на ФТ/US/UC по ID в commit message. Поиск orphan-коммитов и drift. Результат в `reports/commit-audit/YYYY-MM-DD.md` и обновление `commit refs` в `reports/traceability.md`.
- `/daily-brief` (PM) -> Агрегирует git за вчера + meeting outcomes + open blockers в файл `reports/daily/YYYY-MM-DD.md`.
- `/meeting-actions <transcript-path>` (PM) -> Извлечение только action items (assignee, due, ref). Параллельно `/meeting-outcomes` (Analyst) пишет аналитический протокол встречи.

**5.3. Сводные и Сценарные команды:**

- `/full-cycle` (PM) -> Последовательный прогон всех включенных в конфигурацию этапов проектирования силами подчиненных агентов. ПМ сам вызывает нужные роли и проводит их через гейты качества. При отсутствии критических замечаний ПМ формирует сводный отчет качества и запрашивает у пользователя APPROVED сразу на весь пакет документов.
- `/qc-stage` (Anatomist) -> Универсальный второй проход с блокирующим гейтом. ПМ-агент вызывает команду скрыто для валидации артефактов. Анатомист считывает текущий `stage-id` из `reports/pm-state.md`, подгружает нужный чек-лист гейта качества и возвращает структурированный отчет для ПМ.
- `/feature-from-code` (Architect + Analyst) -> Автоматический обход репозитория под управлением ПМ и восстановление описания поведения, диаграмм Mermaid C4 и data-model для недокументированного кода (Сценарий S2). На время работы команды ограничения манифестов расширяются для чтения папки `src/`.
- `/feature-add` (PM) -> Анализ фичи, определение изменяемых артефактов, самостоятельное создание связанных дефектов/задач в GitHub Issues с тегами (`epic`, `story`, `task`) через `skill-agent-pm-backlog-management`.
- `/report-weekly` (Tech-Writer) -> Генерация отчета `weekly-digest-customer-report` для заказчика на основе данных из папок `reports/commit-audit/*` и `reports/daily/*`.
- `/report-presentation` (Tech-Writer) -> Генерация слайдов и презентаций по работе системы для заказчика.

## 6. Сценарии как маршруты в Navigator

Система поддерживает 5 универсальных сквозных сценариев. Маршруты описаны в `reports/navigator.md`:

1. **S1 — Новый проект с нуля:** Перенос MAS по §10 (`documentation/mas-description.md`) → `/pm` → заполнение `project-config.md` → этапы документации командами `/ft`, `/nft`, `/us`, `/vision` и др. (без `/full-cycle`; команды delivery-loop в срезе A не развёрнуты).
2. **S2 — Фича в недокументированном коде:** Инициализация через `/pm` в минимальной конфигурации -> ПМ запускает `/feature-from-code` для реверс-инжиниринга требований и архитектуры (с временным доступом к чтению `src/`) -> ПМ делает `/commit-audit [last-3-months]` для посева матрицы связей -> ПМ выполняет `/backlog-sync` для фиксации GitHub Issues -> переход к сценарию S3.
3. **S3 — Фича или изменение в описанном проекте:** Вызов `/feature-add`. PM сам определяет список изменяемых артефактов и отдает их в работу аналитикам и архитекторам, проводя каждый измененный документ через `/qc-stage`. ПМ создает атомарные задачи в GitHub. Далее ПМ запускает конвейер вайбкодинга: бэкендер пишет код среза -> ПМ отдает код тестеру -> после фиксации багов бэкендером ПМ передает срез фронтендеру -> ПМ отдает тестеру на UI-тесты. ПМ рапортует пользователю только о полной готовности всего среза. Перед демонстрацией ПМ через `/commit-audit` проверяет покрытие кода коммитами.
4. **S4 — Отчётность:** Вызов ПМ-ом команд `/report-weekly` или `/report-presentation`. Факты берутся строго из артефактов PM (коммит-аудиты, дейли-брифы), исключая любые "придуманные" ИИ формулировки.
5. **S5 — Режим обычного чата:** Прямое, стандартное взаимодействие пользователя с агентами Cursor. Выбор данного режима осуществляется пользователем в любой момент времени, отключая или ставя на паузу жесткую последовательность оркестрации ПМ.

## 7. Definition of Done этапа (блокирующий гейт)

Правила `role-pm.mdc` и `role-anatomist.mdc` строго блокируют переход ПМ-агента к следующему этапу/срезу, пока не выполнены условия:

1. Выходной артефакт физически создан по правильному пути.
2. Проведен аудит качества через Анатомиста и в корне папки отчета сформирован `review-report.md`.
3. Все найденные ошибки уровней `critical` и `major` полностью устранены (ПМ сам возвращает задачу исполнителю на доработку и гоняет гейт до "зеленого" отчета).
4. Ошибки уровня `minor` занесены в `reports/pm-state.md` как известные ограничения (known issues) или рекомендации.
5. Матрица связей в `reports/traceability.md` полностью обновлена.
6. Пользователь в чате ПМ написал «утверждаю» / «принимаю этап». ПМ записывает `Stage: <id>: APPROVED` в `reports/pm-state.md`. Без этой фразы ПМ строку не ставит и *не имеет права* переходить к новому глобальному этапу или утверждать работу за человека.

## 8. Конфликты ролей и обработка предложений

Если в процессе проектирования или вайбкодинга у подчиненных агентов возникают конфликты архитектурных решений, интерфейсов или логики:

1. Исполнители (например, `analyst`, `architect`, `back-developer`) формулируют свои варианты в виде независимых предложений в файлах `reports/proposal-*.md`, описывая плюсы, минусы и компромиссы (trade-offs).
2. Агент `agent-pm` сводит эти предложения в единую таблицу, но **не принимает решение самостоятельно**. Он пишет краткое резюме для пользователя: *"Выбор за разработчиком/заказчиком"*.
3. Окончательное решение принимает пользователь. Оно оформляется в виде ADR (Architecture Decision Record) в папке `reports/` (формат `ADR-*.md`) с обязательной пометкой: `Решение заказчика: [Выбранный вариант]`.

## 9. Минимизация контекста (Input Manifest)

Для экономии токенов и предотвращения "замыливания" внимания моделей, в каждом файле команды из папки `.cursor/commands/` прописывается жесткий блок `Input manifest`. 

Охранные правила `role-*.mdc` физически запрещают агенту читать файлы, не входящие в его текущий манифест. Единственные исключения, глобально открытые для чтения всем агентам:

- Глобальный конфигурационный файл `reports/project-config.md`.
- Файл собственного системного промпта агента.
- Контракт API `requirements/openapi.yaml` (при наличии в проекте открыт для Architect, Back-developer, Front-developer и Tech-writer).
- Корневые файлы конфигурации среды и зависимостей проекта (`requirements.txt`, `package.json`, `go.mod`, `.env.example`).

## 10. Копирование и развертывание в новый проект

Перенос **готовой** MAS из репозитория-образца в другой репозиторий. Это **не** создание MAS с нуля — см. §11.

**Предусловие:** целевой репозиторий готов принять ту же **каркасную** структуру папок (`requirements/`, `reports/`, `documentation/`, `artifacts/`, `diagrams/`, при разработке — `src/`, `tests/`). Скиллы и команды в `.cursor/` могут содержать примеры из проекта-источника — их нужно адаптировать под новый продукт (стек, чеклист срезов, интеграции).

Скрипты-генераторы среды **не используются**. Точка входа после копирования — `/pm`.

### 10.1. Что скопировать

| Что | Куда | Зачем |
| --- | --- | --- |
| Папка `.cursor/` целиком | корень нового репозитория | команды, агенты, скиллы, правила |
| `reports/templates/` | `reports/templates/` | шаблоны `project-config`, `pm-state`, traceability и др. |
| `reports/navigator.md` | `reports/navigator.md` | карта для ПМ; **переписать** product-specific блоки (§ «Этот репозиторий сейчас», чеклист срезов) |
| `AGENTS.md` | корень | общие инварианты агента, MAS, `Axxxx`, структура файлов |
| `documentation/mas-description.md` | `documentation/` | описание MAS (этот файл) |
| `documentation/project-structure-v1-1.md` | `documentation/` | опционально; синхрон с `.cursor/rules/rule-structure.mdc` |

**Не копировать слепо** из проекта-источника (создать заново в новом репозитории):

- `reports/checklist.md` — срезы MVP **конкретного** продукта;
- `reports/project-config.md`, `reports/pm-state.md` — ПМ создаст из шаблонов на первом `/pm`;
- `artifacts/vision-scope.md`, `artifacts/tz-gost-*.md` — через `/vision`, `/gost-3460289`;
- `requirements/*.md`, `requirements/user-stories/`, `requirements/use-cases/` — через `/ft`, `/nft`, `/us`, `/uc` и др.;
- `reports/agent-memory.md`, QC-отчёты, `test-run.md` — память и история чужого проекта.

### 10.2. Какие каталоги создать (пустые)

Минимум:

- `requirements/` — при необходимости подпапки `user-stories/`, `use-cases/`;
- `diagrams/`;
- `documentation/` — если ещё нет (предварительное ТЗ, README со стеком);
- `artifacts/`;
- `reports/` — кроме уже скопированных `templates/` и `navigator.md`; опционально `daily/`, `weekly/`, `release/`, `commit-audit/`.

При разработке ПО:

- `src/`, `tests/` (и `test-data/` — только по заданию).

Имена и назначение папок — по `documentation/project-structure-v1-1.md` или `.cursor/rules/rule-structure.mdc`.

### 10.3. Первый запуск

1. Положить в `documentation/` хотя бы черновик ТЗ или README с фактами: продукт, стек, интеграции (ПМ не выдумывает `Specification.md`).
2. Выполнить **`/pm`** (пустой вызов = статус).
3. ПМ создаёт `reports/project-config.md` и `reports/pm-state.md` из шаблонов, если файлов нет (`skill-agent-pm.md`).
4. **Заполнить** `reports/project-config.md`: имя продукта, стек, сценарий MAS (**S1** — новый без требований, **S2** — код без требований, **S3** — описанный проект).
5. Дальше — slash-команды по `reports/navigator.md` и `.cursor/list-commands.md` (`/ft`, `/nft`, `/vision`, …). Пустой `/pm` **не** запускает все роли подряд; нет команды `/full-cycle`.

### 10.4. Custom Agents в Cursor

Файлы `.cursor/agents/` — промпты ролей. Slash-команды из `.cursor/commands/` работают как команды проекта. При необходимости настройте Custom Agents в Cursor по `.cursor/list-commands.md` (таблица «Агенты MAS»). Прямые `/ft`, `/frontend` и остальные команды допустимы без ПМ.

### 10.5. Чеклист готовности переноса

- [ ] `.cursor/` и `reports/templates/` на месте
- [ ] `AGENTS.md` и `reports/navigator.md` скопированы и адаптированы
- [ ] Пустые каталоги из §10.2 созданы
- [ ] В `documentation/` есть вводные по продукту/стеку
- [ ] `/pm` отработал; `project-config.md` заполнен фактами **нового** репозитория
- [ ] Нет чужих `checklist.md`, артефактов `artifacts/` и таблиц `requirements/` из проекта-источника
- [ ] Product-specific формулировки в скиллах просмотрены (или вынесены в `project-config.md` / новый чеклист)

### 10.6. Краткая памятка (одним блоком)

1. Скопировать: `.cursor/`, `reports/templates/`, `reports/navigator.md`, `AGENTS.md`, `documentation/mas-description.md` (и при необходимости `project-structure-v1-1.md`).
2. Создать пустые каталоги: `requirements/`, `diagrams/`, `documentation/`, `artifacts/`, `reports/` (+ `src/`, `tests/` при коде).
3. Положить черновик ТЗ/README в `documentation/`.
4. Выполнить `/pm`; заполнить `project-config.md`.
5. Вести проект командами MAS; чеклист срезов и артефакты — создавать под **новый** продукт, не копировать из образца.

## 12. Дополнительные ограничения

1. Агентам запрещается устанавливать, изменять и удалять файлы и папки вне папки проекта за исключением выполнения прямой команды пользователя.
   - Например, для установки новых приложений в контейнерах Docker (папка F:\Docker)
2. Агенты могут использовать внешние приложения исключительно для реализации функциональных требований проекта. Если требуется доступ к новым внешним приложениям, агент должен предупредить об этом и попросить разрешение на доступ к приложению.
   - Например, можно использовать приложения контейнеров Docker (Redis, бэкенд FastAPI) только с разрешения пользователя.
3. PM обращается к пользователю в следующих случаях:
   - Для ответов пользователя на критические и важные вопросы по проекту.
   - После успешной проверки ФТ, НФТ, US, UC для изменения статуса черновик на статус согласования. Для получения статуса согласования также необходимо получить ответы на все заданные вопросы данного документа.
   - В случае конфликта ролей и обработки предложений ADR.
   - После успешного прохождения тестов для каждого этапа разработки фронтенда. 
   - В случае возникновения проблем, с которыми PM не может справиться без решения пользователя.
   - В иных случаях при необходимости получить решение пользователя.
