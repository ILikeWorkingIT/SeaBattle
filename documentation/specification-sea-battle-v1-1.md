# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
## Проект: «Sea Battle — Distributed PvE Game Engine»

---

## 1. Описание пет-проекта

**Sea Battle** — это клиент-серверная распределенная игровая система, реализующая классическую пошаговую тактическую игру «Морской бой» в режиме «Игрок против Серверного ИИ (PvE)». 

Проект спроектирован с упором на чистую архитектуру (**DDD / Clean Architecture**), строгую типизацию, асинхронные протоколы взаимодействия и алгоритмическую глубину серверного интеллекта.

### Ключевые цели проекта:
* **Инженерный полигон:** Отработка практик проектирования масштабируемых систем, контрактного взаимодействия (REST + WebSocket), тестирования и контейнеризации в Cursor IDE.
* **Масштабируемость и многосессионность:** Серверная часть поддерживает независимое параллельное ведение нескольких игровых сессий (до 3+ активных десктопных клиентов одновременно).
* **Алгоритмический ИИ:** Реализация вероятностно-эвристического алгоритма стрельбы бота (Heatmap / Probability Density Map) с динамическим пересчетом весов клеток поля перед каждым выстрелом.
* **Портфолио:** Демонстрация полного цикла разработки: от требований (US/UC, DDD) до рабочего desktop-приложения и контейнеризированного бэкенда со сбором аналитики.

## 2. Используемый стек технологий

### 2.1. Backend (Серверная часть)
* **Язык разработки:** Python 3.12+ (активное использование `match/case`, строгих аннотаций типов `typing`).
* **Web-фреймворк:** **FastAPI** (асинхронная обработка REST-запросов, встроенный ASGI-сервер `Uvicorn`).
* **Протоколы связи:**
  * **HTTP/REST (OpenAPI 3.1 / Pydantic v2):** Инициализация сессий, генерация полей, получение статистики.
  * **WebSockets (WSS):** Двунаправленный real-time канал для трансляции ходов бота, оповещений о смене состояний и синхронизации попаданий.
* **Архитектурный подход:** Domain-Driven Design (DDD) + Clean Architecture (разделение на слои: *Domain, Application/Use Cases, Infrastructure, Presentation/API*).
* **Тестирование и качество:** `pytest`, `pytest-asyncio`, `ruff` (линтер/форматтер), `mypy` (статический анализ типов).

### 2.2. Хранилище данных и СУБД (State & Analytics)
* **Redis (In-Memory Data Store):**
  * **Game Sessions:** Хранение оперативного состояния активных матчей (матрицы полей, история выстрелов, текущий ход) с установленным TTL.
  * **Analytics & Stats:** Атомарные счетчики (`INCR`, Hashes) для сбора глобальной статистики (всего игр, побед игрока, побед ИИ, среднее число ходов).

### 2.3. Frontend (Клиентская часть)
* **Фреймворк UI:** **PySide6 (Qt for Python 6.x)**.
* **Архитектура клиента:** Desktop GUI с неблокирующим event loop (`QThread` / `asyncio` интеграция через `qasync` или фоновые воркеры) для сетевого взаимодействия без зависания интерфейса.
* **Сетевой клиент:** `httpx` (асинхронный REST-клиент) + `websockets` (клиент постоянного соединения).

### 2.4. Инфраструктура и окружение
* **Контейнеризация:** `Docker`, `Docker Compose` (изолированный запуск бэкенда и экземпляра Redis).
* **Конфигурация:** `pydantic-settings` (.env файлы).

## 3. Описание предметной области и правила игры

Все термины, ограничения и механики базируются на канонических правилах классической игры «Морской бой» (Russian standard rules) и служат неизменным источником требований.

### 3.1. Игровое поле и флот
1. **Размер поля:** Квадратная матрица $10 \times 10$ клеток.
   * Координаты: По горизонтали — буквы (А–К / A–J, исключая «Ё» и «Й»); по вертикали — числа от 1 до 10. В API и памяти используется индексация $[0..9, 0..9]$.
2. **Состав флота каждого игрока (всего 10 кораблей / 20 палуб):**
   * 1 четырёхпалубный линкор ($1 \times 4$)
   * 2 трёхпалубных крейсера ($1 \times 3$)
   * 3 двухпалубных эсминца ($1 \times 2$)
   * 4 однопалубных катера ($1 \times 1$)

### 3.2. Правила расстановки
* Корабли размещаются строго прямолинейно (по горизонтали или по вертикали).
* Корабли не могут пересекаться или соприкасаться сторонами и углами (минимальная дистанция между любыми точками разных кораблей — 1 пустая клетка).
* **В рамках проекта:** Расстановка для игрока и бота выполняется сервером псевдослучайно с обязательной гарантией соблюдения всех правил валидации.

### 3.3. Правила ведения боя
1. **Очередность:** Игру начинает игрок.
2. **Результаты выстрела:**
   * **Промах (`MISS`):** Клетка помечается как проверенная. Право хода переходит к противоположной стороне.
   * **Попадание / Ранен (`HIT`):** Палуба повреждена. Стреляющий сохраняет право хода и делает следующий выстрел.
   * **Потоплен (`SUNK`):** Все палубы корабля уничтожены. Все клетки по периметру потопленного корабля (буферная зона) автоматически помечаются как «промах/пусто», так как другие корабли там находиться не могут. Стреляющий сохраняет право хода.
3. **Условие победы (`GAME_OVER`):** Полное уничтожение всех 10 кораблей (20 палуб) одного из участников.

## 4. Алгоритмическая модель серверного ИИ (Heatmap Bot)

Перед совершением каждого выстрела серверный алгоритм ИИ выполняет динамический расчет **матрицы вероятностей (Heatmap $10 \times 10$)**:

1. **Режим поиска (Hunt Mode):**
   * Вычисляется, какие нерассмотренные корабли игрока еще остались на плаву (их длины: 4, 3, 2, 1).
   * Для каждой оставшейся свободной клетки поля рассчитывается количество способов, которыми оставшиеся корабли могут быть размещены через эту клетку с учетом уже сделанных промахов и потопленных зон.
   * Клетки с наибольшим весом имеют наивысший приоритет для выстрела.
2. **Режим добивания (Target Mode):**
   * Активируется при наличии раненого, но еще не потопленного корабля.
   * Вероятность всех нерелевантных клеток обнуляется ($0\%$).
   * Вероятность клеток, соседствующих с ранением по оси возможного расположения корабля, получает максимальный вес.
3. **Исполнение:** Бот выбирает клетку с максимальным коэффициентом вероятности (при равных весах — случайный выбор из группы лидеров) и отправляет событие выстрела через WebSocket.
